Every command and option of the maplibre-yaml CLI (`@maplibre-yaml/cli`
0.6). For a walkthrough of `init`, `validate`, `preview` and `emit`, see
[The CLI (mlym)](/cli/getting-started/).

## Running the CLI

The CLI needs [Node.js](https://nodejs.org/) 20.9 or later. On an older Node
it stops with "maplibre-yaml needs Node.js 20.9 or newer".

It is one program with several names:

| You type | Works |
| -------- | ----- |
| `npx maplibre-yaml …` | Anywhere, with no install. npx downloads `maplibre-yaml`, a small package that runs `@maplibre-yaml/cli` |
| `npx @maplibre-yaml/cli …` | Anywhere, with no install: the full name |
| `npx mlym …` | After `npm install --save-dev @maplibre-yaml/cli` in the project. Without the install it fails with a 404, because no npm package is called `mlym` |
| `mlym …` or `maplibre-yaml …` | After `npm install -g @maplibre-yaml/cli`, in any folder; or in `package.json` scripts of a project that installed it |

The examples on this page use `npx maplibre-yaml`.

## Global options

| Option      | Alias | Description           |
| ----------- | ----- | --------------------- |
| `--help`    | `-h`  | Show help for a command (`npx maplibre-yaml init --help`) |
| `--version` |       | Show the CLI version  |

## Commands

### init

Create a new project from a template.

```bash
npx maplibre-yaml init [folder] [options]
```

| Argument | Required | Default | Description |
| -------- | -------- | ------- | ----------- |
| `folder` | No | `./<name>` (`./my-map` for `basic`) | Folder to create. It must not exist yet, or be empty |

| Option | Alias | Type | Default | Description |
| ------ | ----- | ---- | ------- | ----------- |
| `--template` | `-t` | string | `basic` | `basic`, `story` or `astro` |
| `--name` | `-n` | string | the folder's name | Project name, used for the page title and the map `id` |
| `--list` | | boolean | | List the templates and exit |

An unknown template or option (for example `--dir`, which `init` does not
have) prints an error and exits with code `1`, and nothing is created.

#### Templates

| Template | Creates | Run it with |
| -------- | ------- | ----------- |
| `basic` | `index.html` (CDN import map, `<ml-map>` with a height, viewport meta tag; core loads from the CDN at the release line this CLI was built with) and `map.yaml` (a street basemap and one clickable point) | `npx serve .` in the folder, then open the address it prints. Needs no install or build. Another local server works if it supports range requests (which PMTiles, FlatGeobuf, GeoParquet and COG files need); `python -m http.server` doesn't |
| `story` | `index.html` and a story file, `story.yaml` | A story map with no build step: the page loads `<ml-scrollytelling>` from the CDN, at the release line this CLI was built with. Serve the folder (`npx serve .`) and scroll; see [Story maps in plain HTML](/integrations/scrollytelling-html/) |
| `astro` | An Astro 7 site: a layout (with the viewport meta tag) and a page rendering `public/configs/map.yaml` with `@maplibre-yaml/astro`'s `<Map>`, the [optional integration](/integrations/astro/#editing-in-astro-dev) in `astro.config.mjs` with commented-out `site`/`base` lines for GitHub Pages, and a `.github/workflows/deploy.yml` that publishes it with `withastro/action`. Its `@maplibre-yaml/core` and `@maplibre-yaml/astro` ranges are the versions this CLI release was built with, and its `package.json` asks for Node.js 22.23.4 or later (Astro 7.4.2's own requirement) | `npm install`, then `npm run dev`. For GitHub Pages, set `site` and `base` in `astro.config.mjs` and push (see [Publishing & subpaths](/guides/publishing/#astro-sites)) |

Every YAML file the templates write starts with the
[schema modeline](/guides/editor-setup/), so editors with the YAML extension
complete and check it as you type. `init` prints the next steps for the
template it used.

```bash
npx maplibre-yaml init my-map                    # ./my-map from the basic template
npx maplibre-yaml init my-site --template astro  # an Astro site
npx maplibre-yaml init --list                    # list the templates
```

### validate

Check map documents and story files against the format. It reports
problems with their path in the document, a message, and the line and
column.

```bash
npx maplibre-yaml validate <patterns> [options]
```

| Argument   | Required | Description                                 |
| ---------- | -------- | ------------------------------------------- |
| `patterns` | Yes      | One or more file paths, folders or glob patterns. All of them are validated |

A pattern can be:

- a file: `map.yaml`;
- a folder: `maps/` (every `.yaml` and `.yml` file under it);
- a glob: `"maps/**/*.yaml"`. Quote it, so the CLI sees the pattern rather
  than your shell's expansion of it. A quoted pattern with a space in a folder
  name, `"My Maps/*.yaml"`, works;
- several of these: `"src/**/*.map.yaml" "maps/*.yaml"`.

Every argument is checked and reported. A file name that doesn't exist
prints `File not found: …`, and a pattern that matches nothing prints
`No files match "…"`. Both make the command exit with code `2` unless a file
also has errors (code `1`). Files excluded by `validate.ignorePatterns` in the
[project settings file](#configuration-file) are skipped, even when named
directly.

| Option     | Alias | Type    | Default | Description                                       |
| ---------- | ----- | ------- | ------- | ------------------------------------------------- |
| `--format` | `-f`  | string  | `human` | Output format: `human`, `json`, `sarif`, `vscode` ([below](#output-formats)) |
| `--strict` / `--no-strict` | | boolean | on in CI, off otherwise | Treat warnings as errors. Without either flag, strict mode is on when the `CI` environment variable is set (as CI services do) and off on your machine |
| `--strict-deprecations` | | boolean | `false` | Also treat deprecation warnings as errors (`--strict` leaves them as warnings) |
| `--watch`  | `-w`  | boolean | `false` | Keep running and re-validate each file when it changes. Only changed files are checked again |

`validate` reports three kinds of finding:

- **errors**: the document is invalid; the map won't render as written.
- **warnings**: valid, but probably not what you meant, such as a layer
  naming a source that isn't declared, or a map with no basemap. In strict
  mode they count as errors.
- **notes**: how a valid value is read, such as a basemap written as just a
  `.pmtiles` file. A note never makes a file invalid, even in strict mode.

```bash
npx maplibre-yaml validate map.yaml
npx maplibre-yaml validate "maps/**/*.yaml" --watch
npx maplibre-yaml validate "**/*.yaml" --format sarif > results.sarif
```

#### Output formats

**`human`** (the default) prints each file with a mark, then its findings
and a summary:

```text
⚠ map.yaml
  warning layers.0.source: Layer "quakes" uses source "quake", which is not declared under sources:. Did you mean "quakes"?
    at line 13, column 13

⚠ 1 file(s) with warnings: 1 warning(s)
```

A note prints as `ℹ note`, and a file with only notes is `✓` valid. With
more than 10 files, the human and `vscode` formats show a progress bar.

**`json`** prints one object: `valid`, a `files` array (each with its
absolute `file` path, `valid`, `errors` and `warnings`), and a `summary` of
counts. Each finding has `path`, `message`, `line`, `column` and `severity`;
notes are in `warnings` with `"severity": "note"` and are counted in
`summary.noteCount`, not `warningCount`. The full shape is in
[Using AI agents › The JSON output](/guides/ai-agents/#the-machine-error-contract).

**`sarif`** prints [SARIF 2.1.0](https://sarifweb.azurewebsites.net/), which
GitHub code scanning reads ([recipe below](#github-code-scanning)). Notes
have the SARIF level `note`.

**`vscode`** prints one line per finding,
`file:line:column: severity: [path] message`, where `severity` is `error`,
`warning`, or `info` for a note. VS Code's problem matcher reads it:
see [Validate on save](/guides/editor-setup/#validate-on-save-vs-code-task).

### preview

Start a local server that shows one YAML document, a map or a story map, on
a page of its own, and reloads it when you save the file.

```bash
npx maplibre-yaml preview <file> [options]
```

| Argument | Required | Description                     |
| -------- | -------- | ------------------------------- |
| `file` | Yes      | The map document or story file to show |

| Option      | Type    | Default | Description                              |
| ----------- | ------- | ------- | ---------------------------------------- |
| `--port`    | number  | `3000`  | Port for the server                      |
| `--no-open` | boolean |         | Don't open a browser tab (by default `preview` opens one) |
| `--debug`   | boolean | `false` | Show a panel with the parsed document as JSON. Maps only |

A mistake in the file shows as an overlay with the field path and message,
in place of the map. A status bar at the bottom shows whether the server is
connected and which file it shows. Data paths in the YAML resolve against
the YAML file's folder, which the server serves.

`preview` shows the document alone, not the HTML page you wrote around it.
To see your own page, serve the folder instead (for example `npx serve .`).

```bash
npx maplibre-yaml preview map.yaml
npx maplibre-yaml preview map.yaml --port 8080 --no-open
```

### emit

Export a map document to a standalone MapLibre `style.json`: a file that
opens in [Maputnik](https://maplibre.org/maputnik/) and renders in a plain
`new maplibregl.Map({ style })`, with no maplibre-yaml on the page. Only
`type: map` documents export, in [format v1 or v2](/guides/format-v2/).
[Export to style.json](/guides/export/) explains how to use the result, and
[Export classes](/guides/export-classes/) what happens to each part of the
document.

```bash
npx maplibre-yaml emit <file> [options]
```

| Argument | Required | Description |
| -------- | -------- | ----------- |
| `file` | Yes | Path to a `type: map` YAML document |

| Option | Alias | Type | Default | Description |
| ------ | ----- | ---- | ------- | ----------- |
| `--out` | `-o` | string | stdout | Write the style to this file. A folder (one that exists, or a path ending in `/`, like `dist/`) gets `style.json` inside it |
| `--with-fallbacks` | | boolean | on | Export what has a style.json fallback (markers become a symbol layer with pin images; `fitTo` becomes a fixed camera) and print a warning for each loss |
| `--strict` | | boolean | off | Refuse the export (exit `1`) if anything would change what the map shows. Cannot be combined with `--with-fallbacks` |
| `--target` | | string | | The maplibre-gl version the style is for, e.g. `5.6.0`. Features that version lacks (such as `state:` below its minimum, or `color-relief` below 5.6) are reported |
| `--trust` | | string | | Deprecated, and has no effect: it is no longer listed in `--help`, and passing it prints a note. Trust gates raw `!html` in popups and `click.emit` host events, and neither is part of a `style.json`, so it never changed the exported file. A later release will remove it |
| `--sprite-base` | | string | | Absolute URL where the folder holding the style will be served. Required, with `--out`, when the document generates sprite images (markers, `images:`), because MapLibre rejects relative sprite URLs |

Warnings go to stderr, so `npx maplibre-yaml emit map.yaml > style.json`
keeps the JSON clean. A part of the document with no style.json form prints
a `contract` warning, and a part whose look changes prints a `lossy` warning,
which `--strict` refuses ([Reading the report](/guides/export-classes/#reading-the-emit-report)).

Some documents need their data at export time. `emit` reads it the way the
published site would serve it: an `https://` URL is fetched, and a local path
resolves against the YAML file's folder, then the current folder and its
`public/` folder.

- A [`classify:`](/guides/thematic-maps/) layer with computed breaks
  (`method:`) has its source's data loaded, and the breaks are written into
  the style. If the data can't be loaded, the export fails and says why.
- A GeoJSON `url:` source is written as `data: <url>`, as the style spec
  expects, so the exported style loads it.
- [Large-data](/guides/cloud-native-data/) files: FlatGeobuf and GeoParquet
  are converted to inline GeoJSON; PMTiles and COG sources, and a Protomaps
  basemap, become `pmtiles://` and `cog://` URLs that the page showing the
  style must register. See
  [Large-data files in an exported style](/guides/export/#large-data-files-in-an-exported-style).

```bash
npx maplibre-yaml emit map.yaml                       # print the style
npx maplibre-yaml emit map.yaml --out dist/           # write dist/style.json
npx maplibre-yaml emit map.yaml --strict --out dist/  # fail on any loss (CI)
npx maplibre-yaml emit map.yaml --out dist/ --sprite-base https://maps.example.org/dist/
```

The last line exports a document with markers: it writes `style.json` and
the sprite files (`mlym.json`, `mlym.png` and their `@2x` versions) into
`dist/`, and the style points at them under `https://maps.example.org/dist/`.

### schema

Print the JSON Schema for a block, read from the installed
`@maplibre-yaml/core` package, so it matches the version `validate` checks
against. The schemas describe [format v1](/guides/format-v2/); there is no
JSON Schema for format v2.

```bash
npx maplibre-yaml schema [block] [options]
```

| Argument | Required | Default | Description                                          |
| -------- | -------- | ------- | ---------------------------------------------------- |
| `block`  | No       | `map`   | One of `map`, `scrollytelling`, `root`, `any`        |

| Option  | Alias | Type   | Description                                     |
| ------- | ----- | ------ | ----------------------------------------------- |
| `--out` | `-o`  | string | Write the schema to a file instead of stdout    |

```bash
npx maplibre-yaml schema map                         # print the map schema
npx maplibre-yaml schema any --out any.schema.json   # write a file for offline use
```

A modeline then points at the written file:

```yaml no-validate
# yaml-language-server: $schema=./any.schema.json
```

See [Editor setup](/guides/editor-setup/) and
[Using AI agents](/guides/ai-agents/) for what the schemas are used for.

### bake

Regenerate the pattern images a [Mapzen-classic](/examples/gallery/crosshatch/)
preset references. The classics are pure style spec, so their whole look
rides on `*-pattern` images; `bake` derives them reproducibly instead of
leaving them as unexplained binaries.

```bash
npx maplibre-yaml bake [preset] --out <dir>
```

| Preset | Writes | From |
| ------ | ------ | ---- |
| `crosshatch` | `earth.png`, `landuse.png`, `water.png` | Tangram's MIT-licensed crosshatch textures, vendored unmodified in the CLI package (`assets/tangram/`, with provenance). The hatches are pre-filtered for MapLibre, which samples patterns without mipmaps: twice the period, softened strokes, 32 tones |
| `crosshatch-walls` | `building-hatch.png` | Tangram's light pen hatch for a `fill-extrusion-pattern`, smoothed along the stroke so walls seen edge-on stay steady. The crosshatch document itself draws plain walls |
| `blueprint` | `grid.png` | A generated drafting grid |

With no preset, `bake` lists them. The docs gallery's committed images are
exactly this output — a test pins them pixel for pixel:

```bash
npx maplibre-yaml bake crosshatch --out docs/public/classics/crosshatch
npx maplibre-yaml bake blueprint --out docs/public/classics/blueprint
```

## Project settings file \{#configuration-file}

A `maplibre-yaml.config.json` file in the folder you run the CLI from sets
default options for `validate` and `preview`. A `.yaml`, `.yml`, `.js` or
`.mjs` file of the same name works too.

```json
{
  "validate": {
    "format": "human",
    "strict": false,
    "ignorePatterns": ["**/node_modules/**", "**/dist/**", "**/*.backup.yaml"]
  },
  "preview": {
    "port": 4000,
    "open": false
  }
}
```

An option you type on the command line wins, then the settings file, then
the built-in default. With the file above, `preview map.yaml` serves on port
4000 without opening a browser, and `preview map.yaml --port 5000` serves on
5000. The `preview` settings need CLI 0.6.1 or later; 0.6.0 ignores them.

| Setting | Type | Default | Description |
| ------- | ---- | ------- | ----------- |
| `validate.format` | string | `human` | Output format |
| `validate.strict` | boolean | on in CI | Treat warnings as errors |
| `validate.ignorePatterns` | string[] | `["**/node_modules/**", "**/dist/**"]` | Glob patterns to skip. Setting it replaces the default, so list those two again if you still want them skipped |
| `preview.port` | number | `3000` | Server port |
| `preview.open` | boolean | `true` | Open a browser tab |
| `preview.debug` | boolean | `false` | Show the debug panel |

## Exit codes

| Code | Meaning             | Commands          |
| ---- | ------------------- | ----------------- |
| `0`  | Success. For `emit`, the style was written; warnings, if any, are on stderr | All |
| `1`  | Invalid input: validation or YAML syntax errors, warnings in strict mode, an unknown template or option, a non-empty `init` folder, an `emit --strict` refusal | validate, emit, init, schema, bake |
| `2`  | File not found, or no file matched a pattern | validate, preview, emit |
| `4`  | Unexpected error (for `emit`, for example, a basemap or image that could not be fetched) | All |

## Environment variables

### CI

When `CI` is set (GitHub Actions and other CI services set it), `validate`
runs in strict mode unless you pass `--no-strict`.

### DEBUG

Set it to any value to print debug messages and the stack trace of an
unexpected error, for a bug report:

```bash
DEBUG=1 npx maplibre-yaml validate "**/*.yaml"
```

### NO_COLOR

Disable colored output:

```bash
NO_COLOR=1 npx maplibre-yaml validate map.yaml
```

## Integration examples

### npm scripts

With the CLI installed in the project (`npm install --save-dev
@maplibre-yaml/cli`), scripts can use the short name:

```json
{
  "scripts": {
    "validate": "mlym validate 'maps/**/*.yaml'",
    "validate:watch": "mlym validate 'maps/**/*.yaml' --watch",
    "preview": "mlym preview map.yaml",
    "export": "mlym emit map.yaml --strict --out dist/"
  }
}
```

### GitHub Actions

`validate` is strict in CI, so warnings fail the job too:

```yaml
name: Validate maps
on: [push, pull_request]
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npx maplibre-yaml validate "**/*.yaml"
```

### GitHub code scanning

SARIF output shows each finding as an annotation on the pull request:

```yaml
name: Code scanning
on: [push, pull_request]
jobs:
  analyze:
    runs-on: ubuntu-latest
    permissions:
      security-events: write
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npx maplibre-yaml validate "**/*.yaml" --format sarif > results.sarif
      - uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: results.sarif
```

### Pre-commit hook

With [husky](https://typicode.github.io/husky/), check the YAML files staged
for a commit (it does nothing when there are none):

```bash
#!/bin/sh
git diff --cached --name-only --diff-filter=ACM -- '*.yaml' '*.yml' \
  | xargs -r npx maplibre-yaml validate
```

## Troubleshooting

### Command not found

`mlym` and `maplibre-yaml` exist only after an install, and `npx mlym` fails
with a 404 without one. Use `npx maplibre-yaml`, or install the CLI (see
[Running the CLI](#running-the-cli)). After a global install, check that
your `PATH` includes npm's global bin folder (`npm prefix -g`).

### Glob patterns not matching files

- Quote the pattern, `"maps/**/*.yaml"`, so your shell doesn't expand it.
- Patterns are relative to the folder you run the command in.
- Check `validate.ignorePatterns` in the project settings file: `validate`
  prints `Skipped …: excluded by validate.ignorePatterns` for a file it
  skipped.

### Watch mode not detecting changes

- Check that the file matches the pattern you are watching.
- On Linux, a large tree can exceed the file-watcher limit; raise it
  (`fs.inotify.max_user_watches`) or watch a smaller pattern.

### Settings file ignored

The CLI reads `maplibre-yaml.config.*` from the folder you run it in, not
from the YAML file's folder. An option typed on the command line overrides
it.
