Complete reference for all maplibre-yaml CLI commands, options, and arguments.

## Running the CLI

The CLI needs [Node.js](https://nodejs.org/) 20.9 or later (22 or 24 LTS
recommended); on an older Node it stops with a message saying so. Every
example on this page uses `npx maplibre-yaml`, which works with no
install: npx downloads the CLI on first use. (`maplibre-yaml` is a small
package that runs `@maplibre-yaml/cli`; `npx @maplibre-yaml/cli` is the same
program under its full name.)

```bash
npx maplibre-yaml validate map.yaml
```

Installing the CLI gives you two shorter command names, `mlym` and
`maplibre-yaml`, for the same program:

```bash
# in a project: then run it as `npx mlym …` or from package.json scripts
npm install --save-dev @maplibre-yaml/cli
npx mlym validate map.yaml

# or globally: then `mlym …` works in any folder
npm install -g @maplibre-yaml/cli
mlym validate map.yaml
```

Without an install, `npx mlym` does not work: `mlym` exists only once
`@maplibre-yaml/cli` is installed. `npx maplibre-yaml …` does work without an
install (it is a small package that runs the CLI). Wherever this page says
`npx maplibre-yaml`, `npx @maplibre-yaml/cli` or an installed `mlym` does the
same.

| Option      | Alias | Description           |
| ----------- | ----- | --------------------- |
| `--help`    | `-h`  | Show help for a command (`npx maplibre-yaml init --help`) |

## Commands

### validate

Validate YAML configuration files against the maplibre-yaml schema.

```bash
npx maplibre-yaml validate <patterns> [options]
```

#### Arguments

| Argument   | Required | Description                                 |
| ---------- | -------- | ------------------------------------------- |
| `patterns` | Yes      | File path(s) or glob pattern(s) to validate |

Patterns can be:

- Single file: `map.yaml`
- Folder: `maps/` (every `.yaml` and `.yml` file under it)
- Glob pattern: `configs/**/*.yaml` (quote it, so the CLI sees the pattern;
  a quoted pattern with a space in a folder name, `"My Maps/*.yaml"`, works)
- Several of these: `src/**/*.map.yaml configs/*.yaml`

Every argument is checked and reported. A file name that doesn't exist prints
`File not found: …`, and a pattern that matches nothing prints `No files match
"…"`. Both make the command exit with code 2 unless a file also has errors
(code 1). Files excluded by `validate.ignorePatterns` in your
[project config](#configuration-file) are skipped, even when named directly.

#### Options

| Option     | Alias | Type    | Default | Description                                       |
| ---------- | ----- | ------- | ------- | ------------------------------------------------- |
| `--format` | `-f`  | string  | `human` | Output format: `human`, `json`, `sarif`, `vscode` |
| `--strict` / `--no-strict` | | boolean | on in CI, off otherwise | Treat warnings as errors. Without either flag, strict mode is on when the `CI` environment variable is set (as CI services do) and off on your machine |
| `--strict-deprecations` | | boolean | `false` | Also treat deprecation warnings as errors (`--strict` leaves them as warnings) |
| `--watch`  | `-w`  | boolean | `false` | Watch for changes and re-validate                 |

#### Output Formats

Besides errors, `validate` reports **warnings** (something that probably
isn't what you meant, such as a layer naming an undeclared source, or a map
with no basemap) and **notes** (how a valid value is read, such as a basemap
written as just a `.pmtiles` file). Notes never make a file invalid, and
`--strict` never turns them into errors.

**human** (default)

- Human-readable colored output
- Shows file paths with checkmarks/X marks
- Displays errors (`error`), warnings (`warning`) and notes (`ℹ note`) with
  their path, message, line and column
- Includes summary with counts

**json**

- Structured JSON output
- Machine-parseable
- Ideal for CI/CD pipelines
- Includes detailed error information with line/column numbers
- Notes are listed with the warnings, marked `"severity": "note"`, and
  counted in `summary.noteCount` (not in `warningCount`)

**sarif**

- [SARIF v2.1.0](https://sarifweb.azurewebsites.net/) format
- Compatible with GitHub Code Scanning
- Integrates with GitHub Advanced Security
- Provides rich error context; notes have the SARIF level `note`

**vscode**

- VS Code problem matcher compatible format
- Format: `file:line:column: severity: [path] message`, where `severity` is
  `error`, `warning`, or `info` for a note
- Use with VS Code tasks for IDE integration
- See [VS Code tasks](/guides/editor-setup/#validate-on-save-vs-code-task)

#### Exit Codes

| Code | Meaning                 |
| ---- | ----------------------- |
| `0`  | All files valid         |
| `1`  | Errors found, including YAML syntax errors (reported with line and column) |
| `2`  | No file matched the pattern(s) |
| `4`  | Unexpected internal error |

#### Examples

Validate a single file:

```bash
npx maplibre-yaml validate map.yaml
```

Validate with glob pattern:

```bash
npx maplibre-yaml validate "configs/**/*.yaml"
```

Validate multiple patterns:

```bash
npx maplibre-yaml validate "src/**/*.map.yaml" "configs/*.yaml"
```

JSON output for CI/CD:

```bash
npx maplibre-yaml validate "**/*.yaml" --format json
```

SARIF for GitHub Code Scanning:

```bash
npx maplibre-yaml validate "**/*.yaml" --format sarif > results.sarif
```

Strict mode (warnings as errors):

```bash
npx maplibre-yaml validate map.yaml --strict
```

Watch mode for development:

```bash
npx maplibre-yaml validate "configs/**/*.yaml" --watch
```

VS Code problem matcher format:

```bash
npx maplibre-yaml validate config.yaml --format vscode
```

### preview

Start a local development server to preview your map with hot reload.
`preview` renders the YAML document — a map (`type: map`) or a story
(`type: scrollytelling`, from CLI 0.5.0) — on a page of its own; to see the
HTML page you wrote around it, serve your folder instead (for example
`npx serve .`). `--debug` applies to maps only.

```bash
npx maplibre-yaml preview <config> [options]
```

#### Arguments

| Argument | Required | Description                     |
| -------- | -------- | ------------------------------- |
| `config` | Yes      | Path to YAML configuration file |

#### Options

| Option      | Type    | Default | Description                              |
| ----------- | ------- | ------- | ---------------------------------------- |
| `--port`    | number  | `3000`  | Port for development server              |
| `--open`    | boolean | `true`  | Open browser automatically               |
| `--no-open` | boolean |         | Don't open browser (keep server running) |
| `--debug`   | boolean | `false` | Show debug panel with config JSON        |

#### Features

- **Hot Reload**: Automatically updates map when YAML file changes
- **Error Overlay**: Shows validation errors (field path and message)
- **Status Bar**: Displays connection state and the file (relative to the folder you ran the command in; the full path on hover)
- **Live Validation**: Validates configuration on every change
- **Debug Panel**: Optional JSON view of parsed configuration

#### Examples

Basic preview:

```bash
npx maplibre-yaml preview map.yaml
```

Custom port:

```bash
npx maplibre-yaml preview map.yaml --port 8080
```

Don't open browser:

```bash
npx maplibre-yaml preview map.yaml --no-open
```

Debug mode:

```bash
npx maplibre-yaml preview map.yaml --debug
```

### init

Create a new project from a template.

```bash
npx maplibre-yaml init [folder] [options]
```

#### Arguments

| Argument | Required | Default | Description |
| -------- | -------- | ------- | ----------- |
| `folder` | No | `./<name>` (`./my-map` for `basic`) | Folder to create. It must not exist yet, or be empty |

#### Options

| Option | Alias | Type | Default | Description |
| ------ | ----- | ---- | ------- | ----------- |
| `--template` | `-t` | string | `basic` | `basic`, `story` or `astro` |
| `--name` | `-n` | string | the folder's name | Project name, used for the page title and the map `id` |
| `--list` | | boolean | | List the templates and exit |

An unknown template or option (for example `--dir`, which `init` does not
have) prints an error and exits with code `1`, and nothing is created.

#### Templates

| Template | Creates | Run it with |
| -------- | ------- | ----------- |
| `basic` | `index.html` (CDN import map, `<ml-map>` with a height, viewport meta tag; core loads from the CDN at the release line this CLI was built with) and `map.yaml` (a street basemap and one clickable point) | `npx serve .` in the folder, then open the address it prints. Needs no install or build. Another local server works if it supports range requests (which PMTiles, FlatGeobuf, GeoParquet and COG files need); `python -m http.server` doesn't |
| `story` | `index.html` and a scrollytelling `story.yaml` | A story map with no build step: the page loads `<ml-scrollytelling>` from the CDN, at the release line this CLI was built with. Serve the folder (`npx serve .`) and scroll; see [Story maps in plain HTML](/integrations/scrollytelling-html/) |
| `astro` | An Astro 7 site: a layout (with the viewport meta tag) and a page rendering `public/configs/map.yaml` with `@maplibre-yaml/astro`'s `<Map>`, the [optional integration](/integrations/astro/#editing-in-astro-dev) in `astro.config.mjs` with commented-out `site`/`base` lines for GitHub Pages, and a `.github/workflows/deploy.yml` that publishes it with `withastro/action`. Its `@maplibre-yaml/core` and `@maplibre-yaml/astro` ranges are the versions this CLI release was built with (`^0.9.0` and `^0.7.0` for CLI 0.6), and its `package.json` asks for Node.js 22.22 or later | `npm install`, then `npm run dev`. For GitHub Pages, set `site` and `base` in `astro.config.mjs` and push (see [Publishing & subpaths](/guides/publishing/#astro-sites)) |

Every YAML file the templates write starts with the
[schema modeline](/guides/editor-setup/), so editors with the YAML extension
complete and check it as you type. `init` prints the next steps for the
template it used.

#### Examples

Create `./my-map` from the basic template, then serve it:

```bash
npx maplibre-yaml init my-map
cd my-map
npx serve .
```

An Astro project:

```bash
npx maplibre-yaml init my-site --template astro
```

List the templates:

```bash
npx maplibre-yaml init --list
```

### emit

Export a map document to a standalone MapLibre `style.json`: a file that
opens in [Maputnik](https://maplibre.org/maputnik/) and renders in a plain
`new maplibregl.Map({ style })`, with no maplibre-yaml on the page. Only
`type: map` documents export. What happens to each construct (layers,
markers, popups, live data, …) is listed in
[Export classes](/guides/export-classes/).

```bash
npx maplibre-yaml emit <file> [options]
```

#### Arguments

| Argument | Required | Description |
| -------- | -------- | ----------- |
| `file` | Yes | Path to a `type: map` YAML document |

#### Options

| Option | Alias | Type | Default | Description |
| ------ | ----- | ---- | ------- | ----------- |
| `--out` | `-o` | string | stdout | Write the style to this file. A folder (one that exists, or a path ending in `/`, like `dist/`) gets `style.json` inside it |
| `--with-fallbacks` | | boolean | on | Export what has a style.json fallback (markers become a symbol layer with pin sprites, `fitTo` on inline data becomes a fixed camera, framed with the same default margin as the live map; on a `url:` source the authored `center`/`zoom` is kept, with a warning) and print a warning for each loss |
| `--strict` | | boolean | off | Refuse the export (exit `1`) if anything would change what the map shows. Cannot be combined with `--with-fallbacks` |
| `--target` | | string | | The maplibre-gl version the style is for, e.g. `5.6.0`. Features that version lacks (such as `state:` below its minimum, or `color-relief` below 5.6) are reported |
| `--trust` | | string | | Deprecated, and has no effect: it is no longer listed in `--help`, and passing it prints a note. Trust gates raw `!html` in popups and `click.emit` host events, and neither is part of a `style.json`, so it never changed the exported file. A later release will remove it |
| `--sprite-base` | | string | | Absolute URL where the folder holding the style will be served. Required, with `--out`, when the document generates sprite images (markers, `images:`), because MapLibre rejects relative sprite URLs |

Warnings go to stderr, so `npx maplibre-yaml emit map.yaml > style.json`
keeps the JSON clean.

Some documents need their data or files at export time. `emit` reads them
the way the published site would serve them: an `https://` URL is fetched,
and a local path resolves against the YAML file's folder, then the site
root and its `public/` folder.

- A [`classify:`](/guides/thematic-maps/) layer with computed breaks
  (`method:`) has its source's data loaded, and the breaks are written into
  the style. If the data can't be loaded, the export fails and says why.
- A GeoJSON `url:` source is written as `data: <url>`, as the style spec
  expects, so the exported style loads it.
- [FlatGeobuf and GeoParquet](/guides/cloud-native-data/) files are converted
  to inline GeoJSON (a file that can't be read leaves the source empty, with
  a warning that `--strict` refuses).
- PMTiles sources are written as `pmtiles://` URLs, COG sources as `cog://`
  URLs, and a Protomaps basemap shorthand as the full style it builds. The
  page showing the exported style must register those protocols itself; see
  [Exporting with `mlym emit`](/guides/cloud-native-data/#exporting-with-mlym-emit).

#### Exit codes

| Code | Meaning |
| ---- | ------- |
| `0` | Style written (warnings, if any, on stderr) |
| `1` | Not a valid map document, a `--strict` refusal, or bad arguments |
| `2` | Input file not found |
| `4` | Unexpected error (for example, the basemap or an image could not be fetched) |

#### Examples

Print the style:

```bash
npx maplibre-yaml emit map.yaml
```

Write `dist/style.json`:

```bash
npx maplibre-yaml emit map.yaml --out dist/
```

Fail instead of exporting with losses (for CI):

```bash
npx maplibre-yaml emit map.yaml --strict --out dist/style.json
```

A document with markers, exported with its generated pin sprites:

```bash
npx maplibre-yaml emit map.yaml --out dist/style.json --sprite-base https://maps.example.org/dist
```

### schema

Print the JSON Schema for a block, resolved from the installed
`@maplibre-yaml/core` package — so it always matches the version `validate`
enforces. Useful for offline editor integration and AI agents.

```bash
npx maplibre-yaml schema [block] [options]
```

#### Arguments

| Argument | Required | Default | Description                                          |
| -------- | -------- | ------- | ---------------------------------------------------- |
| `block`  | No       | `map`   | One of `map`, `scrollytelling`, `root`, `any`        |

#### Options

| Option  | Alias | Type   | Description                                     |
| ------- | ----- | ------ | ----------------------------------------------- |
| `--out` | `-o`  | string | Write the schema to a file instead of stdout    |

#### Examples

Print the map schema to stdout:

```bash
npx maplibre-yaml schema map
```

Write the combined (`any`) schema to a file for offline use:

```bash
npx maplibre-yaml schema any --out any.schema.json
```

Reference the written file from a config with a modeline:

```yaml
# yaml-language-server: $schema=./any.schema.json
```

See [Editor Setup](/guides/editor-setup/) and
[Using AI Agents](/guides/ai-agents/) for how these schemas power in-editor
validation and agent workflows.

### bake

Regenerate the pattern images a [Mapzen-classic](/examples/gallery/crosshatch/)
preset references. The classics are pure style spec, so their whole look
rides on `*-pattern` images; `bake` derives them reproducibly instead of
leaving them as unexplained binaries.

```bash
npx maplibre-yaml bake [preset] --out <dir>
```

| Preset | Writes | From |
| ------ | ------ | ---- |
| `crosshatch` | `earth.png`, `landuse.png`, `water.png`, `building-fallback.png` | Tangram's MIT-licensed crosshatch textures, vendored unmodified in the CLI package (`assets/tangram/`, with provenance) |
| `blueprint` | `grid.png` | A generated drafting grid |

With no preset, `bake` lists them. The docs gallery's committed images are
exactly this output — a test pins them pixel for pixel:

```bash
npx maplibre-yaml bake crosshatch --out docs/public/classics/crosshatch
npx maplibre-yaml bake blueprint --out docs/public/classics/blueprint
```

## Configuration File

Create `maplibre-yaml.config.json` in your project root to set default options
(`.yaml`, `.yml`, `.js` and `.mjs` versions of the same name work too):

```json
{
  "validate": {
    "format": "human",
    "strict": false,
    "ignorePatterns": ["**/node_modules/**", "**/dist/**", "**/*.backup.yaml"]
  },
  "preview": {
    "port": 3000,
    "open": true
  }
}
```

### Configuration Options

#### validate

| Option           | Type     | Default | Description              |
| ---------------- | -------- | ------- | ------------------------ |
| `format`         | string   | `human` | Default output format    |
| `strict`         | boolean  | on in CI | Treat warnings as errors |
| `ignorePatterns` | string[] | `["**/node_modules/**", "**/dist/**"]` | Glob patterns to ignore. Setting it replaces the default, so list those two again if you still want them skipped |

#### preview

| Option | Type    | Default | Description             |
| ------ | ------- | ------- | ----------------------- |
| `port` | number  | `3000`  | Default server port     |
| `open` | boolean | `true`  | Open browser by default |

CLI arguments always take precedence over config file settings.

## Performance

The CLI is optimized for speed:

| Operation              | Performance   |
| ---------------------- | ------------- |
| Single file validation | ~1ms          |
| 10 files validation    | ~3ms          |
| 100 files validation   | ~80ms         |
| Watch mode (cached)    | ~1ms per file |
| CLI startup (`--help`) | ~350ms        |

### Parallel Processing

The validate command checks up to 10 files at a time. For more than 10 files
(with `human` or `vscode` output), it checks them one after another and shows
a progress bar.

### Watch Mode Caching

Watch mode uses mtime-based caching to avoid re-validating unchanged files. Only modified files are re-validated, making watch mode extremely fast for development workflows.

## Exit Codes

All commands use consistent exit codes:

| Code | Meaning             | Commands          |
| ---- | ------------------- | ----------------- |
| `0`  | Success             | All               |
| `1`  | Invalid input: validation or YAML syntax errors, an unknown template or option, a non-empty `init` folder, a `--strict` emit refusal | validate, emit, init, schema, bake |
| `2`  | File not found      | validate, preview, emit |
| `4`  | Unexpected error    | All               |

Use exit codes in scripts and CI/CD pipelines to detect failures:

```bash
if npx maplibre-yaml validate "**/*.yaml"; then
  echo "All configurations valid"
else
  echo "Validation failed with exit code $?"
  exit 1
fi
```

## Environment Variables

### CI

When `CI` is set (GitHub Actions and other CI services set it), `validate`
runs in strict mode unless you pass `--no-strict`. See
[Options](#options).

### DEBUG

Set to any value to print debug messages and the stack trace of an
unexpected error, for a bug report:

```bash
DEBUG=1 npx maplibre-yaml validate "**/*.yaml"
```

### NO_COLOR

Disable colored output:

```bash
NO_COLOR=1 npx maplibre-yaml validate map.yaml
```

## Integration Examples

### npm Scripts

With the CLI installed in the project (`npm install --save-dev
@maplibre-yaml/cli`), scripts can use the short name. Add to `package.json`:

```json
{
  "scripts": {
    "validate": "mlym validate 'configs/**/*.yaml'",
    "validate:watch": "mlym validate 'configs/**/*.yaml' --watch",
    "preview": "mlym preview map.yaml",
    "validate:ci": "mlym validate '**/*.yaml' --format json --strict"
  }
}
```

### GitHub Actions

```yaml
name: Validate Maps
on: [push, pull_request]
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npx maplibre-yaml validate "**/*.yaml" --format json --strict
```

### GitHub Code Scanning

```yaml
name: Code Scanning
on: [push, pull_request]
jobs:
  analyze:
    runs-on: ubuntu-latest
    permissions:
      security-events: write
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npx maplibre-yaml validate "**/*.yaml" --format sarif > results.sarif
      - uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: results.sarif
```

### Pre-commit Hook

Using [husky](https://typicode.github.io/husky/):

```bash
#!/bin/sh
# Validate the YAML files staged for this commit (does nothing when there are none)
git diff --cached --name-only --diff-filter=ACM -- '*.yaml' '*.yml' \
  | xargs -r npx maplibre-yaml validate
```

## Troubleshooting

### Command not found

`mlym` and `maplibre-yaml` exist only after an install. Either:

1. Run it through npx with the package name: `npx maplibre-yaml <command>`
2. Install it in the project (`npm install --save-dev @maplibre-yaml/cli`) and run `npx mlym <command>`
3. Install it globally (`npm install -g @maplibre-yaml/cli`) and check that your PATH includes npm's global bin folder

### Glob patterns not matching files

- Quote patterns to prevent shell expansion: `"configs/**/*.yaml"`
- Use absolute paths or run from project root
- Check ignore patterns in config file

### Watch mode not detecting changes

- Ensure file is within watched pattern
- Check file system limits (increase with `ulimit -n 4096`)
- Verify file permissions

### Permission errors

- Ensure read access to all matched files
- Check directory permissions
- Run with appropriate user permissions
