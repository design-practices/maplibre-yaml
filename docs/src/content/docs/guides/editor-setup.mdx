maplibre-yaml publishes its contract as **JSON Schema**, so any editor backed by
the [YAML Language Server](https://github.com/redhat-developer/yaml-language-server)
(the engine behind the Red Hat **YAML** extension for VS Code, and available in
Neovim, JetBrains IDEs, and others) gives you autocomplete, hover documentation,
and inline validation — with **zero project install**.

<Aside type="note">
The JSON Schema is authoring assistance. `mlym validate` (Zod) remains the
source of truth: it enforces cross-field rules the JSON Schema cannot express.
See [Using maplibre-yaml with an AI agent](/guides/ai-agents/).
</Aside>

## Stable schema URLs

Each block type has a stable, versioned schema URL:

| Block            | Schema URL                                                        |
| ---------------- | ----------------------------------------------------------------- |
| `map`            | `https://docs.maplibre-yaml.org/schema/latest/map.schema.json`             |
| `scrollytelling` | `https://docs.maplibre-yaml.org/schema/latest/scrollytelling.schema.json`  |
| `root` (pages)   | `https://docs.maplibre-yaml.org/schema/latest/root.schema.json`            |
| any of the above | `https://docs.maplibre-yaml.org/schema/latest/any.schema.json`             |

`latest/` always tracks the newest release, and is what the files `mlym init`
creates use.

To pin a version, use the copy that ships inside the npm package, served by a
CDN. It exists for every release from 0.4 on and never moves:

```text
https://cdn.jsdelivr.net/npm/@maplibre-yaml/core@0.9/schemas/map.schema.json
```

Change the version after `core@` to the one your project uses: two numbers
(`major.minor`, as above) name a release line and give the newest release in
it, and three numbers (`major.minor.patch`) name exactly one release. The docs site also serves the current
release under `https://docs.maplibre-yaml.org/schema/v0.9/<block>.schema.json`;
addresses for older versions there redirect to the CDN copy.

## Option 1: The modeline (recommended)

Add a `yaml-language-server` **modeline** as the first line of your file. It
travels with the file, so anyone who opens it gets validation — no shared
settings required. This is the first line of every config the CLI scaffolds:

```yaml
# yaml-language-server: $schema=https://docs.maplibre-yaml.org/schema/latest/map.schema.json
type: map
id: my-map
config:
  center: [-74.006, 40.7128]
  zoom: 12
  mapStyle: "https://tiles.openfreemap.org/styles/liberty"
```

Use the schema that matches the file's block type:

## Option 2: VS Code `yaml.schemas` settings

If you would rather not put a modeline in every file, map globs to schemas in
your project's `.vscode/settings.json` (requires the Red Hat **YAML**
extension). This is the no-modeline alternative:

```json
{
  "yaml.schemas": {
    "https://docs.maplibre-yaml.org/schema/latest/map.schema.json": [
      "**/*.map.yaml",
      "configs/**/*.yaml"
    ],
    "https://docs.maplibre-yaml.org/schema/latest/scrollytelling.schema.json": [
      "**/*.story.yaml"
    ]
  },
  "files.associations": {
    "*.map.yaml": "yaml",
    "**/configs/**/*.yaml": "yaml"
  }
}
```

A complete example is in the repository:
[settings.json](https://github.com/design-practices/maplibre-yaml/blob/main/docs/examples/vscode/settings.json).

<Aside type="tip">
Modelines win over `yaml.schemas` when both are present, so you can set a broad
glob default and override per-file with a modeline.
</Aside>

## Offline / air-gapped

The same schemas ship inside the `@maplibre-yaml/core` npm package, as
`node_modules/@maplibre-yaml/core/schemas/<block>.schema.json` once core is
installed. A modeline can point straight at that file, relative to the YAML
file:

```yaml no-validate
# yaml-language-server: $schema=./node_modules/@maplibre-yaml/core/schemas/map.schema.json
type: map
```

(`@maplibre-yaml/core/schemas/json/<block>.schema.json` is the same file as a
package export, for tools that resolve imports, not for a modeline.) Or write
a copy next to your files with the CLI:

```bash
npx maplibre-yaml schema map --out map.schema.json
```

Then reference the local file:

```yaml no-validate
# yaml-language-server: $schema=./map.schema.json
type: map
```

`mlym schema` reads the schema from the installed core package, so it always
matches the version `mlym validate` enforces.

## What you get

- **Autocomplete** for every field, layer type, control, and source type.
- **Hover documentation** sourced from the same `.describe()` annotations that
  drive the docs.
- **Inline validation** for structure, enums, and types as you type.

Unknown top-level keys are flagged; `x-*` keys are always allowed, for
extensions. Arbitrary MapLibre GL options inside `config:` and
extra source options stay permissive, matching the runtime.

## Validate on save (VS Code task)

The schema checks structure as you type, but not the validator's own rules:
a layer naming a source the document doesn't declare (with a "did you mean"),
a misspelt `fitTo` source, or a map with no basemap. There is no
maplibre-yaml extension for VS Code; a **task** runs `mlym validate` instead,
and VS Code lists its errors, warnings and notes in the **Problems** panel,
next to the lines they belong to.

### Step 1: Add the task

Create or update `.vscode/tasks.json` in your project:

```json
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "maplibre-yaml: Validate Current File",
      "type": "shell",
      "command": "npx",
      "args": ["maplibre-yaml", "validate", "${file}", "--format", "vscode"],
      "problemMatcher": {
        "owner": "maplibre-yaml",
        "fileLocation": "absolute",
        "pattern": {
          "regexp": "^(.+):(\\d+):(\\d+): (error|warning|info): (.*)$",
          "file": 1,
          "line": 2,
          "column": 3,
          "severity": 4,
          "message": 5
        }
      },
      "presentation": {
        "reveal": "silent",
        "panel": "shared"
      },
      "group": "build"
    }
  ]
}
```

With the CLI installed in the project (`npm install --save-dev @maplibre-yaml/cli`),
`npx` uses that copy; otherwise it downloads it on first run.

### Step 2: Run the task

1. Open a `.yaml` file.
2. Press <kbd>Cmd</kbd>+<kbd>Shift</kbd>+<kbd>P</kbd> (Mac) or
   <kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>P</kbd> (Windows/Linux).
3. Type "Run Task" and choose **maplibre-yaml: Validate Current File**.

To run it from a shortcut instead, open **Keyboard Shortcuts**
(<kbd>Cmd</kbd>+<kbd>K</kbd> <kbd>Cmd</kbd>+<kbd>S</kbd>, or
<kbd>Ctrl</kbd>+<kbd>K</kbd> <kbd>Ctrl</kbd>+<kbd>S</kbd>), search for
"Run Task", and bind a key such as <kbd>Cmd</kbd>+<kbd>Shift</kbd>+<kbd>V</kbd>
to it.

### Step 3: Read the Problems panel

Findings appear in the **Problems** panel
(<kbd>Cmd</kbd>+<kbd>Shift</kbd>+<kbd>M</kbd> /
<kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>M</kbd>), each with its file, line and
column: click one to jump to it, and <kbd>F8</kbd> / <kbd>Shift</kbd>+<kbd>F8</kbd>
move to the next and previous one. Errors appear as errors; warnings (for
example a map with no basemap, or a style value starting with the reserved
`=`) as warnings; and notes, which explain how a valid value is read (such as
a basemap written as just a `.pmtiles` file), as information.

### Output format

`--format vscode` prints one line per finding, in the shape the problem
matcher reads, `file:line:column: severity: [path] message`, where severity is
`error`, `warning`, or `info` for a note:

```bash
npx maplibre-yaml validate config.yaml --format vscode
```

```text
/path/to/config.yaml:4:11: error: [config.center] center needs square brackets: center: [0, 0]
/path/to/config.yaml:3:1: warning: [config.mapStyle] No mapStyle: this map has no basemap. …
/path/to/other.yaml:6:3: info: [config.mapStyle] mapStyle: "data/nyc.pmtiles" names a .pmtiles file, so it is read as a Protomaps basemap …
```

The paths are absolute, which is why the task sets `"fileLocation": "absolute"`.

### Complete tasks.json

The repository has a [complete tasks.json](https://github.com/design-practices/maplibre-yaml/blob/main/docs/examples/vscode/tasks.json)
with three tasks, whose problem matchers pick up errors, warnings and notes:

- **Validate Current File**: validates the open file.
- **Validate All Configs**: validates every YAML file under `configs/`, with
  the findings grouped by file in the Problems panel.
- **Watch and Validate**: runs in the background with `--watch` and updates
  the Problems panel each time you save.

### Errors Don't Appear in Problems Panel

1. Check that the task includes `problemMatcher`.
2. Check that `--format vscode` is in the args.
3. Check that `fileLocation` is `"absolute"`: the CLI prints full paths.
4. Check the Problems panel's filter settings.
5. Notes missing? The `regexp` must match `info` as well as `error` and
   `warning`.

### Task Not Found

1. Check that `.vscode/tasks.json` is in the folder you opened in VS Code.
2. Reload the VS Code window.
3. Check that the JSON is valid.

On the first run, VS Code may ask whether to allow the task to run: choose
**Allow**. See VS Code's [Tasks documentation](https://code.visualstudio.com/docs/editor/tasks)
and [problem matchers](https://code.visualstudio.com/docs/editor/tasks#_defining-a-problem-matcher)
for more.
