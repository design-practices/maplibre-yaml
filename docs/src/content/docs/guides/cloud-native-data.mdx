"Cloud-native" files are made to be read **in parts**, straight from a web
server: the browser asks for the bytes it needs (HTTP *range requests*), so a
map can draw a city from a country-sized file without downloading all of it.
Since 0.9, maplibre-yaml reads three of them with nothing but YAML — in plain
HTML from the CDN, in Astro, and under any bundler:

| Format | File | Holds | Source `type:` |
|---|---|---|---|
| **PMTiles** | `.pmtiles` | Vector tiles, raster tiles or elevation, in one file | `vector`, `raster`, `raster-dem` |
| **FlatGeobuf** | `.fgb` | Features (points, lines, polygons) with their properties | `geojson` |
| **Cloud Optimized GeoTIFF (COG)** | `.tif`, `.tiff` | One image: imagery, elevation, or a band of values (in Web Mercator) | `raster`, `raster-dem` |

## The rule: `type:` is what MapLibre draws, the URL is what the file is

You keep writing the source type MapLibre knows — `vector`, `raster`,
`raster-dem`, `geojson` — and point `url:` at the file. The file name tells
maplibre-yaml how to read it.

```yaml
type: map
id: cloud-native-minimal
config:
  center: [10.2, 42.15]
  zoom: 10
  mapStyle: "https://tiles.openfreemap.org/styles/positron"
sources:
  outlines:
    type: vector
    url: /gallery-assets/cloud-native/districts.pmtiles
  districts:
    type: geojson
    url: /gallery-assets/cloud-native/districts.fgb
layers:
  - id: districts
    type: fill
    source: districts
    paint: { fill-color: "#e9c46a", fill-opacity: 0.6 }
  - id: outlines
    type: line
    source: outlines
    source-layer: districts
    paint: { line-color: "#1d3557" }
```

That is the whole setup: no `<script>` to register anything, no extra import
map entry. Layers, popups, the legend, `fitTo` and clustering work exactly as
they do for any other source.

- **`pmtiles://`** in front of the URL works too (`url: pmtiles://data/x.pmtiles`
  or `pmtiles://https://example.org/x.pmtiles`) — it's the form MapLibre's own
  examples use.
- **`format:`** names the format when the URL can't — a signed link or an API
  endpoint with no file extension. It wins over the URL.

```yaml
sources:
  parcels:
    type: geojson
    url: "https://data.example.org/api/parcels?f=fgb"
    format: flatgeobuf
```

<Aside type="caution" title="type: pmtiles is a mistake (with a fix)">
`type: pmtiles`, `type: flatgeobuf`, `type: fgb`, `type: cog` and similar are
rejected with a message that says what to write instead (`type: vector` with
the `.pmtiles` URL; `type: geojson` with the `.fgb` URL; `type: raster` with
the `.tif` URL). A `.fgb` file on a `vector` source, or a `.pmtiles` or `.tif`
file on a `geojson` source, is caught the same way. All of this happens at validation time, so `mlym validate` and the
Astro content loader report it too.
</Aside>

## PMTiles

One `.pmtiles` file holds a whole tile pyramid. Vector, raster and elevation
archives all work:

```yaml
sources:
  buildings:
    type: vector
    url: data/buildings.pmtiles     # layers say which source-layer to draw
  imagery:
    type: raster
    url: data/imagery.pmtiles
    tileSize: 256                   # most raster archives use 256-pixel tiles
  terrain:
    type: raster-dem
    url: data/terrain.pmtiles
    encoding: terrarium
```

- The archive's own metadata (zoom range, bounds, attribution, vector layer
  names) reaches MapLibre, so you rarely need `minzoom`/`maxzoom` here.
- **Framing:** a tile archive has no client-side extent to fit, so `fitTo`
  doesn't apply to PMTiles sources in 0.9 — set `center`/`zoom` (or `bounds`)
  for where the data is.
- **Making one:** `tippecanoe -o buildings.pmtiles buildings.geojson` (vector),
  `ogr2ogr -f PMTiles out.pmtiles in.gpkg`, or `pmtiles convert in.mbtiles
  out.pmtiles` for an existing MBTiles file (a browser can't read `.mbtiles`
  directly).
- **A page that registers its own `pmtiles` protocol keeps it.** If your page
  already does `addProtocol("pmtiles", …)` through `@maplibre-yaml/core/maplibre`
  (the 0.7 way, still supported — for custom headers or a custom `Source`),
  maplibre-yaml leaves that registration alone.

### PMTiles inside a basemap style

A basemap style loaded from a URL can use PMTiles too, with no page
JavaScript: `mapStyle:` (or `basemap:` in format v2) can point at a style
whose sources are `pmtiles://` URLs, such as a Protomaps basemap or one you
host yourself (below). maplibre-yaml registers the `pmtiles://` protocol
before the map is created, so the style's first requests find it. A page that
registered its own `pmtiles` protocol keeps it.

**Relative URLs inside the style are relative to the style.json**, the way a
stylesheet's `url()` is relative to the stylesheet. That applies to a source's
`url` (including the file inside `pmtiles://`), `tiles`, `sprite` and
`glyphs`. MapLibre by itself would resolve them against the page, which
breaks as soon as the page and the style live in different folders. `base`
applies to the style URL itself, so a style under `base="/my-repo/"` finds its
own files under `/my-repo/` too. If the style names a file that isn't there,
the map's notice says which one, instead of showing a blank basemap.

## Host your own basemap

A basemap can be one PMTiles file next to your site, served by the same static
host, with no tile server and no API key:

1. **Cut a regional extract** from the Protomaps daily planet build with the
   [`pmtiles` command-line tool](https://docs.protomaps.com/pmtiles/cli):

   ```bash
   pmtiles extract https://build.protomaps.com/<date>.pmtiles nyc.pmtiles \
     --bbox=-74.26,40.48,-73.70,40.92
   ```

   Pick `<date>` from [build.protomaps.com](https://build.protomaps.com/).
   The tool reads only the part of the planet it needs.
2. **Get a style** for it. Protomaps publishes basemap styles (light, dark,
   grayscale and others) for exactly these tiles; see
   [Protomaps basemaps](https://docs.protomaps.com/basemaps/maplibre). Save the
   style as `style.json` beside the file and point its source at it:
   `"url": "pmtiles://nyc.pmtiles"`. Its `glyphs` and `sprite` can stay on
   Protomaps' asset host, or be copied next to the style and named relatively.
3. **Use it** from your document:

   ```yaml
   config:
     mapStyle: basemap/style.json   # public/basemap/ in an Astro or Vite site
   ```

**Size.** A city extract is typically tens of MB; a large region or a country
can be hundreds of MB or more. GitHub refuses files over 100 MB in a
repository, and a GitHub Pages site is limited to 1 GB, so keep extracts to
the area you show (a smaller `--bbox`, or a lower `--maxzoom`, shrinks the
file). For larger areas, use a host meant for big files, such as an object
store.

**Hosting.** The file is read with HTTP range requests, like any PMTiles file:
GitHub Pages, Netlify, Cloudflare, S3 and R2 support them;
`python -m http.server` does not (see
[Hosting](#hosting-range-requests-and-cors)).

## FlatGeobuf

A `.fgb` file is read into an ordinary GeoJSON source, so everything that
works with a `.geojson` file works with it. Two ways to read it, with `load:`:

| `load:` | What it reads | Needs |
|---|---|---|
| `all` (default) | The whole file, once | Any web server |
| `viewport` | Only the features in view, re-read as the map moves; nothing below `minzoom` (default 10) | A file with a **spatial index**, and a server with **range requests** |

```yaml
sources:
  districts:
    type: geojson
    url: data/districts.fgb                  # small file: read whole
  parcels:
    type: geojson
    url: https://data.example.org/parcels.fgb
    load: { mode: viewport, minzoom: 14 }    # big file: only what's in view
```

**Sizes.** Reading a file whole costs memory and time in the browser, so:

- up to **10 MB**: read whole, no remarks;
- **10–50 MB**: read whole, with a console note suggesting `load: viewport`
  or PMTiles;
- over **50 MB**: not read whole. A file with a spatial index is read by view
  instead (with a console note); one without is refused, and the map says so.

As a rule of thumb, whole-file data is comfortable up to about 100,000 simple
features (~20 MB). Beyond that, use `load: viewport`, or PMTiles for anything
large and static.

- **Coordinates:** the file must be longitude/latitude (EPSG:4326). A file in
  another projection is refused with the `ogr2ogr` command that fixes it.
- **Compression:** write the file uncompressed. A Zstandard-compressed
  FlatGeobuf is recognized and refused with a notice saying so (`zstd -d`
  decompresses it).
- **Making one:** `ogr2ogr -f FlatGeobuf -lco SPATIAL_INDEX=YES out.fgb
  in.geojson` (the index is GDAL's default; QGIS's "Export → FlatGeobuf" works
  too).
- **Live data** (`refresh:`, `stream:`) isn't available for FlatGeobuf
  sources in 0.9 — validation says so. Serve GeoJSON for data that changes.
- **`fitTo`** frames the decoded features; with `load: viewport` it frames
  the extent recorded in the file's header.
- **`classify:`** with computed classes (`method:`) needs the whole file. On a
  source read by view — `load: viewport`, or a file over 50 MB that switched
  to it — validation (for `load: viewport`) or the map (for the size switch)
  asks for explicit `breaks:` instead, which work either way. See
  [Thematic maps](/guides/thematic-maps/).

## Cloud Optimized GeoTIFF (COG)

A COG is an ordinary GeoTIFF laid out for the web: its pixels are stored in
tiles, with smaller copies (overviews) for zoomed-out views, so the browser
reads only the parts it draws. Satellite and aerial imagery, elevation models
and gridded measurements (vegetation, temperature) are often published this
way.

<Aside type="caution" title="COGs must be in Web Mercator (EPSG:3857)">
maplibre-yaml draws COGs that are in Web Mercator, the projection of web map
tiles, and does not reproject them in the browser. A COG in another
projection, such as longitude/latitude (EPSG:4326) or a national grid, is
refused with a notice that gives the command to convert it (see
[Making a COG](#making-a-cog)).
</Aside>

### Imagery

A `.tif` URL on a `raster` source:

```yaml
sources:
  imagery:
    type: raster
    url: data/imagery.tif           # or cog://data/imagery.tif
layers:
  - { id: imagery, type: raster, source: imagery }
```

RGB, greyscale and paletted images draw in their own colours. maplibre-yaml
sets `tileSize: 256` (the size the COG reader draws), unless you set one
yourself. A URL without a telling extension takes `format: cog`.

### Elevation: hillshade and terrain

The same kind of file on a `raster-dem` source is read as elevation (in
metres, from the first band). It drives `hillshade` layers and 3D `terrain:`
exactly like any other elevation source:

```yaml
type: map
id: cog-elevation
config:
  center: [10.2, 42.15]
  zoom: 10
  pitch: 50
  mapStyle: "https://tiles.openfreemap.org/styles/positron"
sources:
  elevation:
    type: raster-dem
    url: /gallery-assets/cloud-native/elevation.cog.tif
terrain:
  source: elevation
  exaggeration: 1.5
layers:
  - id: hills
    type: hillshade
    source: elevation
    paint: { hillshade-exaggeration: 0.5 }
```

You don't write `encoding:`: the COG reader converts the heights to MapLibre's
`mapbox` (Terrain-RGB) encoding, and maplibre-yaml sets that for you.

### One band of values: `colorRamp`

A COG with a single band of measurements (a vegetation index, a temperature, a
probability) has no colours of its own. `colorRamp:` maps the values from
`min` to `max` onto a palette:

```yaml
type: map
id: cog-vegetation
config:
  center: [10.2, 42.15]
  zoom: 9.4
  mapStyle: "https://tiles.openfreemap.org/styles/positron"
sources:
  vegetation:
    type: raster
    url: /gallery-assets/cloud-native/ndvi.cog.tif
    colorRamp: { palette: YlGn, min: 0, max: 0.85 }
layers:
  - { id: vegetation, type: raster, source: vegetation }
```

| Key | Meaning |
|---|---|
| `palette` | A palette name, the same ones [`classify:`](/guides/thematic-maps/) uses: `viridis` (the default), `cividis`, and the ColorBrewer names (`YlGn`, `Blues`, `RdBu`, `Spectral` …). A misspelt name gets a did-you-mean. |
| `colors` | Your own colours instead of a palette, low to high: `colors: ["#2c7bb6", "#ffffbf", "#d7191c"]` |
| `min`, `max` | The values drawn in the first and last colour (required). Values outside the range take the end colours. |
| `reverse` | `true` runs the colours from high to low. |
| `classes` | A number of flat classes (`classes: 5`) instead of a smooth ramp. |

Pixels the file marks as having no value (its NoData value, or NaN) are left
transparent. `colorRamp:` applies to `raster` sources only; in a format v2
document it goes under the source's `runtime:`.

### Making a COG

[GDAL](https://gdal.org/) (3.1 or later; it also ships with QGIS) writes
COGs. One command reprojects any georeferenced raster to Web Mercator and
writes it as a COG:

```bash
gdalwarp -t_srs EPSG:3857 -of COG -co COMPRESS=DEFLATE input.tif output.tif
```

A GeoTIFF that is already in Web Mercator but isn't cloud-optimized (stored
in strips, or without overviews) is converted with:

```bash
gdal_translate -of COG -co COMPRESS=DEFLATE input.tif output.tif
```

- `-co COMPRESS=DEFLATE` is lossless; `-co COMPRESS=JPEG` makes imagery much
  smaller (lossy, for photos only, not for elevation or measurements).
- `-co TILING_SCHEME=GoogleMapsCompatible` (with `gdalwarp` or
  `gdal_translate`) also aligns the file with web map tiles, which makes reads
  a little more efficient.
- Check a file with `gdalinfo output.tif`: it should report
  `Coordinate System is: … "WGS 84 / Pseudo-Mercator"`, `LAYOUT=COG` and
  overviews.

An ordinary GeoTIFF still draws, but the browser may have to download most of
the file to show it, so while you develop the map's notice says so, with the
`gdal_translate` command.

### Size

A COG can be any size: the browser reads only the tiles in view, at the
resolution the view needs, through the overviews. The limits are the host's:
GitHub refuses files over 100 MB in a repository and a GitHub Pages site is
limited to 1 GB in total, so for a large mosaic use an object store (S3, R2,
Google Cloud Storage) and point `url:` at it. Clip the file to the area you
show (`gdalwarp -te …`), and pick the compression that suits the data
(above), to keep it small.

- **Framing:** `fitTo: { source: imagery }` frames the COG's own extent,
  read from the file.
- **A page that registers its own `cog` protocol keeps it.** If your page
  already calls `addProtocol("cog", …)` through `@maplibre-yaml/core/maplibre`
  (for example to send request headers), maplibre-yaml leaves it alone.
- **Content Security Policy:** the COG reader decodes images in background
  workers it starts from `blob:` URLs. A site with a strict CSP needs
  `worker-src 'self' blob:`; without it, the map's notice says the COG
  couldn't be read and why.

## Hosting: range requests and CORS

PMTiles and COG always, and FlatGeobuf with `load: viewport`, read files
**in parts** with HTTP range requests. Most static hosts support them:

| Host | Range requests | Notes |
|---|---|---|
| GitHub Pages | yes | On a project site (`user.github.io/repo/`) set `base` — see below |
| Netlify, Cloudflare Pages, Vercel | yes | |
| Amazon S3, Cloudflare R2, Google Cloud Storage | yes | From another site, set CORS (below) |
| `npx serve`, `astro dev`, `astro preview`, Vite | yes | Good for previewing locally |
| `python -m http.server` | **no** | PMTiles and COGs fail; `load: viewport` falls back to reading the whole file |

**Files on another site** need CORS: the bucket or server must send
`Access-Control-Allow-Origin`, allow the `Range` request header, and expose
`Content-Range` and `Content-Length`. For S3 or R2, a CORS rule like:

```json
[
  {
    "AllowedOrigins": ["https://you.github.io"],
    "AllowedMethods": ["GET", "HEAD"],
    "AllowedHeaders": ["Range", "If-Match"],
    "ExposeHeaders": ["Content-Range", "Content-Length", "ETag"],
    "MaxAgeSeconds": 3000
  }
]
```

**GitHub Pages project sites** serve your files under `/repo-name/`. Set the
`base` attribute (`<ml-map base="/repo-name/">`; Astro passes its own `base`
automatically) and write paths as you would on your own computer —
`data/x.pmtiles`, `/data/x.fgb`, `data/x.tif` and `pmtiles://data/x.pmtiles`
all resolve under the base.

## When something goes wrong

Problems with one file never take down the map: the basemap and every other
layer still draw, and the map's notice ("Part of this map couldn't load")
says what happened in plain words. The common cases:

| What happened | What the notice says |
|---|---|
| The server doesn't support range requests | "`…/x.pmtiles` was served without range-request support (the server sent the whole file instead of the part asked for). PMTiles, COG and FlatGeobuf files need a web server that supports HTTP range requests: GitHub Pages, Netlify, Cloudflare, S3 and R2 do; `python -m http.server` does not — preview locally with `npx serve` instead." |
| Another site refused (CORS), or it's unreachable | "The browser couldn't read `…`: the server didn't allow this page to load it (CORS), or it couldn't be reached. A PMTiles file on another site needs that site to send `Access-Control-Allow-Origin` and to allow the `Range` header." |
| A wrong path that returned a web page | "`…/x.pmtiles` isn't a PMTiles file. A wrong path often returns a web page instead — check the file name and folder." |
| The file isn't there | "`…/x.fgb` didn't load (404 Not Found)", with where the browser looked and the `base` hint for project sites |
| A FlatGeobuf in the wrong projection | "`…/x.fgb` is in EPSG:3857; MapLibre needs longitude/latitude (EPSG:4326). Reproject it: `ogr2ogr -t_srs EPSG:4326 out.fgb x.fgb`." |
| Too large to read whole, no index | "`…/x.fgb` is 180 MB, too large to load whole in a browser. Add `load: viewport` to the source (the file needs a spatial index), or convert it to PMTiles." |
| The format's reader couldn't be downloaded | "The PMTiles reader (`…/chunks/pmtiles.js`) couldn't be downloaded. maplibre-yaml loads its file-format readers on demand from the folder its script came from: if you copied maplibre-yaml to your own site, copy the whole `dist/` folder (not just `register.js`), or load it from the CDN. …" |
| A COG that isn't in Web Mercator | "`…/x.tif` is in EPSG:4326; a COG must be in Web Mercator (EPSG:3857) to be drawn. Reproject it: `gdalwarp -t_srs EPSG:3857 -of COG -co COMPRESS=DEFLATE x.tif out.tif` (GDAL 3.1 or later)." |
| A GeoTIFF that isn't cloud-optimized (a hint while developing; it still draws) | "`…/x.tif` is a GeoTIFF but not a Cloud Optimized one (it has no internal tiles or no overviews), so the browser may download most of the file to draw it. Convert it: `gdal_translate -of COG -co COMPRESS=DEFLATE x.tif out.tif`." |
| A strict Content Security Policy | "The Cloud Optimized GeoTIFF (COG) reader couldn't be set up (this page's Content Security Policy doesn't allow the background workers COG images are decoded in; allow them with `worker-src 'self' blob:`) …" |

The readers for these formats are not part of maplibre-yaml's main script:
a page downloads the PMTiles reader (about 8 KB), the FlatGeobuf reader
(about 12 KB) or the COG reader (about 220 KB, with its image codecs) only when a map uses that
format, from `dist/chunks/` next to
the script. From a CDN that is automatic; if you host maplibre-yaml's files
yourself, copy the whole `dist/` folder
([Installation](/getting-started/installation/#hosting-the-files-yourself)).

## Format v2

In a [format v2](/guides/format-v2/) document the URL stays in the source and
`format:` / `load:` / `colorRamp:` move under the source's `runtime:`:

```yaml
version: 2
type: map
id: cloud-native-v2
style:
  basemap: "https://tiles.openfreemap.org/styles/positron"
  center: [10.2, 42.15]
  zoom: 10
  sources:
    outlines: { type: vector, url: /gallery-assets/cloud-native/districts.pmtiles }
    points:
      type: geojson
      url: /gallery-assets/cloud-native/points.fgb
      runtime:
        load: { mode: viewport, minzoom: 11 }
    vegetation:
      type: raster
      url: /gallery-assets/cloud-native/ndvi.cog.tif
      runtime:
        colorRamp: { palette: YlGn, min: 0, max: 0.85 }
  layers:
    - { id: vegetation, type: raster, source: vegetation }
    - { id: outlines, type: line, source: outlines, source-layer: districts }
    - { id: points, type: circle, source: points }
```

## Exporting with `mlym emit`

A `style.json` can carry a URL but not a file reader, so:

- **PMTiles** export as `pmtiles://` URLs (a `.pmtiles` URL gains the
  scheme). The style then needs a renderer that reads `pmtiles://`, such as
  maplibre-gl JS with the protocol registered. With a bundler, after
  `npm install pmtiles`:

  ```js
  import maplibregl from "maplibre-gl";
  import { Protocol } from "pmtiles";
  maplibregl.addProtocol("pmtiles", new Protocol().tile);
  ```

  In a plain HTML page, import `addProtocol` from the `maplibre-gl` your import
  map names and `Protocol` from `https://esm.sh/pmtiles@4` (esm.sh resolves
  its dependencies; unpkg does not), before the map is created.
- **COG** sources export as `cog://` URLs, in the form the map itself uses:
  `#dem` on an elevation source, a `colorRamp:` written out as the COG
  protocol's `#color:` fragment, and `tileSize: 256`. As with PMTiles, the
  style then needs the protocol registered — here the one from
  [`@geomatico/maplibre-cog-protocol`](https://github.com/geomatico/maplibre-cog-protocol),
  which maplibre-yaml uses itself. With a bundler, after
  `npm install @geomatico/maplibre-cog-protocol`:

  ```js
  import maplibregl from "maplibre-gl";
  import { cogProtocol } from "@geomatico/maplibre-cog-protocol";
  maplibregl.addProtocol("cog", cogProtocol);
  ```

  In a plain HTML page, load the plugin's own browser build
  (`<script src="https://unpkg.com/@geomatico/maplibre-cog-protocol@0.10/dist/index.js"></script>`,
  which defines `MaplibreCOGProtocol`) and call
  `addProtocol("cog", MaplibreCOGProtocol.cogProtocol)` on the `maplibre-gl`
  your import map names, before the map is created.
- **FlatGeobuf** is converted: `mlym emit` reads the file (next to the YAML,
  in the current folder or its `public/`, or over http(s)) and writes its
  features into the style as GeoJSON. If it can't read the file, the source
  is emitted empty and reported, and `--strict` refuses.

See [Export classes](/guides/export-classes/) for the full table.

## Coming later: GeoParquet

One more format is recognized already, so documents written today keep their
meaning when support arrives: **GeoParquet** (`.parquet`, `.geoparquet`,
`format: geoparquet`) on a `geojson` source.

In this version it validates with a warning and shows "can't read … yet (it's
planned)" on the map instead of a confusing error; the rest of the map draws.
Until then, convert GeoParquet to FlatGeobuf (`ogr2ogr out.fgb in.parquet`).
