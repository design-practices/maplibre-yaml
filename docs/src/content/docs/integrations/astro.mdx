Astro is a natural fit for maplibre-yaml - both embrace configuration-driven approaches. This guide covers integrating maps into Astro sites, from simple page embeds to reusable components.

<Aside type="tip" title="Recommended: Use the src Attribute">
  The simplest approach is to place YAML files in the `/public` directory and use the `src` attribute. The web component handles loading and parsing automatically.
</Aside>

## Quick Start

Get a map in a new Astro site in 5 minutes. Every command is shown for npm,
which is what `npm create astro` sets up; use the pnpm or Yarn tab only if your
project already uses that package manager (mixing them leaves you with two
lockfiles).

<Aside type="tip" title="Starting from nothing? Two shortcuts">
  `npx maplibre-yaml init my-site --template astro` (or `mlym init --template
  astro` with the CLI installed) creates a whole site with a map, ready for
  GitHub Pages ([init](/cli/reference/#init)). For every step from an empty
  folder to a published site, follow
  [Quick start: Astro site on GitHub Pages](/getting-started/astro/).
</Aside>

<Steps>

1. **Create an Astro project** (skip this if you already have one)

   ```bash
   npm create astro@latest -- --template minimal
   ```

   Then `cd` into the folder it created.

2. **Install the packages**

   <Tabs syncKey="pkg">
   <TabItem label="npm">
   ```bash
   npm install @maplibre-yaml/astro @maplibre-yaml/core maplibre-gl@^6
   ```
   </TabItem>
   <TabItem label="pnpm">
   ```bash
   pnpm add @maplibre-yaml/astro @maplibre-yaml/core maplibre-gl@^6
   ```
   </TabItem>
   <TabItem label="Yarn">
   ```bash
   yarn add @maplibre-yaml/astro @maplibre-yaml/core maplibre-gl@^6
   ```
   </TabItem>
   </Tabs>

   maplibre-gl 4, 5 and 6 (`>= 6.4.1`) are supported; v6 is recommended. The
   `@maplibre-yaml/astro` components set maplibre-gl 6's worker URL and load
   its stylesheet for you, so this Quick Start needs no extra setup.

3. **Create a map configuration file**

   Create `public/configs/hero-map.yaml` (make the `configs` folder inside
   `public/`):

   ```yaml
   type: map
   id: hero-map
   config:
     center: [-74.006, 40.7128]
     zoom: 12
     mapStyle: "https://tiles.openfreemap.org/styles/liberty"
   layers:
     - id: marker
       type: circle
       source:
         type: geojson
         data:
           type: FeatureCollection
           features:
             - type: Feature
               geometry:
                 type: Point
                 coordinates: [-74.006, 40.7128]
               properties:
                 name: "New York City"
       paint:
         circle-radius: 12
         circle-color: "#3b82f6"
         circle-stroke-width: 2
         circle-stroke-color: "#ffffff"
   ```

   Files in `public/` are served from the site root, so this one is at
   `/configs/hero-map.yaml`. `mapStyle` is the basemap: any MapLibre style
   URL, or a Protomaps `.pmtiles` file you keep in `public/`
   (`mapStyle: { pmtiles: data/city.pmtiles, flavor: light }`), which needs no
   API key ([Host your own basemap](/guides/cloud-native-data/#host-your-own-basemap)).

4. **Put the map on a page**

   Replace the contents of `src/pages/index.astro` with:

   ```astro
   ---
   import { Map } from '@maplibre-yaml/astro';
   ---

   <html lang="en">
     <head>
       <meta charset="utf-8" />
       <meta name="viewport" content="width=device-width" />
       <title>My map</title>
     </head>
     <body>
       <h1>Welcome</h1>
       <Map src="/configs/hero-map.yaml" height="500px" />
     </body>
   </html>
   ```

5. **Run it**

   ```bash
   npm run dev
   ```

   Open the address it prints (usually `http://localhost:4321`). You should
   see a street map of New York with a blue dot (a map that takes more than
   a second shows a small "Loading map…" until the basemap draws). If the
   YAML has a mistake, the map shows an error card naming the field instead.

</Steps>

Publishing on GitHub Pages? A project site is served under `/<repo>/`: set
`base` in `astro.config.mjs` as [Deploying to GitHub Pages](#deploying-to-github-pages-or-any-subpath)
shows. `Map` and `FullPageMap` then put the paths in your YAML under it for
you.

Next: load the YAML at build time so mistakes fail the build
([Basic Usage](#basic-usage-with-map-component)), or tell a story with
[`<Scrollytelling>`](#scrollytelling-component).

### Using `<ml-map>` directly

The `@maplibre-yaml/astro` components above are the easiest path. If you write
your own component around the `<ml-map>` web element instead (the
[Component Patterns](#component-patterns) below), it has to do what the
components do for you: load MapLibre's stylesheet, point maplibre-gl 6 at its
worker, and register the element.

```astro
---
// src/components/MyMap.astro
import 'maplibre-gl/dist/maplibre-gl.css'; // page CSS: here, not in the script tag
interface Props {
  src: string;
  height?: string;
}

const { src, height = '400px' } = Astro.props;
---

<!-- base: paths in the YAML (and src) start at your site's base, on every page -->
<ml-map src={src} base={import.meta.env.BASE_URL} style={`height: ${height}; display: block;`}></ml-map>

<script>
  // maplibre-gl 6 loads its worker from a separate file. Inside a Vite/Astro
  // bundle it cannot find that file by itself, so tell it where it is.
  import { setWorkerUrl } from 'maplibre-gl';
  import workerUrl from 'maplibre-gl/dist/maplibre-gl-worker.mjs?worker&url';
  import '@maplibre-yaml/core/register';

  setWorkerUrl(workerUrl);
</script>
```

The order of these lines does not matter: since `@maplibre-yaml/core` 0.7.1,
`<ml-map>` waits until the page's scripts have run before it builds its map,
so the worker URL is always in place first. Leave out the `setWorkerUrl` lines
and maplibre-gl 6 cannot start, which the map reports on the page as
*Worker failed to load*. On maplibre-gl 4 or 5, delete the two worker lines
(there is no worker file to import, and the build fails if you keep them).

Import the stylesheet in the frontmatter, as above, and the register module in
the `<script>`. A CSS import in the frontmatter is page CSS, which Astro puts
in the page's `<head>` in dev and build alike. From the `<script>`, `astro dev`
injects it with JavaScript instead, and with
[view transitions](#view-transitions) the next navigation drops
it. The register module is the opposite: it must stay in the `<script>`
([why](#referenceerror-htmlelement-is-not-defined)).

## Using @maplibre-yaml/astro Package

<Aside type="tip" title="Recommended for Astro Projects">
  The `@maplibre-yaml/astro` package provides native Astro components with built-in TypeScript support, better error handling, and improved developer experience.
</Aside>

For Astro projects, we recommend using the dedicated `@maplibre-yaml/astro` package instead of the core web components directly. This package provides:

- **Native Astro Components** - Designed specifically for Astro's architecture
- **Build-Time Loading** - Load and validate YAML at build time for better performance
- **Runtime Loading** - Or load from `/public` for dynamic configs
- **TypeScript Support** - Full type safety with MapBlock types
- **Error Handling** - Beautiful error messages with validation details
- **Content Collections** - Schema helpers for Astro Content Collections

### Supported versions

| Astro | Supported | Notes |
|-------|-----------|-------|
| **7** | Yes, tested in CI | Needs Node 22.22 or newer (Astro 7.4's own requirement, `engines.node >=22.22.0`). |
| **6** | Yes, tested in CI | Build collection schemas with `z` from `astro/zod` (see below). |
| **5** | Yes, tested in CI | |
| **4** | Yes, tested in CI | Content-layer collections need three changes, listed below. |

This needs `@maplibre-yaml/astro` 0.5 or later. Earlier versions declare
`astro: ^4 || ^5`, so `npm install` refuses them on Astro 6 and 7.
`@maplibre-yaml/astro` 0.7 needs `@maplibre-yaml/core` 0.9 or later (its peer
range is `>=0.9.0`), so install and upgrade the two together. Every major
is tested the same way. CI builds the [example site](#runnable-example) against
the published tarballs with `astro check`, `astro build` and `astro preview`, then
drives it in a browser. It also runs a smoke test under `astro dev`. The
`maplibre-gl` peer range is `^4 || ^5 || ^6.4.1`; the example site runs on v6.

**Collections and zod.** Astro 4 and 5 ship zod 3. Astro 6 and 7 ship zod 4.
The two cannot nest inside each other. Import `z` from `astro/zod`, which
works on all four majors. The `/utils` schema helpers are built from the same
module, so `LocationPointSchema` and the others nest in your `z.object()` on
every major. (`z` from `astro:content` is the same object, but Astro 6
deprecated that export.) The `getCollectionItemWith*Schema()` helpers type
`entry.data` fully on every major from `@maplibre-yaml/astro` 0.6; on 0.5,
`astro check` on Astro 6 and 7 typed every field `unknown`.

**Astro 4 only.** The `glob()` collection loaders on this page need three
changes:

- Turn on `experimental: { contentLayer: true }` in `astro.config.mjs`.
- Keep the config in `src/content/config.ts`. Astro 4 does not read
  `src/content.config.ts`. A one-line `export { collections } from
  "../content.config";` there serves both: Astro 5+ prefer `src/content.config.ts`.
- Point `base` outside `src/content/`. Astro 4's `glob()` skips files there,
  and the folder becomes a legacy collection whose ids keep the extension
  (`park.md`).

The example site does all three.

<Aside type="caution" title="Older releases: astro dev with @maplibre-yaml/core 0.6.0 or earlier">
  Current releases are not affected. With core 0.6.0 or earlier, every
  `@maplibre-yaml/astro` component fails under `astro dev` with *Failed to
  create map: Map is not a constructor*, while `astro build` works: Vite never
  pre-bundles maplibre-gl when only a dependency's `.astro` file imports it.
  If you are stuck on 0.6.0, tell Vite to pre-bundle it:

  ```js
  // astro.config.mjs
  import { defineConfig } from "astro/config";

  export default defineConfig({
    vite: { optimizeDeps: { include: ["maplibre-gl"] } },
  });
  ```
</Aside>

### Runnable example

[`examples/astro/site`](https://github.com/design-practices/maplibre-yaml/tree/main/examples/astro/site)
is a small site, *Ring of Fire*, that uses every pattern on this page. CI
builds it and drives it in a browser on Astro 4, 5, 6 and 7. The snippets
below marked with a file name are copied from it, and a test fails if they
drift.

| Page | Shows |
|------|-------|
| `/` | `<Map config>` from `loadMapConfig`, `<Map src>`, corner slots |
| `/explore` | `<FullPageMap>` with zoom/reset controls, `showLegend`, markers, a parameters panel, hover popups |
| `/story` | `<Scrollytelling config>`: chapters move the camera, toggle layers, run every action type |
| `/story-runtime` | `<Scrollytelling src>`, loaded in the browser |
| `/volcanoes` | A Markdown collection (`glob()` + `LocationPointSchema`), one page per entry via `buildMapConfigFromEntry` |
| `/gallery` | A YAML collection of whole map documents (`extendSchema(getMapSchema(), …)`) |
| `/field-notes/…` | Dated posts on `getCollectionItemWithLocationSchema()`, one point map each via `buildPointMapConfig` |
| `/transitions` | `<FullPageMap>` and `<Map>` under `<ClientRouter />` view transitions |

Run it from a clone with `pnpm install && pnpm build`, then
`pnpm --filter @maplibre-yaml/example-astro-site dev`. To run the CI check for
one major, use `node scripts/astro-matrix.mjs --majors 7`.

Its content config works unchanged on all four majors:

```ts title="examples/astro/site/src/content.config.ts"
import { defineCollection } from "astro:content";
import { glob } from "astro/loaders";
// `astro/zod` is the zod your Astro version ships: zod 3 on Astro 4/5,
// zod 4 on Astro 6/7. The /utils helpers are built from the same module,
// so they nest inside these objects on every major.
import { z } from "astro/zod";
import {
  LocationPointSchema,
  getMapSchema,
  extendSchema,
  getCollectionItemWithLocationSchema,
} from "@maplibre-yaml/astro/utils";

/** `fuji.md` -> `fuji` on every Astro major (Astro 4 keeps the extension). */
const stripExtension = ({ entry }: { entry: string }) => entry.replace(/\.[^.]+$/, "");

/** Markdown entries with a point location in their frontmatter. */
const volcanoes = defineCollection({
  loader: glob({ pattern: "*.md", base: "./src/collections/volcanoes", generateId: stripExtension }),
  schema: z.object({
    title: z.string(),
    country: z.string(),
    elevation: z.number(),
    lastEruption: z.number(),
    location: LocationPointSchema,
  }),
});

/** Whole map documents as YAML data entries, plus two fields of our own. */
const maps = defineCollection({
  loader: glob({ pattern: "*.yaml", base: "./src/collections/maps", generateId: stripExtension }),
  schema: extendSchema(getMapSchema(), {
    title: z.string(),
    blurb: z.string(),
  }),
});

/**
 * Dated posts with an optional location: the collections guide's Quick Start
 * helper plus one custom field. `astro check` on every major type-checks the
 * /field-notes pages against this schema's inferred types (ml-aot.23: on
 * Astro 6/7 every field used to infer as `unknown`).
 */
const fieldNotes = defineCollection({
  loader: glob({ pattern: "*.md", base: "./src/collections/field-notes", generateId: stripExtension }),
  schema: getCollectionItemWithLocationSchema({
    volcano: z.string(),
  }),
});

export const collections = { volcanoes, maps, "field-notes": fieldNotes };
```

### Basic Usage with Map Component

The `Map` component is the simplest way to add a map to your Astro site:

<Tabs>
<TabItem label="Runtime Loading">

**Load YAML from `/public` directory:**

```astro
---
// src/pages/index.astro
import { Map } from '@maplibre-yaml/astro';
---

<Map
  src="/configs/map.yaml"
  height="500px"
  class="my-map"
/>
```

Place your YAML file in `/public/configs/map.yaml`:

```yaml
type: map
id: my-map
config:
  center: [-120, 37]
  zoom: 4
  mapStyle: "https://tiles.openfreemap.org/styles/liberty"
layers:
  - id: points
    type: circle
    source:
      type: geojson
      url: "https://earthquake.usgs.gov/earthquakes/feed/v1.0/summary/all_week.geojson"
    paint:
      circle-radius: 6
      circle-color: "#007cbf"
```

`<Map src>` hands the URL to `<ml-map src>`, which fetches, parses and
validates the file in the browser and shows its own error card if any of that
fails.

<Aside type="caution" title="src needs @maplibre-yaml/astro newer than 0.4.1">
  In 0.4.1 and earlier, `src` on `Map` and `FullPageMap` never loads in the
  browser. The console shows *Failed to resolve module specifier
  '@maplibre-yaml/core'* and the map shows *No configuration provided*. On
  those versions, use build-time loading (`config`).
</Aside>

</TabItem>
<TabItem label="Build-Time Loading">

**Load and validate YAML at build time:**

```astro
---
// src/pages/index.astro
import { Map, loadMapConfig } from '@maplibre-yaml/astro';

// Loaded at build time - validates YAML and catches errors early
const config = await loadMapConfig('./src/configs/map.yaml');
---

<Map
  config={config}
  height="600px"
  style="border: 2px solid #e2e8f0; border-radius: 8px;"
/>
```

**Benefits of build-time loading:**
- ✅ Validates configuration during build
- ✅ Catches errors before deployment
- ✅ Faster page loads (no runtime YAML parsing)
- ✅ Better for static site generation

</TabItem>
</Tabs>

### Map Component API

```typescript
interface MapProps {
  // Data source (one required)
  src?: string;              // Path to YAML file in /public
  config?: MapBlock;         // Pre-loaded configuration

  // Styling
  height?: string;           // Container height (default: "400px")
  class?: string;            // CSS class name
  style?: string;            // Inline styles

  // Where the paths in the document start (default: your site's base,
  // import.meta.env.BASE_URL). false = resolve relative paths against the page.
  base?: string | false;

  // Hide on-page notices for non-fatal problems (default: false)
  quiet?: boolean;

  // Show author hints on the page wherever it is served (default: false)
  debug?: boolean;
}
```

If you pass both, `config` wins and the component warns at build time.

`quiet` hides the "Part of this map couldn't load" notice (a data file that
404'd, a layer that failed) and the zero-height hint, for a finished site
whose visitors shouldn't see author-facing details. The problems are still
logged to the browser console, and a fatal problem (a document that doesn't
validate, a basemap that never loads) still shows its error card. The small
"Loading map…" shown while a slow map starts is not a notice, so `quiet`
leaves it; hide it with `ml-map .ml-map-loading { display: none; }` if the
page has its own loading indicator. `FullPageMap` and `Scrollytelling` take
the same prop.

The notice always lists **failures**. **Author hints** — a "did you mean", a
key nested under `config:`, coordinates that look written [latitude,
longitude], a value starting with the reserved `=` — show only while you
develop: in `astro dev` (on any address, a Codespaces URL included) and
when the site is served from your computer (`astro preview` on
`localhost`). The built site you deploy doesn't show them. Add `debug` to
show them on a deployed page too, while you check it; `quiet` still wins.
`FullPageMap` and `Scrollytelling` take the same prop (on `Scrollytelling`
it also outlines the chapters). The full rules are under
[when something goes wrong](/integrations/web-components/#when-something-goes-wrong).

### Corner slots

Children with `slot="top-left"`, `"top-right"`, `"bottom-left"`,
`"bottom-right"` or `"legend"` are forwarded to `<ml-map>`'s corner system,
which places them in that corner of the map and stacks them with the built-in
legend and parameters panel. A `legend` slot replaces the built-in legend.
`Map`, `FullPageMap` and `Scrollytelling` all forward them:

```astro title="examples/astro/site/src/pages/index.astro"
<Map config={ringOfFire} height="480px">
  <p slot="top-left" class="caption" data-testid="hero-caption">
    <strong>16 volcanoes, one plate boundary</strong>
    Hover a dot for its name and height.
  </p>
  <a slot="bottom-right" class="caption" href="/explore">Explore full screen &rarr;</a>
</Map>
```

Corners with no content render nothing. `FullPageMap`'s zoom and reset buttons
already sit in `top-right`, and your `top-right` content stacks below them.
Their labels come from the document's `locale:` table
(`NavigationControl.ZoomIn`, `NavigationControl.ZoomOut` and
`maplibre-yaml.FullPageMap.ResetView` — see [Accessibility &
languages](/guides/accessibility-languages/)).

**Examples** (each line is a separate usage, in a page that imports `Map`):

```astro
<!-- Minimal -->
<Map src="/maps/simple.yaml" />

<!-- With custom height -->
<Map src="/maps/dashboard.yaml" height="100vh" />

<!-- With styling -->
<Map
  src="/maps/styled.yaml"
  height="500px"
  class="shadow-lg rounded-lg"
  style="border: 1px solid #ccc;"
/>
```

Build-time loaded:

```astro
---
import { Map, loadMapConfig } from '@maplibre-yaml/astro';
const earthquakes = await loadMapConfig('./src/maps/earthquakes.yaml');
---
<Map config={earthquakes} height="600px" />
```

### Loading Utilities

The package provides utilities for loading YAML configurations:

#### loadMapConfig()

Load and validate a map configuration from a file:

```astro
---
import { loadMapConfig, Map } from '@maplibre-yaml/astro';

// Paths resolve from the project root (where `astro build` runs).
// A missing or invalid file throws YAMLLoadError, which fails the build.
const config = await loadMapConfig('./src/configs/my-map.yaml');
// config is fully typed as MapBlock
---

<Map config={config} />
```

To report errors before failing, see [Error Handling](#error-handling) below.

#### loadFromGlob()

Load multiple configurations at once:

```astro
---
import { loadFromGlob, Map } from '@maplibre-yaml/astro';
import { YAMLParser } from '@maplibre-yaml/core';

// A leading "/" is the project root. A "./" pattern resolves against THIS
// page file, so './src/configs/*.yaml' from src/pages/ matches nothing.
const configFiles = import.meta.glob<string>('/src/configs/*.yaml', {
  query: '?raw',
  import: 'default',
});
const maps = await loadFromGlob(
  configFiles,
  (yaml) => YAMLParser.safeParseMapBlock(yaml)
);
---

<div class="map-gallery">
  {maps.map(({ path, config }) => (
    <div>
      <h2>{config.id} <small>{path}</small></h2>
      <Map config={config} height="400px" />
    </div>
  ))}
</div>
```

If any file fails validation, `loadFromGlob` throws a single `YAMLLoadError`
listing every failing file, which fails the build. A pattern that matches
nothing returns an empty array without an error.

#### Other loaders and types

`loadScrollytellingConfig(path)` loads and validates a story the way
`loadMapConfig` loads a map (see [Scrollytelling Component](#scrollytelling-component)).
`loadYAML(path, schema?)` reads any YAML file with core's parse options and,
given a zod schema, validates it; without one it returns the parsed value
unchecked.

The package exports the types of its props and builders for your own
components: `MapProps`, `FullPageMapProps`, `ScrollytellingProps`,
`ChapterProps`, the frontmatter shapes `LocationPoint`, `RegionPolygon`,
`RouteLine` and `FeatureRef`, and the builder options (`PointMapOptions`,
`MultiPointMapOptions`, `PolygonMapOptions`, `RouteMapOptions`, …):

```typescript
import type { MapProps, LocationPoint } from '@maplibre-yaml/astro';
```

### Content Collections Integration

Use Astro Content Collections for managing map configurations:

**1. Define collection schema:**

<Aside type="caution" title="Use the /utils subpath in content config">
  When importing schemas in `src/content.config.ts`, use `@maplibre-yaml/astro/utils` rather than `@maplibre-yaml/astro`. The main entry re-exports Astro components (`Map`, `FullPageMap`, `Scrollytelling`) which can't be loaded outside the Astro component pipeline. Importing them in a content-config file produces errors like `Content config not loaded` or `Cannot read properties of undefined (reading 'get')`. The `/utils` subpath contains only the schemas and builders -- safe everywhere.
</Aside>

```typescript
// src/content.config.ts
import { defineCollection } from 'astro:content';
import { glob } from 'astro/loaders';
import { getMapSchema } from '@maplibre-yaml/astro/utils';

export const collections = {
  maps: defineCollection({
    loader: glob({ pattern: '**/*.yaml', base: './src/collections/maps' }),
    schema: getMapSchema()
  })
};
```

**2. Add YAML files:**

```yaml
# src/collections/maps/earthquake-map.yaml
type: map
id: earthquake-map
config:
  center: [-120, 35]
  zoom: 6
  mapStyle: "https://tiles.openfreemap.org/styles/liberty"
layers:
  - id: earthquakes
    type: circle
    source:
      type: geojson
      url: "https://earthquake.usgs.gov/earthquakes/feed/v1.0/summary/all_week.geojson"
    paint:
      circle-radius: 8
      circle-color: "#ff4444"
```

**3. Query and use in pages:**

```astro
---
import { getEntry } from 'astro:content';
import { Map } from '@maplibre-yaml/astro';

const earthquakeMap = await getEntry('maps', 'earthquake-map');
if (!earthquakeMap) throw new Error('maps/earthquake-map.yaml not found');
---

<Map config={earthquakeMap.data} height="600px" />
```

### Error Handling

With `src`, problems surface in the browser: `<ml-map>` replaces the map with
an error card and dispatches `ml-map:error`:

```astro
<!-- Invalid YAML or network error will show error message -->
<Map src="/configs/broken.yaml" />
```

Error display includes:
- **YAML Syntax Errors**: Shows parsing error with details
- **Validation Errors**: Lists all validation failures with paths (for example `config.zoom: Expected number, got string`)
- **Missing files**: a *Map file not found* card with the status and the address the browser asked for (for example `Couldn't load src="/configs/missing.yaml": 404 Not Found.`), and a hint when the site looks like it is served under a subpath

With `config`, the same problems surface at build time instead, in the
`astro dev` error overlay and the `astro build` output. The message names the
file, each failing field with its line, and the parser's warnings, which often
explain the error:

```
Scrollytelling configuration validation failed for ./src/stories/trip.yaml:
  error   Chapter 3 ("summit"): Unknown key "centre" — did you mean "center"? ("center" is required here.) (line 81, column 5)
```

To handle them yourself:

```astro
---
import { Map, loadMapConfig, YAMLLoadError } from '@maplibre-yaml/astro';

let config;
try {
  config = await loadMapConfig('./src/configs/map.yaml');
} catch (error) {
  if (error instanceof YAMLLoadError) {
    // `errors` is set for validation failures; a missing file or a YAML
    // syntax error carries only `message` (and the original as `cause`).
    console.error(`${error.filePath}: ${error.message}`);
    // Each entry's `message` already names the file, field and line;
    // `e.path`, `e.line` and `e.reason` hold the parts.
    error.errors?.forEach(e => {
      console.error(`  ${e.message}`);
    });
  }
  throw error; // Fail build on invalid config
}
---

<Map config={config} />
```

### Advanced: Extending Schemas

Add custom metadata to your map configurations:

```typescript
// src/content.config.ts
import { defineCollection } from 'astro:content';
import { glob } from 'astro/loaders';
import { z } from 'astro/zod';
import { extendSchema, getMapSchema } from '@maplibre-yaml/astro/utils';

export const collections = {
  maps: defineCollection({
    loader: glob({ pattern: '**/*.yaml', base: './src/collections/maps' }),
    schema: extendSchema(getMapSchema(), {
      author: z.string(),
      publishDate: z.date(),
      tags: z.array(z.string()),
      featured: z.boolean().default(false)
    })
  })
};
```

```yaml
# src/collections/maps/featured-map.yaml
author: "Jane Doe"
publishDate: 2024-01-15
tags: ["earthquakes", "geoscience"]
featured: true

type: map
id: featured-map
config:
  center: [0, 0]
  zoom: 2
  mapStyle: "https://tiles.openfreemap.org/styles/liberty"
```

```astro
---
import { getCollection } from 'astro:content';
import { Map } from '@maplibre-yaml/astro';

const featuredMaps = await getCollection('maps', ({ data }) => data.featured);
---

{featuredMaps.map(entry => {
  // Hand <Map> only the map document. The metadata fields would otherwise
  // reach <ml-map> as unknown keys and log a warning each.
  const { author, publishDate, tags, featured, ...mapConfig } = entry.data;
  return (
    <div>
      <h2>{mapConfig.id}</h2>
      <p>By {author} on {publishDate.toLocaleDateString()}</p>
      <Map config={mapConfig} />
    </div>
  );
})}
```

## Named Sources

Sources can be defined at the block level and referenced by name across multiple layers. This avoids duplicating source definitions and makes it easy to share data between layers (e.g., a fill and an outline from the same GeoJSON).

```yaml
type: map
id: neighborhood-map
config:
  center: [-73.985, 40.674]
  zoom: 14
  mapStyle: "https://basemaps.cartocdn.com/gl/positron-gl-style/style.json"

sources:
  boundary:
    type: geojson
    url: "https://example.com/data/boundary.geojson"
  parcels:
    type: vector
    url: "https://example.com/tiles.json"

layers:
  - id: boundary-fill
    type: fill
    source: boundary
    paint:
      fill-color: "#3388ff"
      fill-opacity: 0.2
  - id: boundary-outline
    type: line
    source: boundary
    paint:
      line-color: "#3388ff"
      line-width: 2
  - id: parcels-fill
    type: fill
    source: parcels
    source-layer: parcels
    paint:
      fill-color: "#ccc"
```

Named sources are added to the map before layers are processed, so any layer can reference them by string ID. Inline sources on individual layers still work as before — the two approaches can be mixed freely.

<Aside type="tip">
  Use named sources when multiple layers share the same data. Use inline sources for single-layer convenience.
</Aside>

### GeoJSON Sugar

For hand-authored data, a `type: geojson` source can carry a `location`,
`locations`, `region`, or `route` shorthand in place of a full `data:` object.
`loadMapConfig` parses with the core parser, which expands each sugar to
canonical GeoJSON before validation, so the `config` you hand to `<Map>` is
already normalized:

```astro
---
import { Map, loadMapConfig } from '@maplibre-yaml/astro';
const config = await loadMapConfig('./src/config/geojson-sugar.yaml');
---
<Map config={config} height="480px" />
```

```yaml
type: map
id: sugar-demo
config:
  center: [-73.98, 40.75]
  zoom: 12
  mapStyle: "https://basemaps.cartocdn.com/gl/positron-gl-style/style.json"
sources:
  site:
    type: geojson
    location:
      coordinates: [-73.98, 40.75]
      name: "Site"
  path:
    type: geojson
    route:
      coordinates: [[-74.00, 40.73], [-73.98, 40.75], [-73.96, 40.77]]
      name: "Walking route"
layers:
  - id: path-line
    type: line
    source: path
    paint:
      line-color: "#f59e0b"
      line-width: 4
  - id: site-dot
    type: circle
    source: site
    paint:
      circle-radius: 9
      circle-color: "#dc2626"
```

Stories take the same shorthands, on their layers' inline sources and in their
`sources:` block (`loadScrollytellingConfig` and `<Scrollytelling src>` both
expand them).

See [GeoJSON Sugar](/schema/sources/#geojson-sugar) for the full reference and
all four shorthands. A runnable version lives in the minimal example at
`examples/astro/minimal/src/pages/geojson-sugar.astro`.

### Format v2 and interactions

The same `loadMapConfig` / `<Map>` flow shown above works unchanged with
**Format v2** documents (the additive `style:` / `runtime:` split): a v2
document parses to the same internal model as its v1 twin, so the `config` you
hand to `<Map>` is identical either way.

- [Format v2](/guides/format-v2/) — the style/runtime split, key-by-key, with
  the v1 → v2 relocation table.
- [Export to style.json](/guides/interactions/) — declarative interactions, the
  export guarantee, and how `attachInteractions` reattaches behavior (including
  the trust-gated `emit` interaction).

### Map-level features pass straight through

`Map` and `FullPageMap` hand the whole document to `<ml-map>`, through the
`config` attribute or the `src` URL. Map-level features therefore work with no
Astro-specific setup: `markers:`, `images:`, `parameters:` (the params panel),
`legend:`, hover popups, and the 0.9 additions: a layer's
[`classify:`](/guides/thematic-maps/) block with its automatic legend, the
document's `title:` and `description:` for screen readers, and `locale:`
translations ([Accessibility & languages](/guides/accessibility-languages/)).
PMTiles, FlatGeobuf, GeoParquet and COG files in `public/` load as well:
`astro dev`, `astro preview` and GitHub Pages all answer the HTTP range
requests they need ([Large data](/guides/cloud-native-data/)). A `Scrollytelling` story's map is an `<ml-map>`
too, and since `@maplibre-yaml/core` 0.8 a story takes the same map-level keys:
`sources:`, `markers:`, `legend:`, `state:` and `parameters:`, `images:`,
`controls:`, `terrain:`, `projection:` (on 0.7 and earlier a story's map was
`config:` + `layers:` only).

## Editing in astro dev

What you see after saving a file under `astro dev` depends on how the page
loads it:

| You edit | What happens |
|----------|--------------|
| A content-collection YAML or Markdown file | The page updates by itself. |
| A YAML file in `public/` (`<Map src>`) | Reload the page to see it. |
| A file read by `loadMapConfig` / `loadScrollytellingConfig` in page frontmatter, or a `feature_ref` GeoJSON | Reload the page to see it. |
| The `loadGlobalMapConfig` file (`src/config/maps.yaml`) read by a module's top-level `await` | **Restart `astro dev`** (the module ran once and kept the old file). |

Add the optional integration and every row becomes "the page reloads by
itself": it watches the files the loaders read and the YAML, GeoJSON and JSON
under `public/`, and re-runs the modules that read them.

```js
// astro.config.mjs
import { defineConfig } from "astro/config";
import maplibreYaml from "@maplibre-yaml/astro/integration";

export default defineConfig({
  integrations: [maplibreYaml()],
});
```

It also pre-bundles maplibre-gl and `@maplibre-yaml/core` when the dev server
starts. Without that, the first page with a map makes Vite discover them
late: the terminal says *new dependencies optimized ... reloading*, the
browser console shows *504 (Outdated Optimize Dep)*, and the page reloads
once. It only acts under `astro dev`. Builds are the same with or without it.
(Needs `@maplibre-yaml/astro` 0.6 or later.)

## Deploying to GitHub Pages (or any subpath)

A static Astro build works on any static host. One case needs care: a site
served from a **subpath**. A GitHub Pages *project* site lives at
`https://<user>.github.io/<repo>/`, so Astro's
[GitHub Pages guide](https://docs.astro.build/en/guides/deploy/github/) has you
set `base`:

```js
// astro.config.mjs
import { defineConfig } from "astro/config";

export default defineConfig({
  site: "https://<user>.github.io",
  base: "/<repo>",
});
```

(A *user* site, the repo named `<user>.github.io`, is served from the root and
needs no `base`.) Then, everything under `public/` is served under the base:
`public/configs/hero-map.yaml` is at `/<repo>/configs/hero-map.yaml`.

- **`Map`, `FullPageMap`, `Scrollytelling` and `Chapter`: nothing to change.** Keep writing
  `src="/configs/hero-map.yaml"`, and keep the paths *inside* your YAML as
  they are. The components hand the site's base to `<ml-map>` (its
  [`base` attribute](/integrations/web-components/#sites-under-a-subpath-github-pages)),
  which puts every path to your own files under it: data `url:`s, `tiles:`,
  `images:`, marker `icon:`s, a site-hosted `mapStyle`, popup links, and (from
  core 0.9) the file inside a `pmtiles://` or `cog://` URL and a Protomaps
  basemap's `pmtiles:`, `glyphs:` and `sprite:`.

  ```yaml no-validate
  sources:
    volcanoes:
      type: geojson
      url: "/data/volcanoes.geojson"   # public/data/volcanoes.geojson
  images:
    pin: "images/pin.png"              # public/images/pin.png
  ```

  Both spellings load from `public/` on every page of your site, including
  nested ones like `/<repo>/blog/my-post/`. A path that already includes the
  base (`/<repo>/data/volcanoes.geojson`, the workaround older versions
  needed) is used as written, and full `https://` URLs are never changed.
  (Needs `@maplibre-yaml/astro` 0.6 and `@maplibre-yaml/core` 0.8 or later.)
- **Your own `<ml-map>` components** (the [Component Patterns](#component-patterns)
  below) add one attribute, `base={import.meta.env.BASE_URL}`. It applies to
  the element's `src` too, so pass `src` unchanged:

  ```astro
  <ml-map
    src={src}
    base={import.meta.env.BASE_URL}
    style="height: 400px; display: block;"
  ></ml-map>
  ```

- **Stories too.** `<Scrollytelling src="/stories/tour.yaml">` and
  `<Scrollytelling config>` pass the base to `<ml-scrollytelling>`, so the
  story's `src`, every path in its map document, and chapter `image:` /
  `video:` (`/images/photo.jpg` for `public/images/photo.jpg`) load under it.
  A standalone `Chapter`'s media does the same. `base={false}` opts out on
  any of them. (Needs `@maplibre-yaml/astro` 0.6 and `@maplibre-yaml/core`
  0.8.)
- **Links and images in your own pages** need the base too, as in any Astro
  site (see Astro's
  [`base` docs](https://docs.astro.build/en/reference/configuration-reference/#base)).
- **Build-time paths do not change.** `loadMapConfig('./src/...')`,
  `loadGlobalMapConfig` and `feature_ref.source` are files on disk, read at
  build time.

Check it before you push: `npm run build && npm run preview` serves the
site under the base, so open `http://localhost:4321/<repo>/`. Every map should
show its data. A data file that doesn't load is listed in a notice on the map.

<Aside type="note" title="&quot;Some chunks are larger than 500 kB&quot; is expected">
  Every build of a site with a map prints a yellow warning. On Astro 7.4 it
  reads:

  ```text
  [WARN] [vite] [plugin builtin:vite-reporter]
  (!) Some chunks are larger than 500 kB after minification.
  ```

  (older Astro versions print it on one line). That chunk is the map engine
  (maplibre-gl plus maplibre-yaml, about 1.5 MB before compression, loaded
  only by pages with a map); it is a size notice, not an error, and the
  build succeeded. To quiet it, raise Vite's limit in `astro.config.mjs`:
  `vite: { build: { chunkSizeWarningLimit: 2000 } }`.
</Aside>

**Relative paths mean "from `public/`", with or without a base.** The
components pass the base even when it is the default `/`, so
`url: "data/volcanoes.geojson"` loads `public/data/volcanoes.geojson` on every
page. (Before 0.6, a relative path resolved against the page, so on
`/blog/my-post/` it asked for `/blog/my-post/data/volcanoes.geojson`.) To get
the old page-relative behaviour back for one map, pass `base={false}`.

## Server output (SSR)

`output: 'server'` renders pages on request, on the deployed server. The
components work there, and so do `src`, content collections, the builders and
`import.meta.glob` (`loadFromGlob`). `loadMapConfig`,
`loadScrollytellingConfig`, `loadGlobalMapConfig` and `feature_ref` do not:
they read files from your project folder when the page *renders*, and a
deployed server has the built site but not your `src/` folder. Such pages fail
with a 500 and *ENOENT* in the server log.

Prerender the pages that use them, so they run once at build time:

```astro
---
export const prerender = true;

import { Map, loadMapConfig } from '@maplibre-yaml/astro';
const config = await loadMapConfig('./src/configs/map.yaml');
---
<Map config={config} />
```

Or bundle the YAML into the server with an import, which works on request:

```astro
---
import { Map } from '@maplibre-yaml/astro';
import { YAMLParser } from '@maplibre-yaml/core';
import mapYaml from '../configs/map.yaml?raw';

// Throws on an invalid document, like loadMapConfig.
const config = YAMLParser.parseMapBlock(mapYaml);
---
<Map config={config} />
```

The default static output (`astro build` with no `output` setting) is not
affected.

## View transitions

The components work with Astro's client-side router (`<ClientRouter />` in
your layout's `<head>`; `<ViewTransitions />` on Astro 4): each soft
navigation builds the new page's maps and removes the old ones, `FullPageMap`'s
zoom and reset buttons work on every visit, and MapLibre's stylesheet stays
loaded (`@maplibre-yaml/astro` 0.6 or later). The example site's
`/transitions` pages are tested this way on every Astro major.

<Aside type="note" title="Astro 6: a reload on the first page with the router">
  Astro 6's dev server finds the router's own scripts only when the first page
  using `<ClientRouter />` loads. Vite then re-bundles them and reloads that
  page once (*504 (Outdated Optimize Dep)* in the console). It is harmless,
  dev-only, and fixed in Astro 7. To avoid it, pre-bundle them in
  `astro.config.mjs`:

  ```js
  vite: {
    optimizeDeps: {
      include: [
        "astro/virtual-modules/transitions-router.js",
        "astro/virtual-modules/transitions-types.js",
        "astro/virtual-modules/transitions-events.js",
        "astro/virtual-modules/transitions-swap-functions.js",
      ],
    },
  },
  ```
</Aside>

If you write your own component script (like
[the interactive map below](#advanced-interactive-map-component)), keep in mind
that Astro runs a component's `<script>` **once per full page load**, not on
each soft navigation, and import MapLibre's stylesheet in the frontmatter
([why](#using-ml-map-directly)). Do the per-page work in an `astro:page-load`
listener, which fires after the first load and after every navigation:

```astro
<script>
  document.addEventListener('astro:page-load', () => {
    for (const mapEl of document.querySelectorAll('ml-map')) {
      // wire this page's maps here
    }
  });
</script>
```

moves it to a newer minor release on its own, and features documented here
for a later release are missing until you upgrade. Upgrade core and the Astro
package together:

</TabItem>

## Upgrading to 0.6

Three behavior changes matter when you move an Astro project to 0.6:

- **Astro `!html` loader fix (trust-gated).** `loadYAML` / `loadFromGlob` now
  parse with core's canonical options, so an `!html` tag resolves to the same
  `{ $html }` marker core produces (previously the Astro loader silently dropped
  `!html` to a bare string). Rendering is still gated by the popup capability
  policy: `!html` renders as **raw markup only under a trusted policy**, and is
  escaped otherwise. It is trust-gated, not "renders HTML unconditionally."
- **Malformed inline GeoJSON now warns.** A v1 document with malformed inline
  GeoJSON `data` emits a warning (promoted to an error under `mlym validate
  --strict` / CI). Pre-check inline geometry.
- **v2 `style.metadata` flows through.** In Format v2, `style.metadata` is
  carried to the emitted `style.json` root `metadata` slot.

## FullPageMap Component

The `FullPageMap` component creates a full-viewport map with built-in controls and an optional legend. It's perfect for landing pages, dashboards, or dedicated map views.

### Features

- **Full Viewport**: Fixed positioning that fills the entire viewport (100vw × 100vh)
- **Built-in Controls**: Zoom in/out and reset view buttons, placed in the map's top-right corner through `<ml-map>`'s [slots](/integrations/web-components/#slots-your-own-chrome-over-the-map)
- **Optional Legend**: the core legend, with configurable positioning
- **Same Loading Options**: Supports both `src` (runtime) and `config` (build-time) loading
- **Responsive Design**: Optimized layouts for mobile and desktop

### Basic Usage

The map document. For runtime loading (`src`), save it as
`public/configs/world-map.yaml`; for build-time loading, as
`src/configs/world-map.yaml`:

```yaml title="public/configs/world-map.yaml"
type: map
id: world-map
config:
  center: [10, 25]
  zoom: 1.5
  mapStyle: "https://tiles.openfreemap.org/styles/liberty"
layers:
  - id: capitals
    type: circle
    source:
      type: geojson
      data:
        type: FeatureCollection
        features:
          - type: Feature
            geometry: { type: Point, coordinates: [-77.04, 38.91] }
            properties: { name: Washington }
          - type: Feature
            geometry: { type: Point, coordinates: [2.35, 48.86] }
            properties: { name: Paris }
          - type: Feature
            geometry: { type: Point, coordinates: [139.69, 35.69] }
            properties: { name: Tokyo }
          - type: Feature
            geometry: { type: Point, coordinates: [-43.17, -22.91] }
            properties: { name: Rio de Janeiro }
    paint:
      circle-radius: 8
      circle-color: "#e63946"
      circle-stroke-width: 2
      circle-stroke-color: "#ffffff"
```

A whole page, e.g. `src/pages/map.astro`:

<Tabs>
  <TabItem label="Runtime Loading">
```astro
---
import { FullPageMap } from '@maplibre-yaml/astro';
---
<html lang="en">
```

  </TabItem>

<Aside type="caution" title="Keep the viewport meta">
  Without `<meta name="viewport" content="width=device-width, initial-scale=1">`
  in the page's `<head>`, phones lay the page out about 980px wide and shrink
  it: the map, its buttons and legend come out tiny. The shorter snippets
  below show only the component; put them on a page (or in a
  [layout](https://docs.astro.build/en/basics/layouts/)) like this one. In
  `astro dev`, the components warn in the browser console when the meta is
  missing.
</Aside>

### Component API

```typescript
interface FullPageMapProps {
  // Map source (one required)
  src?: string;                    // Path to YAML file in /public
  config?: MapBlock;               // Pre-loaded configuration object

  // Control options
  showControls?: boolean;          // Show zoom/reset controls (default: true)
  showLegend?: boolean;            // Add a default legend: when the document has none (default: false)
  legendPosition?: 'top-left' | 'top-right' | 'bottom-left' | 'bottom-right';
                                   // Legend position (default: 'top-right')

  // Styling (optional - component is fixed viewport by default)
  class?: string;                  // Additional CSS classes
  style?: string;                  // Additional inline styles

  // Where the paths in the document start (default: import.meta.env.BASE_URL)
  base?: string | false;

  // Hide on-page notices for non-fatal problems (default: false; see Map)
  quiet?: boolean;

  // Show author hints wherever the page is served (default: false; see Map)
  debug?: boolean;
}
```

### Legend

`showLegend` uses the core legend — the same one a document's own `legend:`
block produces. When the document has no `legend:`, the component adds a
default one at `legendPosition` (v1: root `legend:`, v2: `runtime.legend`);
when the document declares its own `legend:`, that one wins untouched.

Legend entries come from the layers' `legend:` fields (see
[the layers reference](/schema/layers/)), the legend block's own `items:`,
and the classes of a [classified](/guides/thematic-maps/) layer (listed after
`items:`). Nothing is generated from paint colors: a layer without `legend:`
or `classify:` doesn't appear, and when no layer has one, no legend box is shown (the component
warns at build time, and `<ml-map>` warns in the console).

```yaml no-validate
layers:
  - id: parks
    type: fill
    legend: { label: Parks, color: "#2e7d32", shape: square }
```

Since core 0.9, a layer's own `legend:` entry (or a `classify:` block) shows
a legend even without a `legend:` block or `showLegend`, in the default place
(top-left). `showLegend` moves that legend to `legendPosition`; a `legend:`
block in the document places it instead, and `legend: false` at the top level
turns it off.

`showLegend` needs the document at build time, so it applies to `config`.
With `src`, the document is fetched in the browser — declare `legend:` in the
YAML instead (the component warns at build time if you pass both `src` and
`showLegend`).

### Controls

The built-in controls provide:

- **Zoom In** (+): Increases zoom level by 1
- **Zoom Out** (−): Decreases zoom level by 1
- **Reset View** (↻): Returns to the view the map opened with, including a `fitTo` framing of the data (re-captured on every load)

Controls are accessible with ARIA labels and keyboard navigation. They share
the top-right corner with anything else placed there (a top-right legend, the
params panel, a navigation control) and stack below it instead of
overlapping.

When the document has its own zoom buttons (`controls: { navigation: true }`),
`FullPageMap` shows only its reset button, so one YAML file can serve both
`<Map>` and `<FullPageMap>` without two stacks of +/− in the corner.
`showControls={false}` removes the reset button too.

<Aside type="note" title="Before 0.7">
Earlier versions drew their own buttons and legend over the map, wired to a
`.map` property `<ml-map>` never had — so neither ever worked. If you styled
around those elements, note the legend now carries core's `.ml-map-legend`
markup and the buttons live inside `<ml-map>`.
</Aside>

## Chapter Component

The `Chapter` component displays one narrative section of a scrollytelling story, for pages that lay out chapters themselves. `Scrollytelling` renders its chapters with the same core renderer (`chapterHTML` from `@maplibre-yaml/core/scrollytelling`) and stylesheet, so a `Chapter` looks exactly like a story's own.

### Features

- **Flexible Content**: Title, HTML description, images, and videos
- **Multiple Alignments**: left, right, center, or full-width layouts
- **Theme Support**: Light and dark themes with CSS custom properties
- **Hidden Mode**: Map-only chapters without visible content
- **Active States**: Visual feedback based on scroll position
- **Accessibility**: ARIA labels, semantic HTML, keyboard navigation
- **Responsive Design**: Mobile-optimized with multiple breakpoints
- **Reduced Motion**: Respects user's motion preferences

## Scrollytelling Component

The `Scrollytelling` component creates immersive narrative experiences where the map transitions between different views as users scroll through story chapters. Perfect for data journalism, interactive reports, and guided data tours.

`<Scrollytelling>` renders core's [`<ml-scrollytelling>`](/integrations/scrollytelling-html/)
web component, the same element a plain HTML page uses from a CDN. Astro adds
build-time loading: with `config`, the chapters, the rail and the map's
document are rendered into the page at build time and the element takes them
over in the browser; with `src`, the element fetches and renders the story
itself. Either way one engine drives the camera, layers, actions and rail, so
a story file behaves the same in an Astro site and in a plain page.

<Aside type="note" title="Version pairing">
  `@maplibre-yaml/astro` 0.7 needs `@maplibre-yaml/core` 0.9 or later (0.6
  needed core 0.8, the release that added `<ml-scrollytelling>`). Upgrade both
  together: `npm install @maplibre-yaml/astro@latest @maplibre-yaml/core@latest`.
</Aside>

### Features

- **Scroll-Driven Navigation**: Map automatically transitions as you scroll through chapters
- **Smooth Camera Transitions**: Choose from flyTo, easeTo, or jumpTo animations
- **Layer Control**: Show/hide map layers per chapter for progressive disclosure
- **Chapter Actions**: Execute custom MapLibre actions on chapter enter/exit
- **Optional Markers**: A clickable chapter rail, also driven by the keyboard
- **The whole map document**: `sources:`, `markers:`, `legend:`, the params panel and the rest work in a story
- **Build-time Loading**: Load and validate the story with `loadScrollytellingConfig`
- **One error card**: a story that fails in the browser lists each problem with its line number and any did-you-mean
- **Debug Mode**: Visual indicators to help during development
- **Accessible**: keyboard navigation, reduced motion, and the wheel scrolls the story rather than the map

### Component API

```typescript
interface ScrollytellingProps {
  src?: string;              // Path to YAML config file (in public directory)
  config?: ScrollytellingBlock;  // Pre-loaded scrollytelling configuration
  class?: string;            // Additional CSS class for container
  debug?: boolean;           // Debug mode - chapter outlines, author hints on any host
  // Where the story's paths start (default: import.meta.env.BASE_URL).
  // false = resolve relative paths against the page.
  base?: string | false;
  // Hide on-page notices for non-fatal problems on the story's map,
  // as on Map (default: false). Load/validation errors still show.
  quiet?: boolean;
}
```

### Basic Usage

Load the story at build time and pass it as `config`. Save the story from
[YAML Configuration](#yaml-configuration) below as
`src/stories/earthquakes.yaml` (it needs no other files), then make a whole
page, e.g. `src/pages/story.astro`:

```astro
---
import { Scrollytelling, loadScrollytellingConfig } from '@maplibre-yaml/astro';
const story = await loadScrollytellingConfig('./src/stories/earthquakes.yaml');
---
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>Los Angeles earthquakes</title>
  </head>
  <body style="margin: 0;">
    <Scrollytelling config={story} />
  </body>
</html>
```

The viewport meta makes phones lay the story out at their own width (without
it, the map and chapter text come out tiny), and `margin: 0` lets the map
reach the edges. The other snippets in this section show only the component:
put them on a page like this one, or in a
[layout](https://docs.astro.build/en/basics/layouts/).

Or load it in the browser from `public/`. The component fetches, validates
and renders the story there, and a validation failure shows the errors in
place of the chapters:

```astro title="examples/astro/site/src/pages/story-runtime.astro"

```

</Aside>

### Chapter Configuration

Each chapter supports extensive configuration options:

**Position & Camera:**
- `id`: Unique chapter identifier (required)
- `center`: [longitude, latitude] coordinates (required)
- `zoom`: Zoom level (required)
- `pitch`: Camera tilt (0-85 degrees, default 0)
- `bearing`: Camera rotation (-180 to 180 degrees, default 0)

**Animation:**
- `animation`: "flyTo" (smooth arc), "easeTo" (direct), or "jumpTo" (instant); default "flyTo"
- `speed`: Animation speed (0-2, default 0.6)
- `curve`: Fly curve intensity (0-2, default 1)
- `rotateAnimation`: Keep rotating the camera while the chapter is active
- `spinGlobe`: Keep panning westward while the chapter is active

**Content:**
- `title`: Chapter heading (required)
- `description`: HTML content (rendered as-is, not escaped). Markdown is
  not converted: `**bold**` and `[link](url)` show literally, so write
  `<strong>bold</strong>` and `<a href="url">link</a>`
- `image`: Image shown above the text: a full `https://` URL, or a path to a
  file in `public/` (`/images/fuji.jpg` for `public/images/fuji.jpg`)
- `video`: Video with an inline player, given the same way as `image`
- `alignment`: "left", "right", "center", or "full"
- `hidden`: Hide content for map-only transitions

**Interactivity:**
- `layers.show`: Array of layer IDs to make visible
- `layers.hide`: Array of layer IDs to hide
- `onChapterEnter`: Actions to execute when entering chapter
- `onChapterExit`: Actions to execute when leaving chapter
- `callback`: A name passed in the `ml-scrollytelling:chapter` event, for your page script to dispatch on

### Chapter Actions

Execute MapLibre actions when users enter or exit chapters:

```yaml
chapters:
  - id: filtered-view
    title: "Major Earthquakes Only"
    center: [-118.2, 34.0]
    zoom: 10
    onChapterEnter:
      - action: setFilter
        layer: earthquake-circles
        filter: [">=", ["get", "magnitude"], 5.0]
      - action: setPaintProperty
        layer: earthquake-circles
        property: circle-color
        value: "#ff0000"
    onChapterExit:
      - action: setFilter
        layer: earthquake-circles
        filter: null
```

**Available Actions:**

| Action | Fields | Effect |
|--------|--------|--------|
| `setFilter` | `layer`, `filter` (`null` clears) | Filter features in a layer |
| `setPaintProperty` | `layer`, `property`, `value` | Change a paint property |
| `setLayoutProperty` | `layer`, `property`, `value` | Change a layout property |
| `flyTo` / `easeTo` | `options` (`center`, `zoom`, `bearing`, `pitch`, `duration`, …) | Move the camera, overriding the chapter's own camera |
| `fitBounds` | `bounds: [west, south, east, north]` or `[[west, south], [east, north]]`, `options` (`padding`, `duration`, …) | Frame an area |
| `custom` | anything in `options` | Runs nothing itself. Dispatches `ml-scrollytelling:action` for your page |

A layer action naming a layer the map does not have logs a warning and is
skipped. Enter actions run after the chapter's camera move and layer toggles.

**Events.** The story element (`<ml-scrollytelling>`, which keeps the
`scrollytelling-container` class) dispatches bubbling events. On every
chapter change it dispatches `ml-scrollytelling:chapter`, with
`detail: { chapterId, previousChapterId, index, callback, map }`. `callback`
is the chapter's `callback:` name. On each `custom` action it dispatches
`ml-scrollytelling:action`, with `detail: { action, chapterId, phase, map }`.
A story that cannot load or validate dispatches `ml-scrollytelling:error`,
with `detail: { errors, warnings, source }`. The element also carries
`data-active-chapter`. The example's Tonga chapter
uses a `custom` action to show a banner:

```ts title="examples/astro/site/src/pages/story.astro"
const banner = document.getElementById("story-banner")!;
document.addEventListener("ml-scrollytelling:action", (event) => {
  const { action } = (event as CustomEvent).detail;
  banner.textContent = String(action.options?.banner ?? "");
```

`rotateAnimation: true` slowly rotates the camera while a chapter is active,
and `spinGlobe: true` pans it westward. Both stop on the next chapter and are
skipped when the reader prefers reduced motion.

### Chapter Markers

When `showMarkers: true`, navigation dots appear at the right edge of the map:

- Click a dot to jump to its chapter (the chapters in between are skipped)
- Tab to the rail, then use the arrow keys, Home and End; Enter or Space activates a dot
- The active dot is highlighted (and marked `aria-current` for screen readers)
- Customizable color via `markerColor`
- On phones the cards leave a gutter for the rail, so it never sits on a card

### Themes

**Light theme** (default):
- Light chapter cards on map background
- Suitable for bright map styles
- Light footer background

**Dark theme**:
- Dark semi-transparent chapter cards
- Works well with satellite/dark base maps
- Dark footer background

### Debug Mode

Enable `debug` prop to see:
- Red dashed outlines around inactive chapters
- Green outlines around the active chapter
- Helpful for fine-tuning scroll trigger points
- The story's author hints (a chapter naming a layer that doesn't exist, a
  key nested under `config:`) on the map's notice even on a deployed site;
  without `debug` they show only in `astro dev` and on `localhost`

```astro
<Scrollytelling config={story} debug />
```

### Scroll Behavior

- The active chapter is the one whose card is on screen and nearest the
  middle of it, recomputed as the page scrolls, so scrolling back and forth
  always lands on the chapter you are reading. On phones the map moves on
  once the next card is on screen, not before.
- The story starts reacting once its first chapter reaches the middle 20%
  of the screen (the trigger zone)
- Smooth map transitions between chapters
- Progressive chapter content fade in/out

The chapters scroll over a sticky full-viewport map. The story map's own pan
and zoom gestures are off (set `scrollZoom: true` or `dragPan: true` in
`config:` to turn one back on), so the mouse wheel and touch scroll the story
rather than moving the map, while the rail, legend, markers, popups and slots
on the map stay clickable. The camera is offset so a chapter's `center` is not
under its card: beside a left or right card, above a centred or full-width
card, and above the card on a phone (on a phone on its side every card is a
narrow one on the left, with the subject beside it). Nothing on the map moves
with the scroll: the legend is pinned in one corner above the cards (a
"Legend" button on phones that opens above them; see
[The legend](/schema/scrollytelling/#the-legend)), the other chrome stays in its
corner under the cards, and a chapter photo is never taller than 40% of the
screen. A `slot="legend"` child fills the pinned legend's panel.
The map opens on the story's `config` camera. As soon as it has loaded, the
chapter sitting in the trigger zone is applied at once, without any scrolling.
On a page that starts with the story that is the first chapter: its camera,
`layers` and `onChapterEnter` actions all run on load. Give layers their starting state in `config` and the
layers themselves (for example `layout: { visibility: none }` on a layer a
later chapter reveals), and let the first chapter's actions apply its own
look.

### Accessibility

- Semantic HTML with proper ARIA labels
- Keyboard navigation for chapter markers (Tab, arrow keys, Home, End, Enter)
- Screen reader friendly chapter titles
- Reduced motion: when the reader's system asks for reduced motion
  (`prefers-reduced-motion`), chapter cards stop animating, every chapter
  camera move and camera action (`flyTo`, `easeTo`, `fitBounds`) is instant
  (an action whose `options` set `essential: true` still animates), and
  `rotateAnimation` / `spinGlobe` are skipped
- High contrast mode support

### Performance Tips

1. **Use build-time loading** for better initial page load
2. **Optimize images**: Compress chapter images and use appropriate sizes
3. **Limit chapters**: 5-10 chapters for optimal scrolling experience
4. **Simplify transitions**: Use `jumpTo` for instant transitions on slower devices
5. **Lazy load media**: Images and videos load only when needed

## Global Configuration

For sites with multiple maps, define site-wide defaults (basemap style, center, zoom) once and inherit them everywhere. This eliminates repetition and ensures consistency.

<Steps>

1. **Create a global config YAML file**

   ```yaml
   # src/config/maps.yaml
   title: "My Map Application"
   defaultMapStyle: "https://basemaps.cartocdn.com/gl/positron-gl-style/style.json"
   defaultCenter: [-73.985, 40.674]
   defaultZoom: 14
   theme: light
   ```

2. **Create a shared loader module**

   ```typescript
   // src/lib/map-config.ts
   import { loadGlobalMapConfig } from "@maplibre-yaml/astro";

   export const globalMapConfig = await loadGlobalMapConfig(
     "./src/config/maps.yaml"
   );
   ```

   Top-level `await` is supported in Astro modules during the build phase.
   In `astro dev` this module runs once, so edits to `maps.yaml` show up
   only after a restart, unless you add the
   [integration](#editing-in-astro-dev), which reloads it for you.

3. **Use in pages with map builders**

   ```astro
   ---
   import { Map, buildPointMapConfig } from "@maplibre-yaml/astro";
   import { globalMapConfig } from "../lib/map-config";

   const mapConfig = buildPointMapConfig(
     {
       location: {
         coordinates: [-73.983, 40.676],
         name: "Project Site",
       },
     },
     globalMapConfig, // mapStyle and zoom inherited as fallbacks
   );
   ---
   <Map config={mapConfig} height="400px" />
   ```

</Steps>

All map builders (`buildPointMapConfig`, `buildMultiPointMapConfig`, `buildPolygonMapConfig`, `buildMultiPolygonMapConfig`, `buildRouteMapConfig`, `buildMultiLineStringMapConfig`) accept `globalConfig` as their second argument. Values explicitly set in the builder options take priority; global defaults fill in anything omitted. The center always comes from the geometry, so `defaultCenter` matters only when you build a map without one (as the `fallback` below does).

### GlobalConfig Schema

| Field | Type | Description |
|-------|------|-------------|
| `title` | `string?` | Application title |
| `description` | `string?` | Application description |
| `defaultMapStyle` | `string (URL)` or `{ pmtiles, flavor?, lang? }`? | Default basemap for all maps: a style URL, or a [Protomaps basemap](/guides/cloud-native-data/#host-your-own-basemap) from a `.pmtiles` file in `public/` |
| `defaultCenter` | `[lng, lat]?` | Default map center |
| `defaultZoom` | `number (0-24)?` | Default zoom level |
| `theme` | `"light" \| "dark"` | Default theme (default: `"light"`) |

### Dynamic map per collection item

Use `buildMapConfigFromEntry` in your dynamic route page (`[slug].astro`). The helper inspects the entry data, dispatches to the appropriate builder by geometry type, and falls back to a supplied default if no geometry is set.

```astro
---
// src/pages/projects/[slug].astro
import { getCollection } from "astro:content";
import { Map, buildMapConfigFromEntry } from "@maplibre-yaml/astro";
import { globalMapConfig } from "../../lib/map-config";

export async function getStaticPaths() {
  const entries = await getCollection("projects");
  return entries.map((entry) => ({ params: { slug: entry.id }, props: { entry } }));
}

const { entry } = Astro.props;
const mapConfig = await buildMapConfigFromEntry(entry.data, globalMapConfig, {
  label: entry.data.title,
  description: entry.data.summary,
  fallback: {
    coordinates: globalMapConfig.defaultCenter!,
    name: entry.data.title,
  },
});
---
<Map config={mapConfig} height="300px" />
```

The helper recognizes these fields in this precedence order:

1. `feature_ref` — external GeoJSON file reference
2. `region` — inline polygon
3. `route` — inline line
4. `locations` — inline multi-point
5. `location` — inline single point
6. `options.fallback` — supplied default

The first set field wins; later fields are ignored. The helper is always async because `feature_ref` requires file I/O at build time.

<Aside type="note" title="Field names are library conventions">
  These field names (`location`, `region`, `route`, `feature_ref`) are not GeoJSON canonicals — they're conventions established by the library's `getCollectionItemWith*Schema` helpers. If your collection uses different field names, call the underlying builders (`buildPointMapConfig`, `buildPolygonMapConfig`, etc.) directly instead of the helper.
</Aside>

#### Manual dispatch (when you need custom per-type logic)

If you need to handle each geometry type explicitly (e.g., custom popup or styling per type), call the builders directly:

```astro
---
import {
  Map,
  buildPointMapConfig,
  buildPolygonMapConfig,
  buildRouteMapConfig,
} from "@maplibre-yaml/astro";
import type { MapBlock } from "@maplibre-yaml/core";
import { globalMapConfig } from "../../lib/map-config";

// ...same getStaticPaths as above...

const { entry } = Astro.props;
const data = entry.data;

let mapConfig: MapBlock;

if (data.region) {
  mapConfig = buildPolygonMapConfig({ region: data.region }, globalMapConfig);
} else if (data.route) {
  mapConfig = buildRouteMapConfig({ route: data.route }, globalMapConfig);
} else if (data.location) {
  mapConfig = buildPointMapConfig({ location: data.location }, globalMapConfig);
} else {
  mapConfig = buildPointMapConfig(
    { location: { coordinates: globalMapConfig.defaultCenter! } },
    globalMapConfig,
  );
}
---
<Map config={mapConfig} height="300px" />
```

## GeoJSON Feature References

When multiple collection items share geometry from a single source-of-truth GeoJSON file, copying coordinates into each frontmatter is fragile and verbose. The `feature_ref` field lets a collection item point at a feature in an external GeoJSON file (matched by `featureId` or by property equality). At build time, the loader reads the file, finds the matching feature, detects its geometry type, and dispatches to the existing point/polygon/route builders.

<Aside type="tip" title="Runnable example">
  A complete minimal Astro app exercising every scenario covered in this section lives at [`examples/astro/minimal`](https://github.com/design-practices/maplibre-yaml/tree/main/examples/astro/minimal). The `/showcase` page pairs each `FeatureRef` snippet with the map it produces; `/poas/sample` demonstrates `buildMapConfigFromEntry` with a markdown entry.
</Aside>

### Quick start

<Steps>

1. **Add `feature_ref` to your collection schema**

   ```typescript
   // src/content.config.ts
   import { defineCollection } from "astro:content";
   import { z } from "astro/zod";
   import { glob } from "astro/loaders";
   import {
     FeatureRefSchema,
     LocationPointSchema,
     RegionPolygonSchema,
     RouteLineSchema,
   } from "@maplibre-yaml/astro/utils";

   export const collections = {
     poas: defineCollection({
       loader: glob({ pattern: "**/*.md", base: "./src/collections/poas" }),
       schema: z.object({
         title: z.string(),
         gotf_id: z.number(),
         // Either feature_ref OR inline geometry -- not both
         feature_ref: FeatureRefSchema.optional(),
         location: LocationPointSchema.optional(),
         region: RegionPolygonSchema.optional(),
         route: RouteLineSchema.optional(),
       }),
     }),
   };
   ```

   <Aside type="tip">
     Always use `@maplibre-yaml/astro/utils` (not `@maplibre-yaml/astro`) inside `src/content.config.ts`. The main package entry re-exports Astro components which can't be loaded outside the component pipeline.
   </Aside>

   For automatic mutual-exclusivity validation, use `getCollectionItemWithFeatureRefSchema()` instead. It rejects items declaring both `feature_ref` and inline geometry at content-collection-parse time.

2. **Reference features from frontmatter**

   <Tabs>
   <TabItem label="Match by feature.id">

   ```yaml
   ---
   title: "Gowanus Rezoning Area"
   gotf_id: 1.1
   feature_ref:
     source: "./src/data/gowanus.geojson"
     featureId: "poa-1.1"
   ---
   ```

   </TabItem>
   <TabItem label="Match by property">

   ```yaml
   ---
   title: "Gowanus Rezoning Area"
   gotf_id: 1.1
   feature_ref:
     source: "./src/data/gowanus.geojson"
     match:
       property: "gotf_id"
       equals: 1.1
     fillColor: "#3388ff"
     fillOpacity: 0.25
   ---
   ```

   </TabItem>
   </Tabs>

3. **Build the map in your dynamic page**

   The simplest path is `buildMapConfigFromEntry` — it inspects the entry data, dispatches by geometry type (including `feature_ref`), and produces a `MapBlock`:

   ```astro
   ---
   // src/pages/poas/[slug].astro
   import { getCollection } from "astro:content";
   import { Map, buildMapConfigFromEntry } from "@maplibre-yaml/astro";
   import { globalMapConfig } from "../../lib/map-config";

   export async function getStaticPaths() {
     const entries = await getCollection("poas");
     return entries.map((entry) => ({ params: { slug: entry.id }, props: { entry } }));
   }

   const { entry } = Astro.props;
   const mapConfig = await buildMapConfigFromEntry(entry.data, globalMapConfig, {
     label: entry.data.title,

   ```

   If you need custom per-type behavior, call the underlying builders directly (`buildFeatureMapConfig`, `buildPolygonMapConfig`, etc.) instead. See "Manual dispatch" above.

</Steps>

### Match strategies

Two ways to identify which feature to use:

| Form | When to use |
|------|-------------|
| `featureId: <string \| number>` | When your GeoJSON features have stable top-level `id` fields (RFC 7946) |
| `match: { property, equals }` | When IDs live in `feature.properties` (common -- mirrors MapLibre's `promoteId`) |

Exactly one match must be returned. Zero matches or multiple matches throw `GeoJSONLoadError` with details (file path, total feature count, sample IDs/values).

### Override fields

Frontmatter can override `feature.properties.name` and `feature.properties.description`, plus all style fields (`markerColor`, `fillColor`, `strokeColor`, `fillOpacity`, `color`, `width`, `zoom`). Overrides take priority; `feature.properties` are the fallback.

### Supported geometry types

| Type | Builder dispatched |
|------|-------------------|
| `Point` | `buildPointMapConfig` |
| `MultiPoint` | `buildMultiPointMapConfig` |
| `LineString` | `buildRouteMapConfig` |
| `MultiLineString` | `buildMultiLineStringMapConfig` (renders all segments) |
| `Polygon` | `buildPolygonMapConfig` |
| `MultiPolygon` | `buildMultiPolygonMapConfig` (renders all polygons) |
| `GeometryCollection` (single member) | dispatches to the inner geometry type |
| `GeometryCollection` (multiple members) | throws `GeoJSONLoadError` -- split into separate features |

### Path resolution and security defaults

The `source` value is resolved against `process.cwd()` by default. Two settings on `FeatureLoadOptions` adjust this:

```typescript
import {
  buildFeatureMapConfig,
  type FeatureLoadOptions,
} from "@maplibre-yaml/astro";

const loadOptions: FeatureLoadOptions = {
  // Use a custom project root for monorepo builds where cwd != Astro project dir.
  // Canonicalized via realpath so macOS `/var` -> `/private/var` doesn't trip
  // the containment check.
  projectRoot: "/absolute/path/to/astro/project",

  // Opt in to absolute `source` paths. Default: false.
  // Required for tests using tmpdir, monorepo data outside the project root,
  // or any controlled call site. Do NOT enable when frontmatter values can
  // come from untrusted content (CMS-supplied entries, user uploads).
  allowAbsolutePaths: true,
};

await buildFeatureMapConfig({ ref, loadOptions }, globalConfig);
```

The same `loadOptions` flows through `buildMapConfigFromEntry` and `loadFeatureFile`.

<Aside type="caution" title="Path-traversal protection">
  Relative `source` values that escape the project root via `..` are rejected before any filesystem I/O. Symlinks that live inside the project root but canonicalize OUTSIDE it are also rejected (a post-realpath containment re-check catches this). Absolute paths are rejected unless `allowAbsolutePaths: true` is passed -- the secure-by-default posture protects against UGC frontmatter where an attacker could submit `source: "/etc/passwd"` as a filesystem oracle.
</Aside>

### Error classes

The builder throws one of two error classes:

```typescript
import {
  buildFeatureMapConfig,
  GeoJSONLoadError,
  InvalidFeatureRefError,
} from "@maplibre-yaml/astro";

try {
  await buildFeatureMapConfig({ ref }, globalConfig);
} catch (err) {
  if (err instanceof InvalidFeatureRefError) {
    // Thrown when the ref has neither or both of `featureId` and `match`.
    // Discriminable via instanceof (not wrapped by buildFeatureMapConfig).
  } else if (err instanceof GeoJSONLoadError) {
    // Thrown for everything else: missing file/feature, malformed JSON,
    // unsupported geometry, path-traversal violation, absolute-path
    // rejection, file too large, degenerate LineString, heterogeneous
    // GeometryCollection. `.message` carries the actionable message;
    // `.filePath` carries the resolved path; ES2022 `.cause` carries the
    // underlying fs/parse error when applicable.
  }
}
```

### Build-time only

`buildFeatureMapConfig` reads from the local filesystem via `process.cwd()` (or the configured `projectRoot`). It is **build-time only** -- invoking it in a deployed SSR adapter context throws a `GeoJSONLoadError` whose ENOENT message includes deployment-context hints. With `output: 'server'`, prerender the pages that use it (see [Server output](#server-output-ssr)).

### Performance

| File size | Behavior |
|-----------|---------|
| < 10MB | Fully supported, no caveats |
| 10-50MB | Supported; one-time parse cost |
| 50-100MB | Build-time warning |
| > 100MB | Hard error directing toward PMTiles or splitting |

For data this large, load it in the browser instead of at build time: a
PMTiles, FlatGeobuf or GeoParquet file in `public/` is read in parts as the
map needs it ([Large data](/guides/cloud-native-data/)).

Files referenced multiple times across collection items are parsed once via an mtime-aware cache. Editing the GeoJSON in `astro dev` invalidates the cache on next page render -- no server restart needed. For files with 200+ features, a per-property index is built lazily on the second access for that property.

<Aside type="note" title="Reloading after an edit">
  Editing a GeoJSON file in `astro dev` invalidates the cache (you'll see updated geometry on the next page load), but Vite doesn't know the page depends on the file, so reload it yourself, or add the [integration](#editing-in-astro-dev), which reloads the page when a referenced file changes.
</Aside>

### Ignored style overrides

`FeatureRef` accepts every style field (`markerColor`, `fillColor`, `strokeColor`, `fillOpacity`, `color`, `width`) because the geometry type is not known when the schema parses -- it's resolved when the file loads. When a field doesn't apply to the resolved geometry (e.g., `markerColor` on a Polygon ref), the builder ignores it and emits a one-time `console.warn` during `astro dev`:

```
feature_ref: style override(s) [markerColor, width] do not apply to Polygon geometry from "./src/data/sample.geojson"; they will be ignored.
```

Warnings are deduplicated per `(source, geometryType, ignored-keys)` so reloading the page won't re-emit them. Restarting `astro dev` clears the dedupe cache.

### Lower-level primitives

For advanced cases (e.g., loading one file once and dispatching to many features manually):

```typescript
import {
  loadFeatureFile,
  findFeature,
  GeoJSONLoadError,
  clearFeatureCache,
} from "@maplibre-yaml/astro";

const fc = await loadFeatureFile("./src/data/gowanus.geojson");
const feature = findFeature(fc, { source: "...", featureId: "poa-1.1" });
// Then dispatch manually with the existing sync builders
```

`clearFeatureCache()` is exported for test isolation between files that share absolute paths.

## Component Patterns

These patterns wrap `<ml-map>` yourself and need only `@maplibre-yaml/core`
and `maplibre-gl`. Each script carries the maplibre-gl 6 worker setup explained
in [Using `<ml-map>` directly](#using-ml-map-directly); on maplibre-gl 4 or 5,
delete its two worker lines.

<Aside type="caution" title="Astro 4: render pages through a layout with a head">
  Take a page with no `<head>`, such as one that is just `<Map ... />` with no
  layout. On Astro 4, if its component has a `<script>` but no `<style>`,
  Astro silently drops the script. The register import never runs and
  `<ml-map>` stays an unknown element. Astro 5 is not affected.
</Aside>

### Pattern 1: External YAML with src Attribute (Recommended)

The simplest pattern - let the web component handle everything. Place YAML files in the `/public` directory and reference them with the `src` attribute.

**File structure:**

```
public/
├── configs/
│   ├── hero-map.yaml
│   ├── contact-map.yaml
│   └── locations-map.yaml
src/
├── components/
│   └── Map.astro
└── pages/
    └── index.astro
```

**Map.astro:**

```astro
---
import 'maplibre-gl/dist/maplibre-gl.css'; // page CSS: here, not in the script tag
interface Props {
  src: string;
  height?: string;
}

const { src, height = '400px' } = Astro.props;
---

<ml-map src={src} base={import.meta.env.BASE_URL} style={`height: ${height}; display: block;`} />

<script>
  import { setWorkerUrl } from 'maplibre-gl';
  import workerUrl from 'maplibre-gl/dist/maplibre-gl-worker.mjs?worker&url';
  import '@maplibre-yaml/core/register';

  setWorkerUrl(workerUrl); // maplibre-gl 6: see "Using <ml-map> directly"
</script>
```

**Usage:**

```astro
<Map src="/configs/hero-map.yaml" />
<Map src="/configs/contact-map.yaml" height="300px" />
```

**Benefits:**

- ✅ Simplest possible implementation
- ✅ No build-time parsing needed
- ✅ YAML files are easy to edit
- ✅ Clear separation of configuration and presentation
- ✅ Works with any static file server
- ✅ No template literal whitespace issues

### Pattern 2: External YAML with Build-Time Parsing

For projects that want build-time validation, you can parse YAML during the build:

**File structure:**

```
src/
├── components/
│   └── Map.astro
├── configs/
│   ├── hero-map.yaml
│   ├── contact-map.yaml
│   └── locations-map.yaml
└── pages/
    └── index.astro
```

**Map.astro:**

```astro
---
import 'maplibre-gl/dist/maplibre-gl.css'; // page CSS: here, not in the script tag
import { YAMLParser } from '@maplibre-yaml/core';

interface Props {
  configPath: string;
  height?: string;
}

const { configPath, height = '400px' } = Astro.props;

// Import all YAML files at build time
const yamlFiles = import.meta.glob<string>('/src/configs/**/*.yaml', {
  query: '?raw',
  import: 'default',
  eager: true
});

const yamlContent = yamlFiles[configPath];

if (!yamlContent) {
  const available = Object.keys(yamlFiles).join(', ');
  throw new Error(`Config not found: ${configPath}. Available: ${available}`);
}

const result = YAMLParser.safeParseMapBlock(yamlContent);

if (!result.success) {
  console.error('YAML parse errors:', result.errors);
  throw new Error(`Invalid config ${configPath}: ${result.errors[0].message}`);
}

const configJson = JSON.stringify(result.data);
---

<ml-map style={`height: ${height}; display: block;`} config={configJson} />

<script>
  import { setWorkerUrl } from 'maplibre-gl';
  import workerUrl from 'maplibre-gl/dist/maplibre-gl-worker.mjs?worker&url';
  import '@maplibre-yaml/core/register';

  setWorkerUrl(workerUrl); // maplibre-gl 6: see "Using <ml-map> directly"
</script>
```

**Usage:**

```astro
<Map configPath="/src/configs/hero-map.yaml" />
<Map configPath="/src/configs/contact-map.yaml" height="300px" />
```

**Benefits:**

- ✅ Build-time parsing catches errors early
- ✅ YAML validation during development
- ✅ Configuration bundled with the build

**Tradeoffs:**

- ⚠️ More complex component code
- ⚠️ A deployed site needs a rebuild to pick up YAML changes (in `astro dev`,
  Vite tracks `?raw` imports and reloads the page when you save)

## Advanced: Interactive Map Component

A full-featured component with events and controls using the `src` pattern.
See [Web Components](/integrations/web-components/) for the full event and
method list. `mapReady()` is new in `@maplibre-yaml/core` 0.7. On 0.6, wait
for `ml-map:load` and call `getMap()`.

**InteractiveMap.astro:**

```astro
---
import 'maplibre-gl/dist/maplibre-gl.css'; // page CSS: here, not in the script tag
interface Props {
  src: string;
  height?: string;
  showControls?: boolean;
  onLayerClick?: string; // JavaScript function name to call
}

const {
  src,
  height = '400px',
  showControls = false,
  onLayerClick
} = Astro.props;

const mapId = `map-${Math.random().toString(36).slice(2, 9)}`;
---

<div class="interactive-map" id={mapId}>
  {showControls && (
    <div class="map-controls">
      <button class="control-btn" data-action="zoom-in" title="Zoom In">+</button>
      <button class="control-btn" data-action="zoom-out" title="Zoom Out">−</button>
      <button class="control-btn" data-action="reset" title="Reset View">⌂</button>
    </div>
  )}

  <ml-map
    src={src}
    base={import.meta.env.BASE_URL}
    style={`height: ${height}; display: block;`}
    data-click-handler={onLayerClick}
  />

  <div class="map-status"></div>
</div>

<script>
  import { setWorkerUrl } from 'maplibre-gl';
  import workerUrl from 'maplibre-gl/dist/maplibre-gl-worker.mjs?worker&url';
  import '@maplibre-yaml/core/register';
  import type { MLMap } from '@maplibre-yaml/core/components';

  setWorkerUrl(workerUrl); // maplibre-gl 6: see "Using <ml-map> directly"

  // Wire every interactive map on the page that is not wired yet. This
  // script runs once per full page load; with view transitions
  // (<ClientRouter />) later pages arrive without re-running it, so it also
  // runs on `astro:page-load` (which fires after the first load too -- the
  // `data-wired` guard keeps a map from being wired twice).
  function initInteractiveMaps() {
    document.querySelectorAll<HTMLElement>('.interactive-map:not([data-wired])').forEach(container => {
      container.dataset.wired = '';
      const mapEl = container.querySelector<MLMap>('ml-map');
      const statusEl = container.querySelector<HTMLElement>('.map-status');
      const controls = container.querySelector<HTMLElement>('.map-controls');

      if (!mapEl || !statusEl) return;

      let initialCenter: [number, number] | null = null;
      let initialZoom: number | null = null;

      // Status updates. A layer's first `layer-data-loaded` can fire before
      // `ml-map:load`, so `load` must not overwrite a feature count.
      mapEl.addEventListener('ml-map:load', () => {
        const map = mapEl.getMap();
        if (!map) return;
        initialCenter = map.getCenter().toArray() as [number, number];
        initialZoom = map.getZoom();
        if (!statusEl.textContent) statusEl.textContent = 'Map ready';
        statusEl.className = 'map-status ready';
      });

      mapEl.addEventListener('ml-map:layer-data-loading', (e) => {
        const { layerId } = (e as CustomEvent<{ layerId: string }>).detail;
        statusEl.textContent = `Loading ${layerId}...`;
        statusEl.className = 'map-status loading';
      });

      mapEl.addEventListener('ml-map:layer-data-loaded', (e) => {
        const { featureCount } = (e as CustomEvent<{ featureCount: number }>).detail;
        statusEl.textContent = `${featureCount} features loaded`;
        statusEl.className = 'map-status ready';
      });

      mapEl.addEventListener('ml-map:error', (e) => {
        // `{ error }` for a load/runtime failure, `{ errors }` for a document
        // that failed to parse or validate.
        const detail = (e as CustomEvent<{ error?: Error; errors?: { message: string }[] }>).detail;
        const message = detail.error?.message ?? detail.errors?.map((err) => err.message).join('; ');
        statusEl.textContent = `Error: ${message}`;
        statusEl.className = 'map-status error';
      });

      // Custom click handler
      const clickHandler = mapEl.dataset.clickHandler;
      const handler = clickHandler ? (window as any)[clickHandler] : undefined;
      if (typeof handler === 'function') {
        mapEl.addEventListener('ml-map:layer-click', (e) => {
          handler((e as CustomEvent).detail);
        });
      }

      // Control buttons — mapReady() resolves with the live map (immediately
      // once loaded), so an early click waits instead of silently no-oping.
      if (controls) {
        controls.addEventListener('click', async (e) => {
          const btn = (e.target as HTMLElement).closest<HTMLElement>('[data-action]');
          if (!btn) return;

          const map = await mapEl.mapReady();

          const action = btn.dataset.action;

          switch (action) {
            case 'zoom-in':
              map.zoomIn();
              break;
            case 'zoom-out':
              map.zoomOut();
              break;
            case 'reset':
              if (initialCenter && initialZoom !== null) {
                map.flyTo({ center: initialCenter, zoom: initialZoom });
              }
              break;
          }
        });
      }
    });
  }

  initInteractiveMaps();
  document.addEventListener('astro:page-load', initInteractiveMaps);
</script>
```

## Content Collections Integration (Optional/Advanced)

For sites with many maps that need build-time validation, you can use Astro Content Collections. Note that this is more complex than the recommended `src` attribute pattern:

**src/content.config.ts:**

```typescript
import { defineCollection } from "astro:content";
import { glob } from "astro/loaders";
import { getMapSchema } from "@maplibre-yaml/astro/utils";

const maps = defineCollection({
  loader: glob({ pattern: "**/*.yaml", base: "./src/collections/maps" }),
  // The whole map document schema: sources, layers, legend, markers,
  // parameters, images, every config key. Add fields with extendSchema().
  schema: getMapSchema(),
});

export const collections = { maps };
```

<Aside type="caution" title="Don't hand-write the map schema">
  A `z.object({ type, id, config: z.object({ center, zoom, mapStyle }), layers })`
  looks enough, but `z.object()` silently drops every key it doesn't list.
  `sources:`, `legend:`, `markers:`, `parameters:`, `images:` and most
  `config:` keys (`maxZoom`, `interactive`, ...) vanish before the map sees
  them, and a layer that names a source then points at nothing. Use
  `getMapSchema()`, and [`extendSchema()`](#advanced-extending-schemas) for
  fields of your own.
</Aside>

**src/collections/maps/headquarters.yaml:**

```yaml
type: map
id: headquarters
config:
  center: [-122.4194, 37.7749]
  zoom: 15
  maxZoom: 18
  mapStyle: "https://tiles.openfreemap.org/styles/liberty"
sources:
  office:
    type: geojson
    data:
      type: Feature
      geometry:
        type: Point
        coordinates: [-122.4194, 37.7749]
      properties:
        name: "Headquarters"
layers:
  - id: office
    type: circle
    source: office
    legend: { label: Headquarters, color: "#3b82f6" }
    paint:
      circle-radius: 12
      circle-color: "#3b82f6"
legend:
  position: bottom-left
markers:
  - at: [-122.4180, 37.7762]
    color: "#e63946"
    popup:
      - p:
          - str: "Visitor parking"
```

**CollectionMap.astro:**

```astro
---
import 'maplibre-gl/dist/maplibre-gl.css'; // page CSS: here, not in the script tag
import { getEntry } from 'astro:content';

interface Props {
  slug: string;
  height?: string;
}

const { slug, height = '400px' } = Astro.props;

const mapEntry = await getEntry('maps', slug);

if (!mapEntry) {
  throw new Error(`Map not found: ${slug}`);
}

// Content collection already validates against schema
const configJson = JSON.stringify(mapEntry.data);
---

<ml-map style={`height: ${height}; display: block;`} config={configJson} />

<script>
  import { setWorkerUrl } from 'maplibre-gl';
  import workerUrl from 'maplibre-gl/dist/maplibre-gl-worker.mjs?worker&url';
  import '@maplibre-yaml/core/register';

  setWorkerUrl(workerUrl); // maplibre-gl 6: see "Using <ml-map> directly"
</script>
```

**Usage:**

```astro
<CollectionMap slug="headquarters" height="500px" />
```

## Troubleshooting

### `ReferenceError: HTMLElement is not defined`

<Aside type="danger" title="Critical: Do not import register in frontmatter">
  This is the most common error when using maplibre-yaml with Astro.
</Aside>

**Cause:** Importing `@maplibre-yaml/core/register` in an Astro component's frontmatter (`---` block). The register module defines `class MLMap extends HTMLElement`, which crashes during Astro's server-side rendering because `HTMLElement` is a browser-only API.

**Wrong:**

```astro
---
import "@maplibre-yaml/core/register"; // ❌ Crashes during SSR
---
<ml-map src="/map.yaml" style="height: 400px; display: block;" />
```

**Correct:**

```astro
---
import "maplibre-gl/dist/maplibre-gl.css"; // page CSS: here, not in the script tag
---

<ml-map src="/map.yaml" style="height: 400px; display: block;" />

<script>
  import { setWorkerUrl } from "maplibre-gl";
  import workerUrl from "maplibre-gl/dist/maplibre-gl-worker.mjs?worker&url";
  import "@maplibre-yaml/core/register";  // ✅ Runs client-side only

  setWorkerUrl(workerUrl); // maplibre-gl 6: see "Using <ml-map> directly"
</script>
```

Astro processes non-`is:inline` `<script>` tags as client-side bundles — they never run during SSR. The `@maplibre-yaml/astro` components (`Map`, `FullPageMap`, `Scrollytelling`) handle this automatically.

### Using `client:only` or `client:load` on Astro Components

**Symptoms:** `astro build` fails while bundling the package for the browser,
for example `"readFile" is not exported by "__vite-browser-external"` (from
`@maplibre-yaml/astro/src/utils/loader.ts`), or the component doesn't render.

**Cause:** Using client directives (`client:only="react"`, `client:load`, etc.) on components from `@maplibre-yaml/astro`. These are **Astro components**, not framework components (React/Vue/Svelte), so client directives are invalid.

**Wrong:**

```astro
<Map client:only="react" src="/map.yaml" height="400px" />  <!-- ❌ -->
```

**Correct:**

```astro
<Map src="/map.yaml" height="400px" />  <!-- ✅ -->
```

### Incorrect `src` Path for Public Files

**Symptoms:** The map shows a *Map file not found* card
(`Couldn't load src="public/configs/map.yaml": 404 Not Found.`).

**Cause:** Using a filesystem path instead of a URL path for the `src` prop.

**Wrong:**

```astro
<Map src="public/configs/map.yaml" height="400px" />  <!-- ❌ -->
```

**Correct:**

```astro
<Map src="/configs/map.yaml" height="400px" />  <!-- ✅ -->
```

Files in Astro's `/public` directory are served from the root URL, so `public/configs/map.yaml` is accessed as `/configs/map.yaml`.

### "Expected object, got null" or Similar Schema Errors

**Cause:** YAML indentation was destroyed by template literal processing, or the file couldn't be loaded.

**Solutions:**

1. **Use the `src` attribute pattern** (recommended)

   ```astro
   <Map src="/configs/my-map.yaml" />
   ```

   Place your YAML file in `public/configs/my-map.yaml`

2. **Check browser console for loading errors**

   The web component will log errors if it can't fetch or parse the YAML file.

3. **Verify file path is correct**

   Files in `/public` are served from the root, so `/public/configs/map.yaml` becomes `src="/configs/map.yaml"`

### Map Container Has Zero Height

**Symptoms:** Nothing visible, or map is 0px tall. `<ml-map>` shows a short
note asking for a height (unless it has `quiet`).

**Cause:** CSS height not set properly. (The `Map` component sets a height
for you, 400px by default; this is for your own `<ml-map>` components.)

**Solution:**

```astro
<ml-map src="/configs/map.yaml" style="height: 400px; display: block;" />
```

Both `height` and `display: block` are required.

### Map Not Loading from Public Directory

**Symptoms:** The map shows a *Map file not found* card
(`Couldn't load src="/configs/map.yaml": 404 Not Found.`, then the address
the browser asked for), or a network 404 appears in the console

**Cause:** Incorrect path or file not in public directory.

**Solutions:**

1. Ensure file is in `/public` directory (not `/src`)
2. Use root-relative paths: `src="/configs/map.yaml"` for `/public/configs/map.yaml`
3. Check browser network tab for 404 errors
4. Verify file name and extension are correct

### YAML File Changes Not Updating

**Symptoms:** You saved a YAML file under `astro dev` and the map didn't change.

**Cause:** Vite only reloads the page by itself for files it imports.

**Solution:** See [Editing in astro dev](#editing-in-astro-dev). In short: a
normal reload shows edits to `public/` YAML (`src=`) and to files read by
`loadMapConfig` in page frontmatter. The `loadGlobalMapConfig` file needs a
dev-server restart. Add the `@maplibre-yaml/astro/integration` integration and
all of them reload by themselves.

### Maps Work Locally but 404 on GitHub Pages

**Symptoms:** After deploying to `https://<user>.github.io/<repo>/`, a map
shows a *Map file not found* card for `/configs/map.yaml` (the card says when
the page looks like it is under a subpath), or the basemap shows but your data
layer is missing (a notice on the map, and a 404 for `/data/...` in the
console).

**Cause:** The site is served under a base path, and a URL without it points at
the domain root.

**Solution:** See [Deploying to GitHub Pages](#deploying-to-github-pages-or-any-subpath):
set `base` in `astro.config.mjs` (with `@maplibre-yaml/astro` 0.6 and
`@maplibre-yaml/core` 0.8 or later; current releases do this). `Map`,
`FullPageMap` and `Scrollytelling` then add the base to `src` and to every
path inside your YAML. Your own `<ml-map>` components need
`base={import.meta.env.BASE_URL}`.

### TypeScript Errors with `import.meta.glob`

**Solution:** Astro's generated types already declare `import.meta.glob`. Tell
it what a raw import yields with the type argument:

```typescript
const files = import.meta.glob<string>('/src/configs/*.yaml', {
  query: '?raw',
  import: 'default',
});
```

`as: 'raw'` still works but is deprecated: Vite warns on every build.

### Blank Map and "Worker failed to load"

**Symptoms:** The map area stays empty or shows a *Map Error* card saying
*Worker failed to load*; the console names `maplibre-gl-worker.mjs`.

**Cause:** maplibre-gl 6 loads a worker from a separate file, and inside an
Astro (Vite) bundle it cannot find that file unless it is told where it is.
The `@maplibre-yaml/astro` components do this for you; a component of your own
around `<ml-map>` must do it in its script.

**Solution:** Add the two worker lines and the `setWorkerUrl` call shown in
[Using `<ml-map>` directly](#using-ml-map-directly), or use the package's
`<Map>` component instead.

### Web Component Not Defined

**Symptoms:** `<ml-map>` renders as unknown element.

**Cause:** Registration script didn't run.

**Solution:** Ensure script is in component:

```astro
---
import 'maplibre-gl/dist/maplibre-gl.css'; // page CSS: here, not in the script tag
---

<script>
  import { setWorkerUrl } from 'maplibre-gl';
  import workerUrl from 'maplibre-gl/dist/maplibre-gl-worker.mjs?worker&url';
  import '@maplibre-yaml/core/register';

  setWorkerUrl(workerUrl); // maplibre-gl 6: see "Using <ml-map> directly"
</script>
```

The script must be inside the component, not in the frontmatter. On Astro 4,
also check that the page has a `<head>` (see the Astro 4 caution under
[Component Patterns](#component-patterns)).

## Best Practices Summary

<CardGrid>
  <Card title="Use src Attribute (Recommended)" icon="document">
    Place YAML files in `/public/configs/` and use `<ml-map src="/configs/map.yaml">`. Simplest and most maintainable approach.
  </Card>

  <Card title="Set Explicit Dimensions" icon="seti:css">
    Always set `height` and `display: block` on `<ml-map>` elements.
  </Card>

  <Card title="Keep Config Separate" icon="approve-check">
    Avoid inline YAML in components. External files are easier to edit and maintain.
  </Card>

  <Card title="Use Build-Time Validation (Optional)" icon="warning">
    For critical applications, parse YAML at build time (Pattern 2) to catch errors early.
  </Card>
</CardGrid>
