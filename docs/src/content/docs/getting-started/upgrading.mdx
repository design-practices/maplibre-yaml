This page is the release history of maplibre-yaml for anyone with a map that
already works: how to move it to the current release, and what changed in
each release line, newest first. The current line is 0.9:
`@maplibre-yaml/core` 0.9, `@maplibre-yaml/astro` 0.7 and
`@maplibre-yaml/cli` 0.6. Most maps upgrade with no change to their YAML.

Each package's changelog on npm has the complete list of changes.

## How to upgrade

A project keeps the version it was set up with: nothing moves to 0.9 until
you change it.

<Tabs syncKey="upgrade-kind">
<TabItem label="HTML page (CDN)">

The version is part of the script's address. Use the current release line
in the `register.js` line of your page:

```html
<script
  type="module"
  src="https://unpkg.com/@maplibre-yaml/core@0.9/register.js"
></script>
```

The number after `core@` names a release line: the address loads the newest
release in that line, so bug fixes arrive by themselves, but a new line, which
may behave differently, arrives only when you change the number
([Versions in CDN URLs](/getting-started/installation/#versions-in-cdn-urls)).
A story page (`<ml-scrollytelling>`) uses the same script.

If you load the JavaScript API from esm.sh, change the number in that address
the same way:
`https://esm.sh/@maplibre-yaml/core@0.9?external=maplibre-gl`.

</TabItem>
<TabItem label="npm / Vite">

Before 1.0, a range such as `^0.8.1` in `package.json` stays within 0.8.x,
so `npm install` never moves it to 0.9 by itself. Ask for the latest release:

```bash
npm install @maplibre-yaml/core@latest
```

`package.json` then reads `"@maplibre-yaml/core": "^0.9.0"` (or later).

</TabItem>
<TabItem label="Astro">

Upgrade core and the Astro package together (`@maplibre-yaml/astro` 0.7
requires `@maplibre-yaml/core` 0.9 or later):

```bash
npm install @maplibre-yaml/core@latest @maplibre-yaml/astro@latest
```

`package.json` then reads `"@maplibre-yaml/core": "^0.9.0"` and
`"@maplibre-yaml/astro": "^0.7.0"` (or later). Restart `astro dev`
afterwards.

</TabItem>
<TabItem label="CLI">

With `npx maplibre-yaml …` there is nothing installed to upgrade; write
`npx maplibre-yaml@latest …` once so npx doesn't reuse an older copy it
downloaded before. A CLI installed in a project or globally moves with:

```bash
npm install --save-dev @maplibre-yaml/cli@latest   # in a project: ^0.6.0
npm install -g @maplibre-yaml/cli@latest           # installed globally
```

An installed CLI also answers to its short name, `mlym`, which the notes
below use: `mlym validate` is `npx maplibre-yaml validate`.

</TabItem>
</Tabs>

## 0.9

0.9 adds thematic maps, large-data formats such as PMTiles and GeoParquet,
and map titles, descriptions and translations.

### What behaves differently

Your YAML keeps working. These are the changes you might see after upgrading,
and what to do about each, if anything.

- **Hosting maplibre-yaml's files yourself? Copy the whole `dist/` folder.**
  Some parts of maplibre-yaml now load on demand from `dist/chunks/`, next to
  the script: the readers for PMTiles, FlatGeobuf, GeoParquet and COG files
  and the Protomaps basemap. A page that copied only the script keeps working
  for every other map, but a map that needs a missing reader shows a notice
  naming the file. Loading from unpkg or jsDelivr needs no change.
  ([Hosting the files yourself](/getting-started/installation/#hosting-the-files-yourself))
- **`@maplibre-yaml/astro` 0.7 needs `@maplibre-yaml/core` 0.9.** Upgrade
  both together, as in the Astro tab above.
- **The legend's header always reads "Legend".** On a plain map, a custom
  `legend.title` now appears as a heading inside the panel instead of
  replacing the header, matching story legends; a screen reader announces
  every legend the same way. No change to your YAML. CSS that styled
  `.legend-title` as your title should target `.legend-heading`.
  ([Legend](/schema/map-config/#legend))
- **Author hints show only while you develop.** The on-page notice keeps
  showing failures (a data file that didn't load, a layer MapLibre rejected)
  everywhere, but hints meant for you (a "did you mean", a key in the wrong
  place, coordinates that look written latitude-first) now show only on
  `localhost`, in a `file://` page and under `astro dev` or `vite`, not on
  your published site. Add the `debug` attribute (or the `debug` prop on the
  Astro components) to see them on a deployed page; the console always has
  them. ([When are author hints shown?](/troubleshooting/#when-are-author-hints-shown))
- **Strings that start with `=` in a style value now warn.** The format
  reserves them for a future shorthand: `text-field: "=upper({name})"` used to
  draw the text as written and now gets a warning suggesting a MapLibre
  expression. Text that really starts with `=` is written
  `["literal", "=…"]`.
  ([Strings starting with `=` are reserved](/guides/layers/#strings-starting-with--are-reserved))
- **A map without a basemap now warns in validation** (`mlym validate`
  included). `<ml-map>` already refused such a map with an error card; the
  warning says so before you load the page. Add `mapStyle:` under `config:`.
- **Popup numbers follow the page's language.** A `format: ",.0f"` number
  used to be written in US English everywhere; on a page with
  `<html lang="de">` it now reads `8.336.817`. Name a `locale` in the format
  to fix one regardless of the page.
  ([Number formats](/guides/accessibility-languages/#number-formats))
- **`bounds` accepts both of MapLibre's forms**, four numbers
  `[west, south, east, north]` or two corners `[[west, south], [east, north]]`
  (the second used to fail). Values that validated before but broke the map,
  such as a latitude beyond ±90 or three numbers, are now validation errors
  with the expected order spelled out.
  ([Fit to bounds](/schema/map-config/#fit-to-bounds))
- **`fitTo` on a `url:` source opens already framed** on the data, with no
  jump from `center`/`zoom`. While the file loads, the map waits up to 1.5
  seconds before its first paint; on a slow file it then draws at
  `center`/`zoom` and frames the data when it arrives, as before.
  ([Fit to a source's data](/schema/map-config/#fit-to-a-sources-data))
- **`fitTo` keeps a margin around the data.** Without `padding:`, the data is
  framed with a margin (8% of the map's shorter side, 12 to 48 pixels, plus
  room for the attribution at the bottom), so circles and icons at its edges
  are drawn whole instead of cut in half. Write `padding: 0` for the exact
  extent, as 0.8 framed it, or any `padding:` of your own.
  ([Fit to a source's data](/schema/map-config/#fit-to-a-sources-data))
- **A layer's own legend entry shows a legend.** A layer with
  `legend: { label, color }` used to appear only when the document also had a
  `legend:` block; now the map shows a legend for it anyway, as it does for a
  classified layer. Write `legend: false` at the top level to keep a map
  without one. ([Legend](/schema/map-config/#legend))
- **`mlym emit` writes a GeoJSON `url:` source as `data: <url>`**, the way
  the MapLibre style spec expects, so the exported `style.json` now loads in
  MapLibre. A live `url:` source (`refresh:`, `stream:`) is reported as a
  `contract` warning instead of `lossy`.
  ([emit](/cli/reference/#emit))
- **A slow map says it is loading.** If a map hasn't drawn after about a
  second, a small "Loading map…" appears in its middle until the basemap
  draws. A page with its own loading indicator hides it with
  `ml-map .ml-map-loading { display: none; }`.
- **A layer whose `before:` names a layer the map doesn't have is drawn on
  top** instead of disappearing (MapLibre used to refuse it). While you
  develop, the author notes suggest the closest layer id.
- **The CDN script is larger**: about 175 KB gzip, up from about 125 KB, for
  thematic maps, translations, number formatting and the large-data formats.
  The format readers themselves are separate files, downloaded only by maps
  that use them.

### What's new in 0.9

- **Thematic maps.** A layer's `classify:` block makes a choropleth,
  graduated symbols or a category map from your data, with a legend generated
  for it: explicit breaks or quantile, equal-interval and Jenks classes,
  named colour palettes, rates with `normalize:`, and a colour for missing
  values. See [Thematic maps & legends](/guides/thematic-maps/) and the
  [thematic maps example](/examples/thematic-maps/).
- **Large data from YAML alone.** PMTiles, FlatGeobuf, GeoParquet and Cloud
  Optimized GeoTIFF (COG) files, read in parts straight from a static host
  such as GitHub Pages, and a whole basemap from one Protomaps `.pmtiles`
  file with no API key (`mapStyle: data/city.pmtiles` is enough). See
  [Large data: PMTiles, FlatGeobuf, GeoParquet & COG](/guides/cloud-native-data/).
- **Accessible, translated maps.** A document's `title:` and `description:`
  name and describe the map for screen readers; `locale:` translates every
  piece of text the library puts on the map; popup numbers use
  `Intl.NumberFormat` options. See
  [Accessibility & languages](/guides/accessibility-languages/).
- **Smaller conveniences:**
  - `fitTo: tracts`, the source name alone, as shorthand for
    `fitTo: { source: tracts }`.
  - `legend: false` on a layer keeps it out of the legend.
  - The `debug` attribute on `<ml-map>` and `<ml-scrollytelling>` (and the
    `debug` prop on the Astro components) shows author hints on a published
    page.
  - On a narrow map, a legend and a layer panel in two corners of the same
    edge no longer overlap, and a story's pinned legend no longer covers the
    map's notice.
  - `mlym validate` prints *notes* (`ℹ note`) that explain how a valid value
    is read, such as a basemap written as a `.pmtiles` file alone. Notes are
    not warnings: the file still reads `✓ valid`, and `--strict` never fails
    on them.
  - `mlym init --template basic` and `--template story` load core at the
    release line the CLI was built with, so a new project gets the features
    these docs describe.

### Something broke?

See [Troubleshooting](/troubleshooting/). If a map that worked on 0.8 stops
working on 0.9 and the notes above don't explain it, please
[open an issue](https://github.com/design-practices/maplibre-yaml/issues)
with the YAML and what you see.

## Older releases

Moving a project from an older line, such as 0.5, straight to 0.9? Read the
notes for each line you skip, oldest first.

### Upgrading to 0.8

0.8 added the on-map notice for a layer or file that didn't load, the `base`
attribute for sites under a subpath, and story maps in plain HTML
(`<ml-scrollytelling>`). What changes for an existing project:

- **In Astro, a relative path in a document means "from `public/`".**
  `@maplibre-yaml/astro` 0.6 passes the site's base to the map, so
  `data/x.geojson` loads `public/data/x.geojson` on every page. Before, it
  resolved against the page, so on a nested page such as `/blog/post/` it
  asked for `/blog/post/data/x.geojson`. Paths that start with `/` and full
  URLs behave as before. `base={false}` on a component restores the old
  resolution for that map.
- **The CLI needs Node.js 20.9 or later** (`@maplibre-yaml/cli` 0.5).
- **Colour names are checked.** `circle-color: "bleu"` used to validate and
  then drop the layer on the page; it is now a validation error with a "did
  you mean".
- **Two chapters with the same `id` are an error**, naming both lines. Two
  layers with the same `id` warn: the first is drawn and the repeat skipped.
- **Keys nested one level too deep under `config:` warn** (for example
  `legend:` or `controls:`, which belong at the top level), with the line
  number, instead of being ignored.

### Upgrading to 0.7

0.7 added maplibre-gl 6 support, `markers:`, `images:`, hover popups and
3D terrain, sky and globe. What changes for an existing project:

- **Install maplibre-gl yourself.** It is a peer dependency of
  `@maplibre-yaml/core`, no longer installed with it:
  `npm install @maplibre-yaml/core maplibre-gl@^6`.
- **maplibre-gl 6 in a bundler needs its worker set**, or every map fails
  with *Worker failed to load*
  ([Using a bundler (Vite)](/getting-started/installation/#using-a-bundler-vite)).
  On a CDN page, point the import map at `maplibre-gl@6/dist/maplibre-gl.mjs`
  and the stylesheet at `maplibre-gl@6` too. The Astro components set the
  worker themselves.

### Upgrading to 0.6

Three behaviour changes matter when you move to 0.6:

- **`!html` in popups is trust-gated, not unconditional.** A popup `!html`
  value renders as raw markup only under a **trusted** capability policy;
  otherwise it is escaped and shown as text. `<ml-map>` is untrusted by
  default, so there `!html` content is escaped. In Astro, `loadYAML` and
  `loadFromGlob` now parse with core's own options, so an `!html` tag reaches
  the map as the same `{ $html }` value core produces (before, the Astro
  loader silently turned it into a plain string); it then renders under the
  same trust rule.
- **Malformed inline GeoJSON now warns.** A v1 document whose inline GeoJSON
  `data` is malformed gets a warning, which `mlym validate --strict` and CI
  runs treat as an error. Check inline geometry before upgrading.
- **Format v2 `style.metadata` carries through.** In a v2 document,
  `style.metadata` is copied to the root `metadata` of the emitted
  `style.json`.

### Astro with core 0.6.0 or earlier

With `@maplibre-yaml/core` 0.6.0 or earlier, every `@maplibre-yaml/astro`
component fails under `astro dev` with *Failed to create map: Map is not a
constructor*, while `astro build` works: Vite never pre-bundles maplibre-gl
when only a dependency's `.astro` file imports it. Current releases are not
affected; upgrade core and the Astro package together
([How to upgrade](#how-to-upgrade)). If a project must stay on core 0.6.0,
tell Vite to pre-bundle maplibre-gl:

```js
// astro.config.mjs
import { defineConfig } from "astro/config";

export default defineConfig({
  vite: { optimizeDeps: { include: ["maplibre-gl"] } },
});
```
