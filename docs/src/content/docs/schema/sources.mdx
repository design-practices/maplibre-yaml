Data sources provide the data for map layers. maplibre-yaml supports all MapLibre GL JS source types with enhanced features for dynamic data loading, real-time updates, and streaming.

:::note[Placeholder URLs]
Snippets on this page that show a single `source:` use placeholder URLs such
as `https://example.com/…` and `api.example.com` — swap in your own data.
Complete documents (the ones starting with `type: map`) use real, public data
and run as printed.
:::

## Source Types

| Type | Description | Use Case |
|------|-------------|----------|
| `geojson` | GeoJSON point, line, and polygon data | Primary data source, supports real-time updates |
| `vector` | Vector tiles (Mapbox Vector Tiles) | Efficient large datasets, base maps |
| `raster` | Raster tile imagery | Satellite imagery, basemaps |
| `raster-dem` | Elevation (DEM) tiles | Hillshade and color-relief layers, 3D `terrain:` |
| `image` | Single image overlay | Map overlays, floor plans |
| `video` | Video overlay | Animated overlays |

### Cloud-native files (PMTiles, FlatGeobuf, GeoParquet, COG)

`type:` stays the MapLibre source type; the `url:` says what the file is. A
**PMTiles** archive (`.pmtiles`, or a `pmtiles://` URL) works on a `vector`,
`raster` or `raster-dem` source, a **FlatGeobuf** file (`.fgb`) or a
**GeoParquet** file (`.parquet`, `.geoparquet`) on a `geojson` source, and a
**Cloud Optimized GeoTIFF** (`.tif`, `.tiff`, or a `cog://` URL; Web Mercator
only) on a `raster` or `raster-dem` source — with no page JavaScript. These
keys go with them:

| Property | On | Description |
|----------|----|-------------|
| `format` | `vector`, `raster`, `raster-dem`, `geojson` | `pmtiles`, `flatgeobuf`, `geoparquet` or `cog` — only for a URL with no telling extension (it wins over the URL) |
| `load` | FlatGeobuf, GeoParquet (`geojson`) | `all` (default): the whole file; `viewport` or `{ mode: viewport, minzoom }`: only the features in view (needs range requests, and a FlatGeobuf spatial index or a GeoParquet `bbox` covering column) |
| `columns` | GeoParquet (`geojson`) | The columns to read: by default only the ones the document references (paint, filters, popups, `classify:` …); a list replaces that, `all` reads every column |
| `colorRamp` | COG (`raster`) | Colours for a single band of values: `{ palette, min, max }` (palette names as in `classify:`, default `viridis`), or `colors: ["#…", "#…"]` instead of `palette`; `reverse: true`; `classes: 5` for flat classes instead of a smooth ramp (with `colors:`, spread along them) |

```yaml
sources:
  buildings:
    type: vector
    url: data/buildings.pmtiles
  parcels:
    type: geojson
    url: data/parcels.fgb
    load: { mode: viewport, minzoom: 14 }
  wells:
    type: geojson
    url: data/wells.parquet
    columns: [name, depth_m]
  elevation:
    type: raster-dem
    url: data/elevation.tif          # hillshade layers and terrain:
  ndvi:
    type: raster
    url: data/ndvi.tif
    colorRamp: { palette: YlGn, min: 0, max: 0.9 }
```

`type: pmtiles` (or `flatgeobuf`, `fgb`, `geoparquet`, `parquet`, `cog` …) is an
error that tells you what to write instead. In a v2 document, `format`, `load`,
`columns` and `colorRamp` go under the source's `runtime:`. Hosting, sizes and
error messages: [Cloud-native
data](/guides/cloud-native-data/).

## GeoJSON Source

The primary data source type with comprehensive support for dynamic data loading.

### Data Loading Strategies

| Strategy | Description | When to Use |
|----------|-------------|-------------|
| `runtime` (default) | Fetch when map loads | Keep bundle small, fresh data |
| `build` | Fetch at build time | Faster load, static data |
| `hybrid` | Build-time with runtime refresh | Best of both: fast initial + updates |

### Basic Structure

```yaml
source:
  type: geojson
  url: "https://example.com/data.geojson"
  fetchStrategy: runtime
```

### Data Source Options

**One of these is required:**

| Property | Type | Description |
|----------|------|-------------|
| `url` | string | URL to fetch GeoJSON data — or a FlatGeobuf `.fgb` or GeoParquet `.parquet` file ([cloud-native](#cloud-native-files-pmtiles-flatgeobuf-geoparquet-cog)) |
| `data` | object | Inline GeoJSON object |
| `prefetchedData` | object | Pre-fetched data from build time |

### Examples

#### URL Source

```yaml
source:
  type: geojson
  url: "https://earthquake.usgs.gov/earthquakes/feed/v1.0/summary/all_week.geojson"
```

#### Files on your own site (relative paths)

`url:` also takes a path to a file served by your own site. All of these work:

```yaml
source:
  type: geojson
  url: "data/cities.geojson"      # relative to the page
  # url: "./data/cities.geojson"  # the same thing
  # url: "/data/cities.geojson"   # from the site root
```

**Relative paths resolve against the web page, not the YAML file.** The
browser fetches them exactly as it would a link on that page. With this
layout:

```text
index.html          <ml-map src="maps/city.yaml">
maps/city.yaml
maps/cities.geojson
```

`url: "cities.geojson"` inside `maps/city.yaml` loads `/cities.geojson` (next
to `index.html`) and fails. Write `url: "maps/cities.geojson"`, or use a
root-relative `/maps/cities.geojson`. If a data file doesn't load, the map
shows a notice naming the file and the full address the browser tried, and,
for a YAML file in another folder, the path to write instead.

The same rule applies to every URL in a document: other source `url:` and
`tiles:` entries, `images:`, marker icons, `mapStyle`, and scrollytelling
chapter `image:`/`video:`. (Older releases rejected a bare relative path
like `data/x.geojson` and required `./` or `/` in front of it.)

**On a site published under a subpath** (a GitHub Pages project site at
`https://<user>.github.io/<repo>/`), give `<ml-map>` a `base`:
`<ml-map src="maps/city.yaml" base="/<repo>/">`. Then `/data/cities.geojson`
and `data/cities.geojson` both load `/<repo>/data/cities.geojson`, on every
page, without writing the repo name into the YAML. The Astro `Map` and
`FullPageMap` components set it for you. See
[Sites under a subpath](/guides/publishing/#html-pages-the-base-attribute)
for the full list of fields it applies to.

#### Inline Data

```yaml
source:
  type: geojson
  data:
    type: FeatureCollection
    features:
      - type: Feature
        geometry:
          type: Point
          coordinates: [-74.006, 40.7128]
        properties:
          name: "New York"
          population: 8336817
      - type: Feature
        geometry:
          type: Point
          coordinates: [-118.2437, 34.0522]
        properties:
          name: "Los Angeles"
          population: 3979576
```

#### Build-Time Fetch

```yaml
source:
  type: geojson
  url: "https://example.com/static-data.geojson"
  fetchStrategy: build
```

## GeoJSON Sugar

For hand-authored data, spelling out `data:` as a full `Feature` or
`FeatureCollection` is a lot of ceremony for a handful of coordinates. A
`type: geojson` source may instead carry one of four **sugar** keys in the
data position. Each normalizes to canonical GeoJSON immediately after parse —
before validation — so the renderer only ever sees the `Feature` /
`FeatureCollection` it stands for.

| Sugar | Produces | Coordinates shape |
|-------|----------|-------------------|
| `location` | a single Point `Feature` | `[longitude, latitude]` |
| `locations` | a `FeatureCollection` of Points | array of `{ coordinates, name?, description? }` |
| `region` | a Polygon `Feature` | array of linear rings (`Position[][]`) |
| `route` | a LineString `Feature` (≥ 2 positions) | array of positions (`Position[]`) |

Sugar is valid **only** on `type: geojson` sources and is **mutually exclusive**
with `data:` and `url:` — author exactly one of them. An optional `name` and
`description` on a sugar node become the Feature's `properties` (each defaulting
to `""`); styling and camera fields have no home here — they belong on the
layer's paint or the map's camera.

#### `location` — one point

```yaml
source:
  type: geojson
  location:
    coordinates: [-73.98, 40.75]
    name: "Site"
    description: "A single point of interest"
```

#### `locations` — many points

```yaml
source:
  type: geojson
  locations:
    - coordinates: [-74.00, 40.73]
      name: "Stop A"
    - coordinates: [-73.96, 40.77]
      name: "Stop B"
```

#### `region` — a polygon

`coordinates` is an array of linear rings, exactly as GeoJSON `Polygon`
coordinates are: the first ring is the outer boundary, and each ring should
close (its last position repeating its first).

```yaml
source:
  type: geojson
  region:
    coordinates:
      - [[-74.02, 40.70], [-73.94, 40.70], [-73.94, 40.80], [-74.02, 40.80], [-74.02, 40.70]]
    name: "Study district"
```

#### `route` — a line

```yaml
source:
  type: geojson
  route:
    coordinates: [[-74.00, 40.73], [-73.98, 40.75], [-73.96, 40.77]]
    name: "Walking route"
```

#### A complete map using all four

The sugars compose like any other named source — define them under `sources:`
and reference each by name from a layer:

```yaml
type: map
id: sugar-tour
config:
  center: [-73.98, 40.75]
  zoom: 11
  mapStyle: "https://tiles.openfreemap.org/styles/liberty"
sources:
  site:
    type: geojson
    location:
      coordinates: [-73.98, 40.75]
      name: "Site"
  stops:
    type: geojson
    locations:
      - coordinates: [-74.00, 40.73]
        name: "Stop A"
      - coordinates: [-73.96, 40.77]
        name: "Stop B"
  district:
    type: geojson
    region:
      coordinates:
        - [[-74.02, 40.70], [-73.94, 40.70], [-73.94, 40.80], [-74.02, 40.80], [-74.02, 40.70]]
      name: "Study district"
  path:
    type: geojson
    route:
      coordinates: [[-74.00, 40.73], [-73.98, 40.75], [-73.96, 40.77]]
      name: "Walking route"
layers:
  - id: district-fill
    type: fill
    source: district
    paint:
      fill-color: "#10b981"
      fill-opacity: 0.3
  - id: path-line
    type: line
    source: path
    paint:
      line-color: "#f59e0b"
      line-width: 4
  - id: stops-dots
    type: circle
    source: stops
    paint:
      circle-radius: 7
      circle-color: "#2563eb"
  - id: site-dot
    type: circle
    source: site
    paint:
      circle-radius: 9
      circle-color: "#dc2626"
```

## Real-Time Updates

A GeoJSON source given by `url:` can keep itself current: `refresh:` polls
the URL every `refreshInterval` milliseconds, and `stream:` receives updates
over a WebSocket or Server-Sent Events. `updateStrategy` says how new
features combine with the ones on the map: `replace` (the default) swaps the
whole dataset, `merge` updates features that share an `updateKey` and adds
new ones, and `append-window` adds them while keeping at most `windowSize`
features or `windowDuration` milliseconds of them.

```yaml
source:
  type: geojson
  url: "https://api.example.com/vehicles"
  refresh:
    refreshInterval: 10000
    updateStrategy: merge
    updateKey: "vehicleId"  # required for merge
```

A streamed source still needs somewhere to start: a `url:` to load first, or
`data:` with an empty `FeatureCollection` to start blank (validation refuses a
GeoJSON source with only `stream:`). Write a `refresh:` block next to
`stream:`: the stream connects only when one is there, and its
`updateStrategy` says how each message is applied.

```yaml
source:
  type: geojson
  url: "https://api.example.com/features"   # the current state, loaded first
  stream:
    type: sse                               # or websocket, with a wss:// url
    url: "https://api.example.com/events"
  refresh:
    updateStrategy: merge
    updateKey: "id"
```

How each strategy behaves, reconnection, and reacting to updates from your
page's JavaScript are in [Live data & streaming](/guides/live-data/). Every
key with its type and default is in the sources reference:
[`refresh:`](/reference/yaml/sources/#geojson-refresh) and [`stream:`](/reference/yaml/sources/#geojson-stream).
Live updates work on GeoJSON sources only; a FlatGeobuf or GeoParquet file is
read once.

## Point Clustering

Automatically cluster nearby points at lower zoom levels.

```yaml
source:
  type: geojson
  url: "https://example.com/points.geojson"
  cluster: true
  clusterRadius: 50
  clusterMaxZoom: 14
  clusterMinPoints: 2
```

`clusterRadius` is in pixels (50 by default), and `clusterMaxZoom` is the last
zoom level at which points are clustered; every clustering key is in the
[sources reference](/reference/yaml/sources/#geojson-cluster).

### Cluster Properties Example

Calculate aggregates for clusters:

```yaml
source:
  type: geojson
  url: "https://example.com/earthquakes.geojson"
  cluster: true
  clusterRadius: 50
  clusterMaxZoom: 14
  clusterProperties:
    maxMagnitude: ["max", ["get", "magnitude"]]
    avgMagnitude: ["avg", ["get", "magnitude"]]
    count: ["+", 1]
```

## Loading UI

Loading feedback needs no configuration: while a map starts, `<ml-map>`
marks itself busy (`aria-busy="true"`) and shows a small "Loading map…" if it
hasn't drawn after about a second, and a data file that fails to load is
listed in a notice on the map
([Troubleshooting](/troubleshooting/#reading-what-the-map-tells-you)). A
source's `loading:` block (`enabled`, `message`, `showErrorOverlay`) draws no
overlay of its own: it still validates, with a warning that it has no effect
(deprecated since core 0.9.1), so you can remove it.

## Caching

Control HTTP caching behavior.

```yaml
source:
  type: geojson
  url: "https://example.com/data.geojson"
  cache:
    enabled: true
    ttl: 300000  # 5 minutes
```

Caching is on by default; `ttl` (milliseconds) overrides how long a
response is reused. Turn it off for live data. See
[`cache:`](/reference/yaml/sources/#geojson-cache).

## Additional GeoJSON Options

MapLibre's own GeoJSON source options pass through: `tolerance`, `buffer`,
`lineMetrics`, `generateId`, `promoteId` (`generateId` or `promoteId` is
needed for hover highlights) and `attribution`
([sanitized](#attribution-is-sanitized)). Each is in the
[sources reference](/reference/yaml/sources/#geojson-tolerance).

### Example

```yaml
source:
  type: geojson
  url: "https://example.com/lines.geojson"
  lineMetrics: true
  tolerance: 0.375
  buffer: 128
  attribution: "© Data Provider"
```

## Attribution is sanitized

Every source type's `attribution` is shown in MapLibre's attribution
control, which renders it as HTML. maplibre-yaml sanitizes it first, under
every trust policy: plain text, character references such as `&copy;`, and
`<a href="…">` links with an `http:`, `https:` or `mailto:` URL (keeping only
`href`, `target` and `rel`) pass through; any other markup is escaped and
shows as literal text. The same rule applies to attribution that arrives from
a TileJSON `url:` or a basemap style, and to the `style.json` that
`mlym emit` writes (which reports a `contract` warning when it changes one).
See [Trust and attribution](/integrations/web-components/#trust-and-attribution)
for why: MapLibre's own attribution sanitizer can be bypassed on every
supported maplibre-gl.

## Vector Source

Vector tiles for efficient large dataset rendering.

### Structure

```yaml
source:
  type: vector
  url: "https://api.maptiler.com/tiles/v3/tiles.json?key=YOUR_KEY"
```

or

```yaml
source:
  type: vector
  tiles:
    - "https://tile.example.com/{z}/{x}/{y}.pbf"
  minzoom: 0
  maxzoom: 14
```

Give `url` (a TileJSON URL, or a PMTiles archive: `.pmtiles` or
`pmtiles://`) or `tiles` (tile URL templates). `minzoom`, `maxzoom`,
`bounds`, `scheme` and `attribution` ([sanitized](#attribution-is-sanitized))
are MapLibre's; every key is in the [sources reference](/reference/yaml/sources/#vector).

### Example

```yaml
source:
  type: vector
  tiles:
    - "https://demotiles.maplibre.org/tiles/{z}/{x}/{y}.pbf"
  minzoom: 0
  maxzoom: 14
  bounds: [-180, -85, 180, 85]
  attribution: "© MapLibre"
```

## Raster Source

Raster tile imagery for satellite, terrain, etc.

### Structure

```yaml
source:
  type: raster
  tiles:
    - "https://tile.openstreetmap.org/{z}/{x}/{y}.png"
  tileSize: 256
  maxzoom: 19
  attribution: "© OpenStreetMap contributors"
```

Give `url` (a TileJSON URL, a PMTiles archive, or a Cloud Optimized GeoTIFF:
`.tif` / `.tiff` / `cog://`, see [cloud-native](#cloud-native-files-pmtiles-flatgeobuf-geoparquet-cog))
or `tiles`. `tileSize` defaults to 512, so set `256` for most raster tile
servers. A COG with one band of values takes `colorRamp:`. Every key is in
the [sources reference](/reference/yaml/sources/#raster).

### Example

```yaml
source:
  type: raster
  tiles:
    - "https://server.arcgisonline.com/ArcGIS/rest/services/World_Imagery/MapServer/tile/{z}/{y}/{x}"
  tileSize: 256
  maxzoom: 19
  attribution: "Esri, Maxar, Earthstar Geographics"
```

## Raster DEM Source

Elevation tiles for `hillshade` and `color-relief` layers. Shaped like a raster source, plus an
`encoding` describing how elevation is packed into the tile's RGB channels.

### Structure

```yaml
source:
  type: raster-dem
  tiles:
    - "https://example.com/dem/{z}/{x}/{y}.png"
  encoding: terrarium
  tileSize: 256
```

Give `url` (a TileJSON URL, a PMTiles archive or a COG, as on a raster
source) or `tiles`. `encoding` is `mapbox` (the default), `terrarium` or
`custom`; a `custom` encoding also accepts MapLibre's `redFactor`,
`greenFactor`, `blueFactor` and `baseShift`. Every key is in the
[sources reference](/reference/yaml/sources/#raster-dem).

### Example

A complete hillshade map:

```yaml
type: map
id: terrain
config:
  center: [-121.7, 46.85]
  zoom: 11
  mapStyle: "https://tiles.openfreemap.org/styles/liberty"
layers:
  - id: hills
    type: hillshade
    source:
      type: raster-dem
      url: "https://tiles.mapterhorn.com/tilejson.json"
      encoding: terrarium
    paint:
      hillshade-exaggeration: 0.6
```

### 3D terrain

The same source type drives map-level 3D terrain. Declare the DEM as a
**named** source and point the document-root `terrain:` at it — see
[Terrain, sky & projection](/schema/map-config/#terrain-sky--projection):

```yaml
type: map
id: alps
config:
  center: [11.39, 47.27]
  zoom: 12
  pitch: 70
  mapStyle: "https://tiles.openfreemap.org/styles/liberty"
sources:
  terrainSource:
    type: raster-dem
    url: "https://tiles.mapterhorn.com/tilejson.json"
    encoding: terrarium
terrain:
  source: terrainSource
  exaggeration: 1
```

:::note
`encoding` defaults to `mapbox` even when `url:` points at a TileJSON that
declares a different one, so set it explicitly for terrarium tiles. MapLibre
recommends a separate `raster-dem` source for a `hillshade` layer rather than
sharing the terrain's — one source serving both renders at reduced quality.
:::

## Image Source

Single image overlay anchored to geographic coordinates.

### Structure

Four corner coordinates must be specified clockwise starting from top-left:
1. Top-left
2. Top-right
3. Bottom-right
4. Bottom-left

```yaml
source:
  type: image
  url: "https://example.com/overlay.png"
  coordinates:
    - [-80.425, 46.437]  # top-left
    - [-71.516, 46.437]  # top-right
    - [-71.516, 37.936]  # bottom-right
    - [-80.425, 37.936]  # bottom-left
```

Both `url` and `coordinates` are required
([image source reference](/reference/yaml/sources/#image)).

### Example

```yaml
- id: map-overlay
  type: raster
  source:
    type: image
    url: "https://example.com/historical-map-1890.png"
    coordinates:
      - [-80.425, 46.437]
      - [-71.516, 46.437]
      - [-71.516, 37.936]
      - [-80.425, 37.936]
  paint:
    raster-opacity: 0.7
```

## Named Source Definitions

Define sources once and reference them by name across multiple layers.

### Block-Level Sources

The recommended approach for most use cases. Define sources directly on a map block and reference them by string ID in layers:

```yaml
type: map
id: neighborhood-map
config:
  center: [-74.025, 40.72]
  zoom: 13.5
  mapStyle: "https://basemaps.cartocdn.com/gl/positron-gl-style/style.json"

sources:
  states:
    type: geojson
    url: "https://maplibre.org/maplibre-gl-js/docs/assets/us_states.geojson"
  omt:
    type: vector
    url: "https://tiles.openfreemap.org/planet"

layers:
  - id: state-fill
    type: fill
    source: states
    filter: ["==", ["get", "STATE_NAME"], "New Jersey"]
    paint:
      fill-color: "#3388ff"
      fill-opacity: 0.15
  - id: state-outline
    type: line
    source: states
    paint:
      line-color: "#3388ff"
      line-width: 2
  - id: buildings
    type: fill
    source: omt
    source-layer: building
    paint:
      fill-color: "#9ca3af"
```

### Live Refresh on a Named Source

A named source refreshes like an inline one, and does so **once** no matter how
many layers reference it:

```yaml
sources:
  vehicles:
    type: geojson
    url: "https://api.example.com/vehicles"
    refresh:
      refreshInterval: 5000
      updateStrategy: merge
      updateKey: vehicleId

layers:
  - id: vehicle-dots
    type: circle
    source: vehicles
  - id: vehicle-labels
    type: symbol
    source: vehicles
```

One poll feeds both layers, and each still receives its own
`ml-map:layer-data-loaded` event. Polling stops when the last layer referencing
the source is removed.

The layer-keyed APIs resolve to the shared source, so you address it through
any referencing layer:

```js
renderer.updateLayerData("vehicle-dots", geojson);  // updates both layers
```

`updateLayerData` writes to the **source**, so every layer drawing from it
reflects the change. That is intended: one source, one dataset.

### Referencing With `$ref`

A layer can also point at a source with a JSON-pointer style reference. In a
map document it resolves against the document's own `sources:`; in a
[multi-page document](/schema/root/#root-level-sources-ref) it resolves
against the root `sources:`, next to `pages:`.

```yaml
sources:
  boundary:
    type: geojson
    url: "https://maplibre.org/maplibre-gl-js/docs/assets/us_states.geojson"

layers:
  - id: boundary-fill
    type: fill
    source: { $ref: "#/sources/boundary" }
```

Unlike the bare name (`source: boundary`), which shares one source between
the layers that name it, `$ref` copies the definition into the layer when the
document is read, so each layer gets its own copy. Prefer the bare name;
`$ref` exists for generated documents, tooling and multi-page documents.
Nested references — a `$ref` whose target itself contains a `$ref` — are not
resolved.

Block-level sources are added to the map before layers are processed, so any layer in that block can reference them by name. This avoids duplicating source definitions when multiple layers use the same data.

### Sharing Sources Across Pages (Multi-Page)

To reuse the same data on multiple pages of a root document, define a named **layer** (with its source inline) at the root level and pull it into blocks with a `$ref` object:

```yaml
layers:
  quakes:
    id: quakes
    type: circle
    source:
      type: geojson
      url: "https://earthquake.usgs.gov/earthquakes/feed/v1.0/summary/all_week.geojson"
      refresh:
        refreshInterval: 300000
        updateStrategy: replace
    paint:
      circle-radius: 6
      circle-color: "#e74c3c"

pages:
  - path: "/"
    title: "Home"
    blocks:
      - type: map
        id: main-map
        config:
          center: [0, 0]
          zoom: 2
          mapStyle: "https://tiles.openfreemap.org/styles/liberty"
        layers:
          - $ref: "#/layers/quakes"
```

A layer can also reach a root-level source with the object form
`source: { $ref: "#/sources/name" }` (see [Root-level sources](/schema/root/#root-level-sources-ref)).
The string form `source: "#/sources/name"` is never resolved, and bare names
(`source: quakes`) only resolve against the map block's own `sources:` section.

### Inline Sources

For single-use sources, the inline pattern still works and is the simplest approach:

```yaml
layers:
  - id: markers
    type: circle
    source:
      type: geojson
      data:
        type: FeatureCollection
        features: []
    paint:
      circle-radius: 6
      circle-color: "#3b82f6"
```

All three patterns (block-level named sources, shared named layers, inline sources) can be mixed freely within a configuration.

### Clustered Points with Custom Properties

```yaml
- id: earthquakes
  type: circle
  source:
    type: geojson
    url: "https://earthquake.usgs.gov/earthquakes/feed/v1.0/summary/all_week.geojson"
    cluster: true
    clusterRadius: 50
    clusterMaxZoom: 12
    clusterProperties:
      maxMagnitude: ["max", ["get", "mag"]]
      count: ["+", 1]
  paint:
    circle-radius:
      - case
      - ["has", "point_count"]
      - ["step", ["get", "point_count"], 20, 10, 30, 50, 40]
      - 8
    circle-color:
      - case
      - ["has", "point_count"]
      - ["interpolate", ["linear"], ["get", "maxMagnitude"], 0, "#fef3c7", 8, "#dc2626"]
      - "#3b82f6"
```
