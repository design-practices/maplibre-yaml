A GeoParquet overview file (`geo:overviews`, major version 0) read by view now draws the level that fits the zoom: at each settled view, the finest level whose zoom is at or below the map's whole zoom (the coarsest one further out), instead of always the full-detail level. Levels apply whenever the file is read by view — `load: viewport`, or the default on a file over the whole-file limits counted on its full-detail rows; a smaller file is still read whole at full detail, and `load: { overviews: false }` keeps the full-detail level only. Without an author `minzoom`, such a file is read from zoom 0, so its coarsest level serves wide views; an author `minzoom` still wins. The per-view budget applies to the level being read: a level over `maxFeatures` shows the zoom-in line (no coarser level is drawn instead) with one author hint naming what the coarsest level holds there and how to rebuild the overviews, and a level that declares neither `zoom` nor `gsd` draws full detail with one hint. A level switch is a data change, not a document update: it fires no `ml-map:update-applied`, and hover and selection feature state for the source is reset at the switch, since feature ids are unique only within a level. Overview hints are shown once per source, also across the reader a live update recreates for a changed `load:`.

GeoParquet and FlatGeobuf sources accept `load: { overviews: false }` (experimental), in v1 documents and under a v2 source's `runtime:`, and the key is in the JSON Schema. It is the switch for GeoParquet overview files (`geo:overviews`): read by view, they are set to draw the level that fits the zoom, and `overviews: false` keeps 0.9.2's full-detail level only. On a FlatGeobuf source the key warns that it does nothing; a value that isn't `true` or `false` is an error. A source key of the wrong type, such as `load: { maxFeatures: lots }`, is now reported at that key (`sources.lots.load.maxFeatures`) rather than at the source.

New exports `readGeoParquetFacts(buffer, name)` and `readFlatGeobufFacts(buffer, name)` report what a GeoParquet or FlatGeobuf file holds — rows and row groups (rows per group, the bbox column, whether the groups are spatially sorted, overview levels with their zooms) or a FlatGeobuf header's feature count, spatial index and geometry type, plus the CRS and extent — from the file's footer or header alone, through any `AsyncBuffer` (`{ byteLength, slice(start, end?) }`, hyparquet's shape: a file handle, a range reader over HTTP, or bytes in memory). They are Node-safe and import nothing from `node:`, and a projected CRS or a GeoArrow encoding is reported (`lonLat: false`, `encoding`) instead of refused. The readers load on first use from the same on-demand modules as the decoders, so the CDN bundle does not grow.

A `classify:` with a computed `method:` now works on a GeoParquet source read by view (`load: viewport`, or a file over the whole-file limits that switched itself to by view), instead of being refused. The breaks come from the `field` column (and the `normalize` column, if any) of the file's full-detail rows — never a coarse overview level — read once, without geometry, when the source loads, so the legend and the paint stay the same at every zoom and pan and change only when the document does. Each scanned column may be up to 32 MB compressed, counted separately for `field` and `normalize`. Over that, or when the read fails, the layer keeps its no-data colour and shows one notice naming `mlym breaks`. A missing or text field gets the usual field hint. FlatGeobuf sources read by view and vector tile sources (PMTiles) are still refused. Their notice, at parse time and at runtime, now names `mlym breaks` with the file, field, method and classes filled in, and you paste the `breaks: [...]` line it prints.
