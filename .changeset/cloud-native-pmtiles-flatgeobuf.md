PMTiles and FlatGeobuf now work from YAML alone — no page JavaScript, in plain HTML from the CDN, under Vite/Astro, in `<ml-map>`, `<ml-scrollytelling>` and v1/v2 documents. Keep `type:` as the MapLibre source type and point `url:` at the file: a `.pmtiles` file (or `pmtiles://` URL) on a `vector`, `raster` or `raster-dem` source, a `.fgb` file on a `geojson` source; add `format:` only for a URL without a telling extension. Core registers the PMTiles protocol once on the maplibre-gl module it renders with, before any map is created (a page's own `pmtiles` registration is kept), so a basemap style loaded from a URL can use `pmtiles://` too: a Protomaps basemap, or one hosted next to the site as a single PMTiles extract. Inside such a style, relative URLs (the file inside `pmtiles://`, TileJSON, tiles, sprite and glyphs) resolve against the style.json itself, and a missing file gets a notice instead of a blank basemap. A full basemap needs no style file either: `mapStyle: { pmtiles: data/nyc.pmtiles, flavor: dark, lang: es }` (`basemap:` in v2; also accepted as `defaultMapStyle` and by the Astro map builders' `mapStyle` option) builds the Protomaps basemap style in the page around a Protomaps `.pmtiles` extract hosted with the site or on any server with range requests, with no API key and no tile server: the layers of the `light`, `dark`, `white`, `grayscale` or `black` flavor, labels in `lang:` or else the page's language, OpenStreetMap and Protomaps attribution, and Protomaps' hosted fonts and icons unless `glyphs:`/`sprite:` point at your own copies. A relative path resolves against the page with `base` applied; the document's layers draw on top, and `before:` and story chapters can name the basemap's layers by id. Validation tells the shorthand apart from a style object by shape and catches a misspelled flavor or key and a file that isn't `.pmtiles`; the map's notice names a missing file or a PMTiles file that isn't a Protomaps basemap. Core reads FlatGeobuf into an ordinary GeoJSON source, so popups, legends, `fitTo` and clustering work unchanged; `load: viewport` reads only the features in view from large indexed files, and size guards keep a too-big file from freezing the tab. `base` now applies to the file inside a `pmtiles://` URL (these 404'd on GitHub Pages project sites). Failures — a server without range requests (`python -m http.server`), CORS, a wrong path that returned a web page, a missing file, a projected or Zstandard-compressed FlatGeobuf, a file too large to read whole — appear in the map's notice in plain words. `type: pmtiles` / `flatgeobuf` / `mbtiles` and a format on the wrong source type are validation errors with the fix; GeoParquet (`.parquet`) and COG (`.tif`, `cog://`) are recognized and reported as "not supported yet", so documents written today keep their meaning when they land. `mlym emit` writes PMTiles sources as `pmtiles://` URLs, writes a Protomaps basemap as the full style it generates, and converts FlatGeobuf files to inline GeoJSON. The readers ship inside core, so there is nothing extra to install, and installing core no longer pulls in OpenLayers, which the flatgeobuf package lists as an optional dependency. They are not part of core's main script: a page downloads a reader only when a map uses its format (see the entry on on-demand format readers). Cloud-native support adds about 9 KB gzip to the CDN build `register.browser.js`; the readers themselves (about 8 KB gzip for PMTiles, 12 KB for FlatGeobuf) and the Protomaps basemap style generator (about 7 KB) load only when needed. Across the whole 0.9 release, including thematic maps, translatable UI strings and number formatting, `register.browser.js` grows from about 124 KB to about 160 KB gzip (+36 KB) compared with 0.8.1.
