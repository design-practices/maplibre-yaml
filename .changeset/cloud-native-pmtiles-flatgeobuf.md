PMTiles, FlatGeobuf and GeoParquet now work from YAML alone — no page JavaScript, in plain HTML from the CDN, under Vite/Astro, in `<ml-map>`, `<ml-scrollytelling>` and v1/v2 documents. Keep `type:` as the MapLibre source type and point `url:` at the file: a `.pmtiles` file (or `pmtiles://` URL) on a `vector`, `raster` or `raster-dem` source, a `.fgb` or `.parquet` file on a `geojson` source; add `format:` only for a URL without a telling extension. Core registers the PMTiles protocol once on the maplibre-gl module it renders with, before any map is created (a page's own `pmtiles` registration is kept), so a basemap style loaded from a URL can use `pmtiles://` too: a Protomaps basemap, or one hosted next to the site as a single PMTiles extract. Inside such a style, relative URLs (the file inside `pmtiles://`, TileJSON, tiles, sprite and glyphs) resolve against the style.json itself, and a missing file gets a notice instead of a blank basemap. Core reads FlatGeobuf and GeoParquet into an ordinary GeoJSON source, so popups, legends, `classify:`, `fitTo` and clustering work unchanged; `load: viewport` reads only the features in view from large files (a FlatGeobuf spatial index, or a GeoParquet file's `bbox` covering column and location-sorted row groups), and size guards keep a too-big file from freezing the tab. GeoParquet reads only the columns the document uses (paint, filters, popups, `classify:` …; `columns:` chooses them, `columns: all` reads every one), opens a file with a single request, and reads WKB geometry in snappy, zstd, gzip, lz4 or brotli files. `base` now applies to the file inside a `pmtiles://` URL (these 404'd on GitHub Pages project sites). Failures — a server without range requests (`python -m http.server`), CORS, a wrong path that returned a web page, a missing file, a projected or Zstandard-compressed FlatGeobuf, a projected GeoParquet file, GeoArrow-encoded geometry (with the command that rewrites it as WKB), a Parquet file without geometry metadata, a file too large to read whole — appear in the map's notice in plain words. `type: pmtiles` / `flatgeobuf` / `geoparquet` / `mbtiles`, a format on the wrong source type, and live data (`refresh:`/`stream:`) on a FlatGeobuf or GeoParquet source are validation errors with the fix (`format: parquet` gets "did you mean `geoparquet`"); COG (`.tif`, `cog://`) is recognized and reported as "not supported yet", so documents written today keep their meaning when it lands. `mlym emit` writes PMTiles sources as `pmtiles://` URLs and converts FlatGeobuf and GeoParquet files to inline GeoJSON (for GeoParquet, every column or the `columns:` listed); classify breaks computed at export read both formats too. The readers ship inside core, so there is nothing extra to install, and installing core no longer pulls in OpenLayers, which the flatgeobuf package lists as an optional dependency. They are not part of core's main script: a page downloads a reader only when a map uses its format (see the entry on on-demand format readers). Cloud-native support adds about 12 KB gzip to the CDN build `register.browser.js`; the readers themselves (about 8 KB gzip for PMTiles, 12 KB for FlatGeobuf, 23 KB for GeoParquet, and 68 KB more for a brotli-compressed GeoParquet file) load only when needed. Across the whole 0.9 release, including thematic maps, translatable UI strings and number formatting, `register.browser.js` grows from about 124 KB to about 162 KB gzip (+38 KB) compared with 0.8.1.
