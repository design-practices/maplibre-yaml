`load: viewport` now has a limit per view, so zooming a large FlatGeobuf or GeoParquet file out to a whole city no longer reads the whole file (and re-reads it on every pan) until the tab runs out of memory. Before each read the map estimates how many features the view holds — from the FlatGeobuf spatial index or the GeoParquet row groups' extents, without downloading any features — and above the budget it reads nothing: readers see "Too many features to show here — zoom in to see them." over the map until they zoom in, and the author gets a one-time hint with the count. The default is 150,000 features per view; set it with `load: { mode: viewport, maxFeatures: 50000 }` (a whole number, 1 or more). The budget also applies to a file too large to load whole that switched itself to reading by view. A GeoParquet view is also left unread when the row groups it touches hold more than 3 × `maxFeatures` rows, since each is decoded whole: a file written in 100,000-row groups decoded about 600,000 rows for a view of 145,000 features (3.8 GB, 10 fps). Its author is told to rewrite it with about 10,000-row groups sorted along a Hilbert curve (a one-line `uvx … gpio sort hilbert` command in the hint), or — when the row groups are already small but loosely packed, as GDAL's `SORT_BY_BBOX` writes them — to sort it along a Hilbert curve, or to convert it to PMTiles. The same line shows below the source's `minzoom`, where nothing is read either, and a `fitTo` on a source read by view no longer frames it further out than that `minzoom`: a citywide file used to open on a blank map at zoom 9.9, and now opens at zoom 10, where its features load. The line follows the page's colour scheme, is hidden whenever `<ml-map quiet>` is set (not only when it first shows), and goes when the source's last layer is removed — a source no layer draws also stops reading on every move.
