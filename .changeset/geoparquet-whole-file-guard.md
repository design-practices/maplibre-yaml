GeoParquet and FlatGeobuf files are now read whole when they are small and by view when they are large, with a limit you can see and change. Before, the GeoParquet guard counted only the compressed bytes of the columns a map reads, so an 857,000-row file that downloads as 47 MB passed it and was decoded on the page (about 230 MB of columns, over 4 GB of memory). Both formats now check, before reading any data, how many features the file holds (GeoParquet's footer, FlatGeobuf's header) and, for GeoParquet, how large the columns it reads are once decoded. Up to 400,000 features (and 50 MB transferred, 150 MB decoded) a file loads whole, as in 0.9.1 — a 275,000-parcel borough still draws whole. Above that, a file that can be read in parts (a GeoParquet file with a `bbox` column and sorted row groups, an indexed FlatGeobuf) is read by view, and any other is refused with a notice that names the count and how to fix it. `load: { maxFeatures: N }` is the one override: above 400,000 it raises the whole-file limit for that source (heavier on memory; the 150 MB decoded limit still applies). A FlatGeobuf served compressed is now measured by its decompressed bytes, and the note that a large file is being read by view now reaches the page while the author is developing, not only the console.
